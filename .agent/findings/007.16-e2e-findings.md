recovery, concurrency, conflict, and multi-repository paths contain none.**

The 11 findings below are all in the _operator_ surface: what a human can see,
and what a human can do when something goes wrong. Nothing corrupted state, lost
work, or produced wrong code.

Severity: **0 critical · 6 major · 5 minor** — defensible because the happy path

## G1 — Idempotent re-invocations report false success

Re-running a terminal command prints the success line again, emits no event, and
changes nothing. An operator cannot distinguish "I just did it" from "it was
already done" — dangerous for the human-gated publish step.

- `B1 - action:YES - approve-integrated-objective-reports-success - `approve objective` on an already-`integrated`objective prints`objective integrated: <id>`again. No second`objective.integrated` event, no new commit — a silent no-op reported as an action.`
  - Severity: **major**
  - Repro: `node src/main.ts approve objective --id 01KYB1A2T6540GHHWRWT750AA1` (twice)
  - Suggestion: reject the transition with `ObjectiveNotAwaitingConfirmationError`, or print `already integrated` on a distinct exit path.
- `B2 - action:YES - republish-reports-success - `publish repository`on an already-published branch at the same OID prints`repository published: <id> -> <oid>`again with no new`repository.published` event.`
  - Severity: **minor**
  - Repro: run the publish command twice.
  - Suggestion: print `already published @<oid>` and skip the push.

## G2 — A failed task cannot be diagnosed from the CLI

The reason is captured in the event feed but is absent from the one command an
operator would actually run.

- `B3 - action:YES - get-task-hides-failure-reason - `get task`on a`failed`task prints only id/title/status/agent. No reason, no attempt count, no workspace, no branch — while`task.failed`carries`{"reason":"VerificationFailedError: … (exit 1)","attempts":"1"}`.`
  - Severity: **major**
  - Repro: task `01KYB1RG40N6TT6HFBCR51QVJQ` — `get task --id` vs. its `task.failed` event.
  - Suggestion: render `reason:` and `attempts:` on `get task` for `failed`, the same way `summary:` is rendered for `completed`.
- `B4 - action:YES - daemon-summary-not-run-scoped - The daemon's closing summary counts the whole DB, not the run. A run whose only task failed printed `1 initiative(s) landed` and exited 1 — that "landed" was an unrelated initiative from a previous run. No failure line at all.`
  - Severity: **major**
  - Repro: `.data/e2e-00716/daemon-fail.log` — last two lines are `1 initiative(s) landed` / `EXIT=1`.
  - Suggestion: scope the summary to initiatives touched by this run and always report failures first (`1 task(s) failed: <id> — <reason>`).

## G3 — No abandon path; lifecycle commands are asymmetric

- `B5 - action:YES - failed-task-cannot-be-discarded - A `failed`task's only exit is`retry`. `reject task`throws`TaskNotAwaitingConfirmationError` (`src/app/task/reject-task.ts:73`), and under the objective-branch workflow tasks go `pending → running → completed|failed`and never enter`awaiting_confirmation`. So an initiative holding one unachievable task can never reach a terminal state — `pause initiative` is the only escape, and pause is not terminal.`
  - Severity: **major**
  - Repro: `reject task --id 01KYB1RG40N6TT6HFBCR51QVJQ --resolution discard` → `error: task … is not awaiting confirmation; current status: pending`
  - Suggestion: allow `reject task --resolution discard` from `failed`, transitioning to a terminal `abandoned`, and let an objective complete when every task is `completed|abandoned`.
- `B6 - action:YES - no-reject-objective - `approve`and`retry`both have`objective`subcommands;`reject`has only`task`. Under 007.12 the objective is the review unit, so there is no way to reject the work an objective is asking to integrate.`
  - Severity: **major**
  - Repro: `node src/main.ts reject objective --id <id>` → `error: unknown command 'objective'`
  - Suggestion: add `reject objective --id --resolution retry|discard --reason`.
- `S1 - action:YES - retry-objective-missing-note - `retry task`accepts`--note <text>`to steer the retry;`retry objective` does not, so an objective retry carries no operator guidance.`
  - Severity: **minor**
  - Repro: `retry objective --id <id> --note x` → `error: unknown option '--note'`
  - Suggestion: accept `--note` on `retry objective` and pass it to the re-queued tasks.

## G4 — Delivery has no terminal state and no attributable event

- `B7 - action:YES - published-event-has-no-subject - `repository.published`is the only event with no subject id column — every other event carries`taskId`/`objectiveId`/`initiativeId`. The text renderer prints the literal `undefined`, and the id is reachable only inside `payload.repositoryId`.`
  - Severity: **major**
  - Repro: `list event --after 0 --limit 1000` → `01KYB1KXWR… repository.published undefined {"repositoryId":…}`
  - Suggestion: add a `repositoryId` subject to the event row so the feed is filterable by repository — 007.15 called publish "observable"; an unattributable event is not.
- `S2 - action:NO - initiative-has-no-published-terminal - After a successful remote push the initiative stays `landed` forever. Publication state lives only on the repository resource, so nothing at the initiative level says delivery finished.`
  - Severity: **major**
  - Repro: `get initiative --id 01KYB1A2T5CRCW35G2PEAFBAC6` after publish → `status: landed`
  - Resolution after debate: **do not fix in 007.16.** A `delivered` status
    duplicates per-target publication state (deliberate in 007.13) into a second
    place where it can _disagree_ with its source — a `diverged` target under a
    `delivered` initiative is a lie the model cannot express. It also hides an
    unmade decision (all targets vs. any). The reduced alternative — rendering
    per-target publication on `get initiative` — is _also_ a new feature needing
    initiative↔target correlation rules, so it is deferred too. 007.15 already
    removed a defined-but-undriven `delivered`; re-adding it now would repeat
    that mistake. If ever needed it must be **derived** from target states, never
    stored, with `initiative.delivered` emitted when the predicate first holds.

## G5 — CLI robustness and contract drift

- `B8 - action:YES - publish-unknown-branch-crashes - `publish repository --branch <unknown>`escapes as an unhandled`execSync`error: a raw Node stack trace with`Error: Command failed: git rev-parse refs/heads/…` and git's "ambiguous argument" hint.`
  - Severity: **major**
  - Repro: `publish repository --repository 01KYB160J67JDQC4JW255NHT4Z --branch nope/does-not-exist`
  - Suggestion: pre-check the ref and throw `UnknownReferenceError("branch", …)` so the CLI's error formatter renders one line.
- `S3 - action:YES - json-flag-is-not-ndjson - `list event --help`says "print events as newline-delimited JSON" but the command emits one`{"events":[…],"nextCursor":…}` object. Any consumer written to the documented contract breaks.`
  - Severity: **minor**
  - Repro: `list event --after 0 --limit 5 --json`
  - Suggestion: fix the help text to describe the envelope (do not change the shape — the `nextCursor` envelope is the better contract).
- `S4 - action:NO - e2e-playbook-drift - The `/e2e`skill doc is wrong in three places: it documents`retry objective --note`, says `list event`"caps at ~100 rows without --limit" (the default page is **5**, with a clear`more available — pass --after <id>`sentinel), and says the OAuth account lands in`~/.kanthord/accounts.json`(the real login creates a credential row in the DB; no`accounts.json` is ever written).`
  - Severity: **minor**
  - Suggestion: correct the skill doc. Not a program defect — fix alongside `S1`/`S3` rather than as its own story.
