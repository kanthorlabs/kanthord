## Findings

Severity: none critical (a working feature reached the remote). One group is
`major` (breaks the "to completion" + "pull progress" goal); the rest `minor`.

### Group 1 — Delivery lifecycle is disconnected from the initiative (MAJOR)

Root cause: `publish` is a standalone repository action. It does not touch the
initiative aggregate and does not write to the event feed. The deferred `pr@1`
agent (007.12) was the only thing that would have closed the loop.

- **1a [MAJOR] Initiative dead-ends at `awaiting_pr`.**
  After objective `integrated` + repo published to remote, `get initiative`
  still shows `status: awaiting_pr`. The domain defines the terminal transition
  `awaiting_pr->delivered` and the `delivered` state, but **no production use
  case invokes it** (callers: approve-objective, retry-objective, run-daemon,
  run-next-task — none handle it). There is no `deliver initiative` CLI verb.
  Repro:

  ```
  node src/main.ts get initiative --id 01KYA3R59WRAMMWWH3Q005AC1A
  # status: awaiting_pr   (after successful publish)
  ```

  Impact: the engineer can never drive an initiative to "done" via the CLI
  without the deferred pr@1 agent — directly against the project goal of
  building a feature "to completion".

- **1b [MAJOR] `publish repository` emits no event.**
  The `initiative.delivered` event type exists in `src/domain/event.ts` but is
  never emitted, and there is no `repository.published` event type at all. After
  a successful publish the pull feed's last event is `initiative.awaiting_pr`.
  Repro:
  ```
  node src/main.ts publish repository --repository <id> --branch kanthord/init/<id>
  node src/main.ts list event --after 0 --limit 1000   # nothing about publish
  ```
  Impact: a human polling `list event` (the pull-based progress/notification
  channel) never sees that the work was delivered to the remote.

Suggested fix (one coherent change): give the operator a manual completion path
that advances the initiative and records it — either a new `deliver initiative`
use case, or have `publish repository` (when it delivers the initiative's
branch) advance `awaiting_pr->delivered` and emit `initiative.delivered` +
`repository.published`. To be settled by debate (see below).

### Group 2 — Objective-branch landing target is invisible to the operator (MINOR)

- **2a [MINOR] Publishable branch name is not surfaced.**
  The landed work lives on `kanthord/init/<initiative-id>`. Neither
  `get initiative` nor `get objective` prints this branch, yet `publish
repository --branch <b>` requires it. The operator has to know the internal
  naming convention or spelunk `git branch` in the bare home.
  Suggestion: print the objective/initiative branch in `get initiative`
  (it already prints `workspace:`), or default `publish --branch` to it.

- **2b [MINOR/DOC] e2e playbook + helpers are stale vs. objective-branch flow.**
  The `/e2e` skill "Verify the real program" step uses
  `git -C .../home show HEAD:src/todo.mjs` — but the landed code is on
  `kanthord/init/<id>`, not home `HEAD`/`main`, so the documented command
  FAILS (`path 'src/todo.mjs' does not exist in 'HEAD'`). `e2e-status.sh` also
  still prints vestigial per-task `candidate:` columns (always `none`) left over
  from the superseded per-task gate.
  Suggestion: point the verify step at the objective branch; drop or repurpose
  the `candidate:` column.

### Group 3 — CLI noun consistency (MINOR)

- **3a [MINOR] `get repository` is missing.**
  `create repository`, `publish repository`, `land repository` all exist, but
  reading a repo back requires `get resource --id`. `get repository` errors with
  `unknown command 'repository'`.
  Suggestion: add `get repository` (alias to the resource read) for symmetry.

## Non-findings (verified, not bugs)

- Help subcommand bug from the skill gotchas did **not** reproduce:
  `publish repository --help` correctly showed the subcommand help.
- Objective landing on `kanthord/init/<id>` (not home `main`) is the delivery
  contract, not a bug — `main` moves only on publish.
- Serial sibling edits with no conflict is expected under the objective-branch
  workflow.
