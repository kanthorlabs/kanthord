## SOFTWARE-ENGINEER — Story B · fix migration 17 FK-parent rebuild

**Cycle.** GREEN for `src/storage/sqlite/migrations.test.ts` (3 failing tests reproduced by the FK constraint failure at migration 17).

**Files changed.**

- `src/storage/sqlite/migrate.ts` (edited) — `Migration` interface gains an optional `disableForeignKeys?: boolean` flag (documented: set when `up` rebuilds a table that is an FK _parent_). `applyOne` now, when the flag is set, runs `PRAGMA foreign_keys=OFF` before `BEGIN` and restores `PRAGMA foreign_keys=ON` in a `finally` after `COMMIT`/`ROLLBACK`.
- `src/storage/sqlite/migrations.ts` (edited) — migration `version: 17` (`"007.15-s2-initiative-landed-status"`) now sets `disableForeignKeys: true`, with a one-line comment explaining why. No SQL inside the migration's `up` changed.

**Root cause (verified against `node:sqlite` directly, not guessed).** `initiatives` is an FK _parent_ (`objectives.initiativeId TEXT NOT NULL REFERENCES initiatives(id)`). The migration-16-style rebuild pattern (`CREATE initiatives_new` → `INSERT...SELECT` → `DROP TABLE initiatives` → `RENAME`) works fine for FK _child_ rebuilds (events, migrations 8/12/16) but fails for a parent rebuild: `DROP TABLE` on a non-empty FK parent trips SQLite's foreign-key violation counter for every referencing child row. I verified two things with a minimal repro against `node:sqlite`:

1. `PRAGMA defer_foreign_keys=ON` issued _inside_ the transaction does **not** help — the violation counter is incremented by the `DROP TABLE` step and is never decremented (nothing re-touches the child rows), so `COMMIT` still fails even though `PRAGMA foreign_key_check` reports zero violations in the final state.
2. Disabling `PRAGMA foreign_keys` _before_ `BEGIN` (SQLite's documented 12-step table-rebuild recipe) and re-enabling it _after_ `COMMIT` avoids the counter entirely and leaves the database in a genuinely consistent state (`PRAGMA foreign_key_check` empty, child rows intact) — this is the fix applied.

Since `PRAGMA foreign_keys` is a documented no-op when toggled inside an active transaction, the fix could not live purely inside migration 17's `up()` (which only runs between the runner's `BEGIN`/`COMMIT`) — it required a small, targeted addition to the runner (`migrate.ts`) that only activates for migrations that opt in via the new flag. Every other migration is unaffected (`disableForeignKeys` defaults to falsy, so `applyOne`'s behavior for versions 1-16 is byte-for-byte the same as before).

**Seam (GREEN).** With `disableForeignKeys: true` on migration 17, `applyOne` disables FK enforcement before starting the migration's transaction, runs the same DROP/RENAME rebuild SQL as written by the RED turn, commits cleanly, and re-enables FK enforcement — so `migrations.test.ts`'s three previously-failing tests (which exercise migration 17 against a non-empty database with existing `objectives` rows referencing `initiatives`) now complete without a `FOREIGN KEY constraint failed` error.

**Refactor.** None named for this Task; the fix is the minimal targeted addition (a runner-level opt-in flag), not a broader migrate.ts refactor.

**Build check.**

- typecheck: `npm run typecheck` → exit 0, clean.

**Assumptions.**

- VERIFIED (via a standalone `node:sqlite` repro, not just SQLite docs recollection): `PRAGMA foreign_keys=OFF` issued before `BEGIN`, with the DROP+RENAME rebuild inside the transaction, then `PRAGMA foreign_keys=ON` after `COMMIT`, leaves `PRAGMA foreign_key_check` empty and the child table's data intact — confirming this is a real fix, not just error suppression.
- VERIFIED: `migrate.ts`'s `Migration` interface is only consumed by `migrations.ts`'s array literals and the `migrate()` function itself (grepped `src/` for other `Migration` usages) — adding an optional field is a backward-compatible, additive change; migrations 1-16 don't set it and are therefore unaffected.
