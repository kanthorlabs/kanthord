## 2026-07-28 · Story 4 S4-T1 GREEN (013-lease-fenced-run-recovery) — requeue on exit

- Decided to extract `requeueRunningTask` per the Story 4 spec verbatim (plain exported function, `RequeueStore` interface, no `uow.transaction` call inside — caller is already inside one). The precedent `settleObjective` in `src/app/objective/settle-objectives.ts:40-63` is the right shape: shared transition function with a narrow deps object. Refactored `RecoverInterruptedTasks` to reuse it (the original `transitionTask` + `newEvent` imports became unused and were removed; verified by `rg`).
- Decided to loosen `SqliteJobQueue.discard` from `WHERE id=? AND status='running' AND revoked=0` to `WHERE id=? AND status='running'`. The TE's "Open to Software Engineer" did not name this change explicitly, but the Story 4 spec requires `requeueRunningTask` to delete a revoked row (a `running, revoked=1` row, mid-drain), and the S2 lease guard on `discard` would otherwise throw `StaleLeaseError` and roll back the entire requeue transaction. The S2 late-write invariant is preserved: a _discarded_ (gone) row matches zero rows under either SQL, and the S2 test at `sqlite.test.ts:1024` (the only `discard`-throws assertion) drives that exact case. `finish` keeps its strict `AND revoked=0` guard because its semantics are different — it's a state mutation, and a revoked run must not write `completed`/`failed` to the queue.
- Decided to fill the tx2 abandoned branch with `listRunningJobsForTask(taskId).find(j => j.id === jobId)?.revokeReason ?? ""` BEFORE calling `requeueRunningTask`. The order is load-bearing: requeue discards the row, and the reason is unrecoverable after the discard. The TE's "Open to Software Engineer" pinned this ordering; the test at `run-next-task.test.ts:2284-2369` asserts the reason round-trips from the revoked row to the `task.abandoned` payload.
- Flagged the S3 test at `run-next-task.test.ts:2178-2242` as `ATTEMPT-FAILED:` (TE's lane). The test was written for Story 3's "soft early return" contract and asserts `events === ["task.started"]` / `store.saved.length === 1` — those are now stale because the tx2 fill-in produces `["task.started", "task.ready", "task.abandoned"]` and `store.saved.length === 2`. The test's first 3 assertions (result, no finish, no saveTaskResult) still pass. The fix is mechanical: update the S3 assertion set, or merge into the S4 test.
