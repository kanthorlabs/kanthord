# EPIC 007.19 — Refuse an apply that references an uncreatable objective

## Goal

`import graph --apply` **silently ignores** a brand-new objective authored in the
package, promises in `--dry-run` to create tasks that reference it, and then dies
mid-transaction with an unhandled stack trace. After this epic, such a package is
refused at preflight with one actionable line, and `--dry-run` shows the problem
before anything is written.

Measured against the current tree (`scripts/e2e/uncreatable-objective-proof.sh`,
which fails at its first assertion today):

```
$ import graph <pkg> --apply --initiative <id> --dry-run     # exit 0
unchanged: … (initiative.md)
unchanged: … (objective.md)
unchanged: … (task-base.md)
would create: orphan-task (…/task-orphan.md)
1 created, 0 updated, 3 unchanged, 0 missing
                                    ← `orphan-obj` is never mentioned at all

$ import graph <pkg> --apply --initiative <id>               # unhandled throw
InvalidObjectiveIdError: Invalid objectiveId (not found): orphan-obj
    at #assertObjectiveExists (sqlite-task-repository.ts:101:13)
    at SqliteTaskRepository.save (sqlite-task-repository.ts:106:32)
    at ApplyGraph.execute (apply-graph.ts:702:24)
    at runApply (import-graph.ts:178:31)                     ← escapes the boundary
    … 8 more frames
```

The defect is an asymmetry between how tasks and objectives are handled in
`src/app/graph/apply-graph.ts`:

```
:683  pkg.tasks.filter((t) => t.id === undefined)       ← id-less TASKS are collected and created
:686  pkg.objectives.filter((o) => o.id !== undefined)  ← id-less OBJECTIVES are filtered OUT
```

Three consequences, and the third is the one that costs a debugging session:

1. The classify loop only runs `if (obj.id !== undefined)` (`:277`), so a new
   objective produces **no classification line at all** — not `created`, not
   `missing`, nothing. `--dry-run` reports a clean plan.
2. The write phase has exactly one `created` branch and it is
   `cls.kind === "task"` (`:814`). There is no objective-creation path anywhere.
3. So the objective is dropped, and its tasks resolve through `objRefToId`'s
   `o.id ?? o.ref` to the bare ref slug. EPIC 007.18's boundary guard catches it at
   the repository — but only **after** `uow.transaction` has opened, and the throw
   **escapes** the `runApply` error boundary (it is not registered in
   `error-map.ts`), so the user gets a 12-frame stack trace instead of one line.

Note the guard's message value is already correct — it names `orphan-obj`, the
objective, not the task. Three things are wrong, and none of them is the wording:
**`--dry-run` is silent and exits 0** while actively promising `would create:
orphan-task`; the failure is discovered **mid-transaction** rather than at
preflight; and it surfaces as an **unhandled stack trace**, not a mapped CLI error.

This epic does **not** add the ability to create objectives through `--apply`
(see Non-goals). It makes the existing limitation honest and visible before any
write, and routes it through the CLI error boundary.

### Decision record

- **The gate belongs in `ApplyGraph`, not the CLI.** A package that references an
  uncreatable objective is invalid _data_; the use case is the only place that
  protects every caller. This mirrors EPIC 007.18 Story 3's placement of
  `StaleManifestError`.
- **Refuse the whole apply, do not partially apply.** The package expresses one
  intent. Writing the tasks that happen to resolve while dropping the ones that do
  not is the false-success reporting EPIC 007.16 Story 3 already fought.
- **The error must be a mapped one-liner, not a stack trace.** 007.18's guard
  already names the right value (`orphan-obj`); what it lacks is registration in
  `error-map.ts`, so it escapes `runApply` as an unhandled rejection. The new
  preflight error must name the objective ref, list the task refs blocked by it,
  state the remedy, and exit non-zero with **one** stderr line and empty stdout.
- **Detection is preflight, before the first write.** `--dry-run` must report it,
  which means the check cannot live in the write phase where 007.18's guard sits.
  007.18's `InvalidObjectiveIdError` stays as the last-resort backstop at the
  repository boundary; this epic makes it unreachable through this path.
- **Two remedies exist and the message must pick the right one.** `create objective`
  (`src/apps/cli/commands/create/objective.ts` — the command already exists) adds
  the objective to a live initiative; `--create` builds a fresh initiative from the
  whole package. The message names `create objective`, because by definition the
  initiative here is already live.

## Verification Gate

Gates: `npm run verify` (typecheck + test + verify:handoff + lint + db status)

Proof: one committed script (AGENTS.md — the Verification Gate sets up validation
in a bash script, never inline). Hermetic: no model, no network, no repository.

```sh
scripts/e2e/uncreatable-objective-proof.sh
```

Exits 0 and prints `007.19 PROOF OK` only when all four cases hold against the
real program. The script owns `.data/proof-00719`, builds a one-objective /
one-task graph on `agent: fake@1`, imports it with `--create`, then appends a
second objective file with a **new** ref plus a task pointing at it, and asserts:

1. **`--dry-run` reports the problem.** It names the unresolvable objective ref
   (`orphan-obj`) and exits non-zero. Today it exits **0**, never mentions
   `orphan-obj`, and prints `would create: orphan-task` — a promise the apply
   cannot keep. This is the heart of the epic and the assertion that fails first
   against the current tree.
2. **`--apply` refuses and writes nothing.** Exit is non-zero, the new task does
   not appear in `list task --initiative --json`, and the pre-existing task's
   title is unchanged.
3. **The refusal is a mapped one-liner, not a stack trace.** The output names
   `orphan-obj` and does **not** contain the raw class name
   `InvalidObjectiveIdError`, a `FOREIGN KEY constraint failed`, or stack frames
   (`at ApplyGraph.execute`). Today the throw escapes `runApply` and prints 12
   frames.
4. **A package whose objectives all resolve still applies.** Regression guard:
   remove the orphan objective file and its task, retitle the original task, and
   `--apply` succeeds. This must keep passing — the gate must not become a blanket
   refusal.

Task shape follows EPIC 007.18's Proof: `fake@1`, no initiative `bindings:`, no
task `context:`, no `.fake-agent.json`. `fake@1` is absent from
`EXECUTOR_BINDING_SPECS` (`binding-resolver.ts:17`) so the import takes no
`--bind` flag. Unlike 007.18 the daemon never runs — this epic is about preflight
classification, so no task needs to reach a terminal state.

## Stories

1. **Detect and refuse at preflight** — collect the package's unresolvable
   objective refs during classification and throw a new
   `UncreatableObjectiveError` before the write phase opens its transaction.
   - An objective ref is _unresolvable_ when a package task's `objectiveRef` is
     neither a key of the package's ref→id map with a real `id`, nor an existing
     objective in the DB. Reuse `apply-graph.ts`'s existing `objRefToId` /
     `resolveObjectiveId` (hoisted in 007.18 to `:247-251`) rather than adding a
     second resolution mechanism — there must stay exactly one.
   - Aggregate: one error for the whole package listing every unresolvable
     objective ref and, per ref, the task refs blocked by it. Do not throw on the
     first one — a user fixing three new objectives should learn all three in one
     run.
   - Throw before `uow.transaction` opens, so `--dry-run` and `--apply` take the
     same path and neither writes.
   - Note the id-less-objective case is currently invisible: `:686` filters those
     rows out of `pkgObjById`. The detection must look at what the **tasks**
     reference, not only at what the objective list contains, or a new objective
     with no tasks pointing at it would still slip through unreported.
2. **Surface it through the CLI** — register `UncreatableObjectiveError` in
   `src/apps/cli/error-map.ts` and confirm it flows through the `runApply` error
   boundary EPIC 007.18 Story 3 added (`import-graph.ts`). One line to stderr,
   non-zero exit, empty stdout — the `apps/cli/get.ts:29` idiom. The message must
   name `create objective` as the remedy.
3. **The Proof script** — `scripts/e2e/uncreatable-objective-proof.sh` plus its
   generator `scripts/e2e/make-orphan-objective-graph.sh <dir> [--add-orphan]`,
   following the conventions of `make-sha-graph.sh` / `sha-classification-proof.sh`
   (755, `set -Eeuo pipefail`, ERR trap naming the failing line, quoted heredocs,
   generator prints nothing, negative assertions use `! grep -q` never `grep -vq`,
   and every command whose exit code matters is **captured to a file** rather than
   piped into `grep -q` — the `pipefail` race that made 007.18's Proof flaky in
   ~40% of runs).

## Non-goals

- **Creating objectives through `--apply`.** That is the real capability behind
  this defect and it needs its own epic: it drags in ordering (the objective must
  be written before its tasks in one transaction), `after:` sequencing edges,
  `creation_sha` recording, and stamping the minted id back into the file. This
  epic deliberately ships the refusal instead, so the tool stops lying while that
  work is planned properly.
- Any change to how id-**bearing** objectives are classified, updated, or
  reparented — EPIC 007.18 owns that and its tests pin it.
- Re-litigating 007.18's boundary guard. `InvalidObjectiveIdError` stays as the
  repository-level backstop; this epic simply makes it unreachable via this path.
- Initiative-level equivalents. A package whose `initiative` is unknown is already
  handled (`UnknownNodeError`, `apply-graph.ts:453`).
