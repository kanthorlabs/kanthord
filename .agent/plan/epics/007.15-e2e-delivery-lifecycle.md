# EPIC 007.15 — Local-done initiative state + observable publish

## Goal

The E2E run (`.agent/findings/007.15-e2e-findings.md`) showed two lifecycle
gaps. First, once all its objectives integrate, an initiative goes straight to
`awaiting_pr` and stops there — but `awaiting_pr` conflates two different things
("the local work is done" and "a PR is open/awaited"), and the deferred `pr@1`
agent is the only thing that would ever move it on. Second, `publish repository`
delivers the branch to the remote but writes nothing to the pull-based event
feed, so a human polling `list event` never sees the delivery.

This epic collapses the initiative lifecycle to just what is real today and
makes delivery observable:

- Replace `awaiting_pr` with a terminal-for-now initiative status **`landed`** =
  _the work is locally done_ (all objectives integrated into the bare managed
  home), reached automatically at integration, with an `initiative.landed`
  event. No manual verb — local completion is automatic.
- **Remove `awaiting_pr` and `delivered` entirely** (domain, migration, event
  types, daemon check, docs). They were defined-but-undriven; a future `pr@1`
  agent will introduce its own PR states (likely per delivery target) when it is
  actually built. Initiative lifecycle is now just `building → landed`.
- `publish repository` emits a new `repository.published` event (it still does
  not change the initiative status — remote delivery lives in per-`(repo,branch)`
  publication state).

Decision record: the `landed` name and the removal of `awaiting_pr`/`delivered`
were confirmed by the human after an adversarial debate of the alternatives
(keep-reserved vs remove; `landed` vs `integrated`).

## Verification Gate

Gates: `npm run verify` (typecheck + test + verify:handoff + lint + db status)

Proof: run against the real program on an isolated DB — build the TODO graph,
integrate, publish, and show the initiative lands locally (with event) and the
publish is observable:

```sh
export KANTHORD_DB="$PWD/.data/proof-00715/kanthord.db"
mkdir -p "$(dirname "$KANTHORD_DB")"
node src/main.ts db migrate
# ... author TODO graph, import, run daemon --until-idle, approve objective ...
# with INIT=<initiative id>, REPO=<repo id>, BR=kanthord/init/$INIT :

# 1) initiative reaches the local-done terminal automatically at integration:
test "$(node src/main.ts get initiative --id $INIT | sed -n 's/^status: //p')" = "landed"
# 2) the local-done event is on the feed exactly once:
node src/main.ts list event --after 0 --limit 1000 --json \
  | grep -o '"type":"initiative.landed"' | wc -l | grep -qx 1
# 3) awaiting_pr is gone — never emitted:
node src/main.ts list event --after 0 --limit 1000 --json \
  | grep -c '"type":"initiative.awaiting_pr"' | grep -qx 0

node src/main.ts publish repository --repository $REPO --branch $BR
# 4) publish is observable on the feed:
node src/main.ts list event --after 0 --limit 1000 --json \
  | grep -o '"type":"repository.published"' | wc -l | grep -qx 1
echo "PROOF OK"
```

Must print `PROOF OK`.

## Stories

- **Story A — `repository.published` event (idempotent).** Add the
  `repository.published` event type; inject the shared `EventFeed` + UnitOfWork
  into `PublishRepository`; emit the event (payload `{repositoryId, branch,
remoteOID}`) atomically with the publication-state write, only on a real
  transition to `published` for that `remoteOID` (not on no-op re-publish).
- **Story B — `landed` local-done status; remove `awaiting_pr`/`delivered`.**
  Replace the initiative status `awaiting_pr` with `landed` and the event
  `initiative.awaiting_pr` with `initiative.landed`; delete `delivered` and
  `initiative.delivered`; the only initiative transition is `building->landed`.
  Retarget `approve-objective` and the daemon's post-integration check
  (`run-daemon.ts`) to `landed`. Includes the SQLite migration (rebuild the
  initiatives status CHECK to `('building','landed')` and the events type CHECK
  to drop the two removed types and add `initiative.landed` + Story A's
  `repository.published`).

## Non-goals

- The deferred `pr@1` agent and any PR/delivery states it will need. `pr@1`
  introduces its own states (likely per delivery target) when it is built; this
  epic deliberately does not pre-add them.
- Any manual "deliver/complete initiative" CLI verb — local completion is
  automatic at integration; remote publish stays a separate per-repo action.
- A multi-repo / multi-branch delivery manifest.
- Findings S1 (surface the publishable branch in `get initiative`), S2 (refresh
  the `/e2e` playbook + `e2e-status.sh` columns), S3 (`get repository`) — fixed
  directly as maintainer edits, not through this epic.
