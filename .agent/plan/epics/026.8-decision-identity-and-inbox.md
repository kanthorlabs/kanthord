# EPIC 026.8 — decision occurrences: stable identity, real names, an addressable Inbox

> Authored 2026-07-31. The design went through the debate engine (`pi`,
> read-only). It rejected the draft's derived id outright, rejected `410` as the
> answer for a closed decision, and reorganised the whole remaining API-gap
> inventory **by operator loop instead of by API prerequisite** — recorded as
> the 026.8 family in `docs/ui-design.md`. Eight findings are marked
> **[debate]**.
>
> Execution order: 026 → 026.1 → … → 026.7 → **026.8** → 026.9 … → 026.15.
> **This is the first UI epic that writes `src/**` as well as `ui/**`**, so its
> stories touch domain, app, adapter and HTTP layers under the ordinary
> architecture rules.

## Goal

A decision stops being an anonymous row. Each one becomes a persisted
**occurrence** with an opaque id, a stable machine kind, and a lifecycle the
server can answer for: open, resolved or expired. The queue carries the entity
names it already reads, so the Inbox stops showing shortened ids. A decision has
a URL. Filtering happens on the server, before ranking and limiting, so a
filtered view is the truth rather than a slice of a capped page.

## Verified facts (measured on this tree, 2026-07-31 — do not re-litigate)

- The queue is a **projection with no table**: `getDecisionQueue` recomputes
  items per call, and `DecisionItemView` (`views/queue.ts:11`) carries no id.
- **`GetDecisionQueue` already reads the names** — task titles
  (`get-decision-queue.ts:278`), objective names (`:309`), initiative names
  (`:263`), project names (`:335`) — and the DTO discards all but
  `projectName`. **[debate]**
- A decision exists only for: task `awaiting_confirmation`, task `failed`,
  objective `conflict`, objective `awaiting_confirmation`, or initiative
  `landed` with publication `unpublished`/`diverged`
  (`src/domain/actionability.ts:389`).
- `kindLabel` is a **presentation label**. Identity and filtering must not
  depend on it; a stable machine kind is a separate field. **[debate]**
- `actionableSince` can be `null`, so an occurrence cannot always be derived
  from "the opening actionable event". Existing decisions need minting or
  backfill. **[debate]**
- `GET /api/queue` takes only `?limit` (1–500) and returns `counts {total,
byKind}`, `truncated`, `warnings[]`. Order is `downstream` desc,
  `actionableSince` asc (null last), then id.
- A decision **recurs**: a failed task can be reattempted and fail again. Any
  identity derived from `(entity, kind)` would give two distinct occurrences the
  same id, and a stale tab would address the new one as the old. **[debate]**

## Decisions (binding)

1. **A decision is a persisted occurrence, not a hash.** A small table holds an
   opaque ULID, the subject type and id, the **machine kind**, the opening event
   id where one exists, the lifecycle state, and the resolution metadata. The
   projection opens an occurrence when a decision first appears and closes it
   when it stops applying. A tuple hash is rejected: it is unstable across a
   kind change, it collides across recurrences, and it cannot tell a real past
   decision from a fabricated id. **[debate]**
   Identity is keyed by the **subject** — at most one occurrence per subject is
   open — and the **opening event id is the generation marker**: a subject that
   re-enters the state under a new opening event closes the old occurrence
   (`superseded`) and opens a new one, even when no reconcile ever observed the
   gap. Without that marker a retry followed by a second failure would let a
   stale tab address the new decision as the old — the exact failure this
   decision exists to prevent. **[debate]**
2. **Existing decisions are minted on first sight, and the upgrade is that first
   sight.** `actionableSince: null` items have no opening event, so the
   occurrence is minted when the projection first observes them. `db migrate`
   runs the projection **once** after applying the schema, so every decision open
   at upgrade time is minted by the upgrade itself and not left waiting for
   somebody to open the Inbox. A migration may not import `src/domain/`, so the
   backfill is a post-migration step in `db migrate`, never SQL; it is idempotent,
   so a second `db migrate` mints nothing new. No silent fallback to a derived id.
   **[debate]**
3. **`GET /api/queue/:id` answers `200` with a lifecycle representation** —
   `state: "open" | "resolved" | "expired"` — for every occurrence the server
   knows, and `404` for an id it never issued. **`410` is rejected**: the draft
   promised a resolved representation and then proposed returning an error
   instead of it, and `410` is cacheable by default. **[debate]**
4. **`resolved` and `expired` are defined here, not left as adjectives — and
   the test is an event, not an adjective.**
   `resolved` = a **verdict event** for the decision's subject exists after the
   occurrence opened: `task.ready` (retry), `task.approved`, `task.rejected`,
   `task.discarded`, `task.abandoned`, `objective.integrated`,
   `objective.discarded`, `initiative.discarded`, or `repository.published` for
   the initiative's repository. That event id is the closing event id.
   `expired` = it stopped applying with no such event, in one of two named
   causes: `superseded`, when the same subject re-entered the state under a new
   opening event (a recurrence), or `vanished`, when the subject simply left the
   state that produced it. The representation names the cause, and carries the
   closing event id when one exists. A "state change" with no event of its own is
   `expired`/`vanished` — the server does not guess intent. **[debate]**
5. **Machine kind is a separate field from `kindLabel`.** `kind` is a stable
   enum used for identity, filtering and tests; `kindLabel` stays the
   presentation string and may change without breaking anything. **[debate]**
6. **The queue DTO carries the names the projection already read** — the task
   title, the objective name, the initiative name — so the Inbox needs no
   fan-out. 026.7 decision 2's id-labelled rows become real titles here.
7. **A resolved detail keeps a display snapshot.** Names on a closed occurrence
   come from the snapshot **as last observed while the occurrence was open**,
   refreshed on every reconcile that still saw it — never from a live join, so a
   rename or a deletion does not rewrite history. A closing reconcile no longer
   sees the subject, so "the names at the instant it closed" is not obtainable
   and is not claimed: the representation marks the names as historical and says
   they are as last observed. **[debate]**
8. **Filtering happens on the server, before ranking and limiting.**
   `GET /api/queue?kind=<machine kind>&project=<id>`; `project` is an id, never
   a name. `counts.total` and `counts.byKind` stay **global** and are labelled
   as such, so a filtered view never hides how much is really waiting.
   **[debate]**
9. **"Next open item" is honest or absent.** With filters and ids it is
   implementable for the current filtered order; where the window is capped, the
   control says it moves within the loaded window. It is never a bare "Next"
   over a truncated page. **[debate]**
10. **The Inbox gets its deep link**: `#/inbox/:decisionId`, unblocked at last
    (026.1 decision 4 forbade it, 026.7 decision 1 called it unsupported).
    A `404` renders AsyncBoundary `missing`; a closed occurrence renders
    `resolved` or `expired`, never `missing`.

## Verification Gate

Gates: `npm run verify`.

Hermetic coverage required beyond the Proof:

- **Domain/app**: an occurrence is opened once per decision and reused while it
  stays open; a decision that closes and recurs gets a **second, different** id,
  including when no reconcile observed the gap (the opening event changed); a
  kind change does not change an existing id; minting covers
  `actionableSince: null`; the whole reconcile runs in one transaction.
- **Upgrade**: `db migrate` backfills the decisions open at that moment exactly
  once; running it twice mints nothing new.
- **HTTP**: `GET /api/queue/:id` is `200` for open, resolved and expired, and
  `404` for an unknown id; no path answers `410`; `?kind=` and `?project=`
  filter **before** limiting, proven by a fixture larger than the limit;
  `counts` stay global under a filter.
- **View**: the DTO carries `id`, `kind`, the entity names and the state; a
  closed occurrence carries its snapshot names and is marked historical.
- **UI**: a row renders its real title; the kind filter issues a server request
  and does not filter client-side; `#/inbox/:id` renders open, resolved and
  expired distinctly, and `missing` only for a `404`.
- **Regression**: 026.7's Proof still passes — the Inbox keeps its literal order
  statement, its truncation banner and its no-fan-out rule.

Proof: `scripts/e2e/ui-decision-identity-proof.sh` — deterministic, no model, no
outbound network, nothing left running. It reuses 026.7's fixture recipe
(`KANTHORD_FAKE_AGENT` + `make-landing-graph.sh` + `run daemon --until-idle`) to
produce a **real** decision:

```bash
scripts/e2e/ui-decision-identity-proof.sh
```

It must print `026.8 ok: …`. Phases:

- **A** — build the UI; Chromium present, or exit with the install command.
- **B** — the fixture: drive the root task to `failed` for real; assert the task
  status from SQLite before any UI assertion.
- **C** — `GET /api/queue` now returns an `id` and a machine `kind` per item,
  plus the task's real title; the same id comes back on a second call
  (**stability across recomputation** — the point of decision 1).
- **D** — `GET /api/queue/:id` is `200` with `state: "open"`; an unknown id is
  `404`; **no route answers `410`**.
- **E** — the decision is closed for real by retrying the task through the CLI
  and running the daemon again, so the task fails a second time; the same id is
  then `200` with a **closed** state, the closing reason, and historical names —
  not a `404` — and the second failure is a **new** occurrence with a new id,
  itself `open`. The re-run is required, not decoration: a retry alone leaves the
  queue empty, which would make phases F and G vacuous.
- **F** — filtering is server-side: `?kind=<the other kind>` returns zero items
  while `counts.total` still reports the global total (measured after the
  recurrence, so the total is real).
- **G** — in the browser: the Inbox row shows the real title; the kind filter
  issues a request carrying `kind=`; `#/inbox/<id>` cold-loads the decision and
  renders its state; `#/inbox/<unknown>` renders `missing`.
- **H** — R3 holds: no request the page issued carried an `Authorization`
  header.

Ran against the CURRENT tree (2026-07-31): the script exits `1` in phase C,
because the queue DTO has no `id` (`src/apps/http/views/queue.ts:11-32`). Phase A
now passes — `ui/` and `npm run build:ui` landed with EPIC 026.

## Stories

- **S1 — the occurrence in the domain**: opening, closing, recurrence, machine
  kind (decisions 1, 4, 5).
- **S2 — persistence + migration**, including the backfill of decisions open at
  migration time (decision 2).
- **S3 — the projection writes occurrences** and reuses open ones.
- **S4 — the queue DTO** gains `id`, `kind`, the names and the state
  (decisions 5, 6).
- **S5 — `GET /api/queue/:id`** with its three states and `404` (decisions 3,
  4, 7).
- **S6 — server-side filters** before ranking, with global counts (decision 8).
- **S7 — the Inbox wiring**: real titles, the filter control, `#/inbox/:id`,
  and an honest "Next" (decisions 9, 10).
- **S8 — the Proof**: `scripts/e2e/ui-decision-identity-proof.sh` prints
  `026.8 ok: …` without its assertions being edited.

## Non-goals

- **No approve, reject, reattempt, abandon, pause or resume** — 026.9–026.11,
  and approval deliberately waits for the candidate diff so evidence lands
  before the response can act on it.
- **No candidate diff** — 026.9.
- **No event feed, no acknowledgement, no digest paging** — 026.12.
- **No agent API.** Deferred; a list endpoint joins the epic that needs it.
- **No `410` anywhere** (decision 3).
- **No client-side filtering** (decision 8).
