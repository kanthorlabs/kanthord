# EPIC 007.18 — Separate content drift from lifecycle progress

## Goal

`canonicalTask` (`src/domain/sha.ts:8-28`) hashes `status` alongside the task's
declarative content. Because `save()` re-stamps the sha on every write
(`sqlite-task-repository.ts:87-88`), a task that merely _ran_ gets a different
`sha256` than the baseline recorded at import time. `classifyNode`
(`apply-graph.ts:77-90`) checks `liveSha !== baselineSha` **first** (`:85`), so that
task classifies `drifted`, `drifted` is a blocking conflict (`:398-401`, gated at
`:415`), and the whole `import graph --apply` writes nothing.

Proven numerically on the real E2E DB (task `01KYB1A2T6540GHHWRWT750AA2`, all
other canonical fields byte-identical):

```
live DB status              : completed
tasks.sha256 (live)         : 4258b7c53b9c7cef…
manifest baseline           : 43e854c0928f8f3b…
recompute with status=pending  : 43e854c0928f8f3b…   ← equals the baseline
recompute with status=completed: 4258b7c53b9c7cef…   ← equals the live sha
```

Corroboration: `canonicalObjective` / `canonicalInitiative` (`sha.ts:31-44`) do
**not** hash status, and in that same run the initiative and objective classified
`unchanged` while all five tasks classified `drifted`.

Consequence: **once a task has run, no `--apply` can ever succeed on its
initiative again.** Conflicted nodes keep their old baseline (`:664-676`, plus the
CLI merge at `import-graph.ts:241-245`), so the drift never heals. This is the root blocker for inserting work into a live plan
(`.agent/findings/007.17-midway-insertion-findings.md`, `F1`).

After this epic:

- `canonicalTask` hashes **declarative content only** — status is removed.
- A completed task whose file nobody touched classifies **`unchanged`** and is not
  written, so it stops blocking the addition of a _different_ task.
- The lifecycle protection that status-in-sha was providing is **kept, and made
  explicit**: the CAS gains its own `status` predicate.

### Why status was in the hash (design intent, preserved)

Status was embedded deliberately, as a race guard. `compareAndApply`
(`sqlite-task-repository.ts:331-350`) compares **only** the sha, so a status change
was the thing that invalidated a stale CAS:

```
t0  apply preflight: task X is `pending`, content changed → classify `updated`
t1  daemon (separate process) claims X → status=`running` → save() re-stamps sha256
t2  apply CAS: expectedSha ≠ current sha → conflict → rollback        ✅ caught
```

Removing status from the hash without replacing this guard would let step `t2`
succeed and **overwrite the instructions of a running task**. This epic therefore
replaces the implicit signal with an explicit predicate; it does not drop it.

### Decision record

- **The status predicate becomes explicit, not implicit.**
  `compareAndApply(id, expectedSha, expectedStatus, spec)` and
  `conditionalDeleteTask(id, expectedSha, expectedStatus)` both guard on two
  predicates with two distinct meanings. `compareAndApply` does it in one atomic
  statement — `UPDATE … WHERE id = ? AND sha256 = ? AND status = ?`, no affected
  rows meaning conflict. `conditionalDeleteTask` cannot: its five non-cascading
  child tables must be cleared before the `tasks` row, so the predicate is checked
  by a single read first (see Story 1). That read is not a TOCTOU window —
  `node:sqlite` is synchronous and the caller holds `BEGIN IMMEDIATE`.
- **This is strictly better than status-in-sha**, for three reasons: the two
  failure modes become distinguishable in the error message ("content changed
  underneath" vs "task is no longer pending"); the `locked` check at
  `apply-graph.ts:87-88` stops being **shadowed** by the `drifted` check above it
  (today it is unreachable for any progressed task); and an untouched progressed
  task stops being a conflict.
- **The race only exists for nodes that are written.** `unchanged` writes nothing,
  so it needs no CAS and has no race — which is why removing status from the hash
  costs nothing for the insertion use case:

  | Live state              | Package intends | Class       | Writes? | Race possible?           |
  | ----------------------- | --------------- | ----------- | ------- | ------------------------ |
  | ran, file untouched     | no change       | `unchanged` | no      | no                       |
  | pending, file edited    | change          | `updated`   | **yes** | yes → explicit predicate |
  | ran, file edited        | change          | `locked`    | no      | no                       |
  | changed behind our back | any             | `drifted`   | no      | no                       |

- **Three sha stores must move in lockstep.** `tasks.sha256` (live),
  `graph_import_map.creation_sha` (DB baseline — verified to hold `43e854…`, the
  same value as the manifest), and the on-disk `.kanthord-export.json` manifests.
  The first two are migrated; manifests are outside the DB and must be re-exported.
  Missing any one of these reintroduces universal drift — the exact bug being fixed.
  "Lockstep" means _for rows that had not really drifted_: a `creation_sha` whose
  content genuinely diverged before the migration is deliberately left alone, so
  real drift survives instead of being laundered into `unchanged` (Story 2).
- **The race itself is proven by a hermetic unit test, not by the Proof block.** A
  true interleaving cannot be made deterministic from a shell script, and a
  timing-dependent Proof gate would be flaky. The Proof proves the observable
  classification contract (the wiring); a fake repository that flips status between
  classification and write proves the guard (the unit). This is a deliberate split,
  per AGENTS.md: tests prove the units, the Proof proves the wiring.

## Verification Gate

Gates: `npm run verify` (typecheck + test + verify:handoff + lint + db status)

Proof: one committed script (AGENTS.md — the Verification Gate sets up validation
in a bash script, never inline). Hermetic: no model, no network, no repository.

```sh
scripts/e2e/sha-classification-proof.sh
```

Exits 0 and prints `007.18 PROOF OK` only when all five cases hold against the real
program. The script (authored in Story 5, alongside its graph generator
`scripts/e2e/make-sha-graph.sh`) creates its own project and DB under
`.data/proof-00718`, builds a three-task graph, drives one task to `completed` and
one to `failed`, then asserts:

1. **the fix** — a `completed` task whose file nobody touched classifies
   `unchanged: <ran-task>` and **not** `drifted`. Before this epic that single
   classification blocked every `--apply` on the initiative forever.
2. a **new** task lands on an initiative that has already run work
   (`make-sha-graph.sh $G --add-new-task` writes only `task-new.md`, leaving the
   other files and the live manifest untouched) and arrives `pending`. Its id comes
   from `list task --initiative --json` matched on title, because there is no
   `find task` subcommand — `find` covers project / initiative / objective /
   resource only.
3. editing a **pending** task's file still applies (`updated`). This is a
   regression guard: it passed before this epic too, and must keep passing.
4. editing a **completed** task's file is refused as `locked: <ran-task>` and is
   **not** written. Before this epic the `locked` check at `apply-graph.ts:88` was
   unreachable — the `drifted` check above it shadowed every progressed task.
5. a real out-of-band content change (`add dependency`, which restamps the sha) is
   still caught as `drifted: <idle-task>`.

Task shape, and why it is not the two independent tasks first sketched here:

- **`fake@1`, no bindings, no `.fake-agent.json`, no repository.** `fake@1` is
  absent from `EXECUTOR_BINDING_SPECS` (`binding-resolver.ts:17`), so it needs no
  repository / `ai_provider` / `credential` context and the import takes no
  `--bind` flag; `FakeRunner` returns `completed` and produces no landing
  candidate. `generic@1` requires all three and would fail the run with
  `CredentialError: task has no ai_provider context`. `.fake-agent.json` /
  `KANTHORD_FAKE_AGENT` is the seam for the **pi** loop (`main.ts:35-43`), which
  `fake@1` never enters.
- **Three tasks, not two.** `run daemon --until-idle` drains the queue, so two
  independent tasks both reach `completed` and nothing is left `pending` for cases
  3 and 5. `ran-task` completes; `blocker-task` is failed through the existing
  `--fail <id>` flag (`commands/run/daemon.ts:12-23`); `idle-task` depends on
  `blocker-task` and therefore stays `pending` — only a `completed` dependency
  satisfies an edge, and a failed task does not cascade (discard is an explicit
  command, 007.16).

## Stories

1. **Content-only hash + explicit CAS status predicate** — one story, not two.
   Removing `status` from the hash deletes the implicit race guard, and the
   explicit predicate replaces it; shipping them apart leaves a tree where
   `npm run verify` is green while no lifecycle guard exists at all and an
   `--apply` overwrites a running task's instructions.
   - Drop `status` from `canonicalTask`'s parameter object and hashed JSON
     (`src/domain/sha.ts:16` and `:26`) and from its **six** call sites:
     `create-graph.ts:230`, `apply-graph.ts:210` / `:244` / `:462` / `:573`, and
     `sqlite-task-repository.ts:48` inside `#computeTaskSha` (`:29-51`), whose
     `#stampSha` (`:57-85`) then drops `status` from both its SELECT (`:60`) and
     its call (`:80`). Note `apply-graph.ts:147` and `:171` are
     `canonicalInitiative` / `canonicalObjective` — out of scope.
   - Change `compareAndApply(id, expectedSha, spec)` →
     `(id, expectedSha, expectedStatus, spec)` and
     `conditionalDeleteTask(id, expectedSha)` →
     `(id, expectedSha, expectedStatus)` in `src/storage/port.ts:122` / `:141` and
     `sqlite-task-repository.ts:331` / `:410`. Return a discriminated conflict
     reason (`"sha"` | `"status"`) plus the row's actual status, on a new
     `TaskCasResult` — `CasResult` stays as-is, since it is shared with the four
     `InitiativeRepository` CAS ops and with `conditionalReparent`.
   - `compareAndApply` guards with one atomic
     `UPDATE … WHERE id = ? AND sha256 = ? AND status = ?`, treating no affected
     rows as a conflict (compare `changes > 0`, never `=== 0` — node:sqlite types
     it `number | bigint`). `conditionalDeleteTask` **cannot** use the `DELETE …
WHERE` equivalent: only `graph_import_map.task_id` cascades
     (`migrations.ts:157`), so the five non-cascading child tables must be cleared
     first (`sqlite-task-repository.ts:419-426`) and the predicate has to be
     checked before any statement runs. It reads `sha256, status` once — serving as
     both guard and diagnostic — which is safe because `node:sqlite` is synchronous
     and the caller holds `BEGIN IMMEDIATE` (`apply-graph.ts:438`).
   - Pass the **preflight-observed** status from `apply-graph.ts:481`
     (`compareAndApply`) and `:602` (`conditionalDeleteTask`) — not `:471`, which is
     `conditionalReparent`. It must ride on `ApplyClassification` (`:38-46`, which
     has no status field today): the write phase's own re-read at `:444` happens
     inside the transaction where the value can never have changed, so re-reading
     makes the guard a provable no-op.
2. **Migration 21 — re-stamp both DB sha stores, preserving real drift** —
   recompute `tasks.sha256` for every row under the new `canonicalTask`, **and**
   rewrite `graph_import_map.creation_sha` so a task whose content is untouched
   satisfies `liveSha === baselineSha` immediately after migrating. Objective and
   initiative shas are unaffected (their canonical forms never included status).
   Version **21**, not 20: this text originally said 20 because the highest
   registered version was then 19, but EPIC 007.17 has since registered **20**, and
   `validateSequence` (`migrate.ts:56-62`) throws unless versions are contiguous
   `1..n` — so 20 would now collide and 22 would break every DB open. The frozen
   canonical helpers ship as `canonicalTaskV20` (old, status-bearing) and
   `canonicalTaskV21` (new, content-only).
   `creation_sha` must **not** be rewritten unconditionally — that would erase
   drift that was genuinely present before migrating, leaving a really-changed row
   classifying `unchanged`. The migration therefore freezes **two** canonical
   forms and rewrites a baseline only when the row's content has not drifted since
   it was minted, tested by recomputing the old status-bearing digest at status
   `"pending"` — the status every baseline carries (`create-graph.ts:230` passes a
   fresh `newTask`'s status; `apply-graph.ts:573` hardcodes it).
   The baseline-source question is **answered: the on-disk manifest is
   authoritative** for every node carrying an `id` (`apply-graph.ts:143/166/195`
   read `manifest?.nodes[id]`); `graph_import_map.creation_sha` is the baseline
   only on the id-less branch (`:221-252`). So Story 3 is required, not optional.
3. **Reject stale manifests** — on-disk `.kanthord-export.json` files hold
   pre-change baselines and cannot be migrated, so a pre-007.18 manifest must fail
   with a single-line, actionable error naming `export initiative` as the remedy
   rather than reporting every node as `drifted`. Bump `GRAPH_FORMAT_VERSION`
   (`format.ts:10`) 2 → 3 and make both producers emit it — `export-initiative.ts:42`
   hardcodes `1`, and `import-graph.ts:470-471` writes `2` only when the initiative
   declares bindings. The gate belongs in **`ApplyGraph`**, not the CLI: a stale
   manifest is invalid _data_, and the use case is the only place that protects
   every caller. Throw a new `StaleManifestError` right after
   `apply-graph.ts:137` (`const manifest = pkg.manifest;`), before the first
   classification, gating on `manifest.formatVersion` — **never**
   `pkg.formatVersion`, which defaults to `1` for a manifest-less package
   (`graph-codec.ts:287`) and would reject every `--create` round-trip.
   This needs an **error boundary that does not exist**: `main.ts:48` is a bare
   `await program.parseAsync(...)`, and neither `runImportGraph` nor
   `commands/import/graph.ts:55-92` catches — so `ApplyGraph`'s existing throws
   escape as unhandled rejections today, and `error-map.ts` imports
   `UnknownNodeError` / `CrossInitiativeError` / `DriftConflictError` for a mapping
   this path can never reach. Wrap the `applyGraph.execute` call in `runApply` with
   `{ ...toResult(err), stdout: [] }` (the `apps/cli/get.ts:29` idiom) and register
   the new class in `error-map.ts`. 27 test fixtures pinning `formatVersion: 1`
   move to `3`.
4. **Distinguishable conflict reporting** — `apply-graph.ts` and the CLI must
   surface _which_ predicate failed: `refused: task <id> is no longer pending
(status: running)` for a status conflict vs `refused: task <id> changed outside
this package` for a sha conflict. Carry it on a **typed** field —
   `casReason?: { kind: "sha" } | { kind: "status"; currentStatus: string }` added to
   `ApplyClassification` (`:38-46`) — not encoded into the existing
   `reason?: string`, which already carries unrelated preflight diagnostics for
   missing nodes (`"non-pending"` / `"drifted"`, set at `:301-303`, printed at
   `:193-194`). Formatting lives at `import-graph.ts:294-299`, whose existing
   aggregate wording (`refused: 1 drifted node(s)`) stays for preflight conflicts.
   Depends on Story 1's discriminated reason.
5. **The two Proof scripts** — the Verification Gate must be a committed bash
   script, not inline bash (AGENTS.md), so this story ships both halves:
   - **`scripts/e2e/make-sha-graph.sh <dir> [--add-new-task]`** — the package.
     Objective `sha-obj` with three tasks on `agent: fake@1` and **no** initiative
     `bindings:` and **no** task `context:`: `ran-task` (no deps, completes),
     `blocker-task` (no deps, failed by the daemon's `--fail <id>`), and
     `idle-task` (`dependencies: [blocker-task]`, so it stays `pending`). No
     `.fake-agent.json` — that file is the pi-loop seam (`main.ts:35-43`) and
     `fake@1` never enters it. With `--add-new-task` it writes only `task-new.md`
     (`ref: new-task`, title `Added after work already ran`) into an existing
     output dir, leaving the other files and the live manifest untouched, so the
     proof can prove a fresh insert lands on an initiative that has already run
     work.
   - **`scripts/e2e/sha-classification-proof.sh`** — the Verification Gate itself:
     takes no arguments, owns `.data/proof-00718`, runs the five cases listed in
     the gate above, and prints `007.18 PROOF OK`.

   Two tasks are not enough and `generic@1` cannot be used — see the gate's "Task
   shape" note for the code that forces both.

## Non-goals

- Adding fields _to_ the content hash. The digest must still cover every
  declarative field (title, instructions, ac, agent, verification, dependencies,
  objectiveId) — verify that inventory is complete, but do not extend it. Trading
  today's false positive for a false negative (a real concurrent edit reading as
  `unchanged`) is the worse direction.
- Backward compatibility for existing `.kanthord-export.json` files or existing
  DBs beyond migration 21. Local development only; a clear error plus re-export is
  the supported path (Story 3).
- The `import graph --apply` false-success reporting and ref resolution — EPIC
  007.16 Story 3 (criteria D and E) already owns those.
- Sequencing edges and follow-up nodes — EPIC 007.17.
- Creation-time validation of an agent's required context types. (`F3` in the
  findings file is **retracted** — `create task --context` already works; only the
  fail-fast check is missing, and `AgentCatalog` would need to declare
  requirements first.)
- Any change to when `save()` is called or to task lifecycle transitions.
