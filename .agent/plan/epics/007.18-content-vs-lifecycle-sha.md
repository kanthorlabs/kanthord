# EPIC 007.18 — Separate content drift from lifecycle progress

## Goal

`canonicalTask` (`src/domain/sha.ts:8-28`) hashes `status` alongside the task's
declarative content. Because `save()` re-stamps the sha on every write
(`sqlite-task-repository.ts:87-88`), a task that merely _ran_ gets a different
`sha256` than the baseline recorded at import time. `classifyNode`
(`apply-graph.ts:83-85`) checks `liveSha !== baselineSha` **first**, so that task
classifies `drifted`, `drifted` is a blocking conflict (`:390`), and the whole
`import graph --apply` writes nothing.

Proven numerically on the real E2E DB (task `01KYB1A2T6540GHHWRWT750AA2`, all
other canonical fields byte-identical):

```
live DB status              : completed
tasks.sha256 (live)         : 4258b7c53b9c7cef…
manifest baseline           : 43e854c0928f8f3b…
recompute with status=pending  : 43e854c0928f8f3b…   ← equals the baseline
recompute with status=completed: 4258b7c53b9c7cef…   ← equals the live sha
```

Corroboration: `canonicalObjective` / `canonicalInitiative` (`sha.ts:31-44`) do
**not** hash status, and in that same run the initiative and objective classified
`unchanged` while all five tasks classified `drifted`.

Consequence: **once a task has run, no `--apply` can ever succeed on its
initiative again.** Conflicted nodes keep their old baseline (`:657`), so the drift
never heals. This is the root blocker for inserting work into a live plan
(`.agent/plan/epics/007.17-midway-insertion-findings.md`, `F1`).

After this epic:

- `canonicalTask` hashes **declarative content only** — status is removed.
- A completed task whose file nobody touched classifies **`unchanged`** and is not
  written, so it stops blocking the addition of a _different_ task.
- The lifecycle protection that status-in-sha was providing is **kept, and made
  explicit**: the CAS gains its own `status` predicate.

### Why status was in the hash (design intent, preserved)

Status was embedded deliberately, as a race guard. `compareAndApply`
(`sqlite-task-repository.ts:331-350`) compares **only** the sha, so a status change
was the thing that invalidated a stale CAS:

```
t0  apply preflight: task X is `pending`, content changed → classify `updated`
t1  daemon (separate process) claims X → status=`running` → save() re-stamps sha256
t2  apply CAS: expectedSha ≠ current sha → conflict → rollback        ✅ caught
```

Removing status from the hash without replacing this guard would let step `t2`
succeed and **overwrite the instructions of a running task**. This epic therefore
replaces the implicit signal with an explicit predicate; it does not drop it.

### Decision record

- **The status predicate becomes explicit, not implicit.**
  `compareAndApply(id, expectedSha, expectedStatus, spec)` and
  `conditionalDeleteTask(id, expectedSha, expectedStatus)` guard with a single
  atomic statement:
  `UPDATE … WHERE id = ? AND sha256 = ? AND status = ?`, treating `changes === 0`
  as a conflict. Two predicates, two distinct meanings, both atomic.
- **This is strictly better than status-in-sha**, for three reasons: the two
  failure modes become distinguishable in the error message ("content changed
  underneath" vs "task is no longer pending"); the `locked` check at
  `apply-graph.ts:87-88` stops being **shadowed** by the `drifted` check above it
  (today it is unreachable for any progressed task); and an untouched progressed
  task stops being a conflict.
- **The race only exists for nodes that are written.** `unchanged` writes nothing,
  so it needs no CAS and has no race — which is why removing status from the hash
  costs nothing for the insertion use case:

  | Live state              | Package intends | Class       | Writes? | Race possible?           |
  | ----------------------- | --------------- | ----------- | ------- | ------------------------ |
  | ran, file untouched     | no change       | `unchanged` | no      | no                       |
  | pending, file edited    | change          | `updated`   | **yes** | yes → explicit predicate |
  | ran, file edited        | change          | `locked`    | no      | no                       |
  | changed behind our back | any             | `drifted`   | no      | no                       |

- **Three sha stores must move in lockstep.** `tasks.sha256` (live),
  `graph_import_map.creation_sha` (DB baseline — verified to hold `43e854…`, the
  same value as the manifest), and the on-disk `.kanthord-export.json` manifests.
  The first two are migrated; manifests are outside the DB and must be re-exported.
  Missing any one of these reintroduces universal drift — the exact bug being fixed.
- **The race itself is proven by a hermetic unit test, not by the Proof block.** A
  true interleaving cannot be made deterministic from a shell script, and a
  timing-dependent Proof gate would be flaky. The Proof proves the observable
  classification contract (the wiring); a fake repository that flips status between
  classification and write proves the guard (the unit). This is a deliberate split,
  per AGENTS.md: tests prove the units, the Proof proves the wiring.

## Verification Gate

Gates: `npm run verify` (typecheck + test + verify:handoff + lint + db status)

Proof: hermetic, no-model. Builds a two-task graph, runs one task to `completed`,
then exercises all four classifications against the real program.

```sh
set -euo pipefail
export KANTHORD_DB="$PWD/.data/proof-00718/kanthord.db"
rm -rf "$(dirname "$KANTHORD_DB")"; mkdir -p "$(dirname "$KANTHORD_DB")"
node src/main.ts db migrate
PROJECT=$(node src/main.ts create project --name proof-00718 | head -1)
git init --bare "$PWD/.data/proof-00718/origin.git" >/dev/null
REPO=$(node src/main.ts create repository --project $PROJECT --name r \
  --remote-url "$PWD/.data/proof-00718/origin.git" --branch main \
  --path "$PWD/.data/proof-00718/home" | head -1)

# NEW in this epic: two independent tasks (ref: ran-task, ref: idle-task) + .fake-agent.json
scripts/e2e/make-sha-graph.sh .data/proof-00718/graph
G=.data/proof-00718/graph
node src/main.ts import graph $G --create --project $PROJECT --bind source=$REPO
INIT=$(node -e 'console.log(require("./.data/proof-00718/graph/.kanthord-export.json").initiativeId)')
RAN=$(node -e 'const j=require("./.data/proof-00718/graph/.kanthord-export.json");console.log(j.refToId.tasks["ran-task"])')
IDLE=$(node -e 'const j=require("./.data/proof-00718/graph/.kanthord-export.json");console.log(j.refToId.tasks["idle-task"])')

# drive ran-task to completed; idle-task stays pending (no deps between them)
node src/main.ts run daemon --until-idle --poll-interval 200 || true
test "$(node src/main.ts get task --id $RAN | sed -n 's/^status: //p')" = "completed"

# ---- 1) THE FIX: a completed task with an untouched file is `unchanged`, not `drifted`
node src/main.ts import graph $G --apply --initiative $INIT --dry-run \
  --bind source=$REPO > /tmp/p1.txt 2>&1
grep -q "unchanged: $RAN" /tmp/p1.txt
grep -vq "drifted: $RAN" /tmp/p1.txt

# ---- 2) a NEW task can now be added to an initiative that has already run work
#     The extra task file is emitted by the script, NOT by an inline heredoc: a
#     heredoc containing a fenced `Verification` block cannot survive inside a
#     markdown code fence (prettier promotes the outer fence and the inner close
#     terminates the block early).
scripts/e2e/make-sha-graph.sh $G --add-new-task    # writes task-new.md (ref: new-task)
node src/main.ts import graph $G --apply --initiative $INIT --bind source=$REPO

# There is no `find task` subcommand (find covers project / initiative /
# objective / resource only), so resolve the new id from `list task --json`:
NEW=$(node src/main.ts list task --initiative $INIT --json | node -e '
  const r = JSON.parse(require("node:fs").readFileSync(0, "utf8"));
  const t = r.find((x) => x.title === "Added after work already ran");
  if (!t) { console.error("insert did not land"); process.exit(1); }
  console.log(t.id);
')
test -n "$NEW"                                     # the insert actually landed
test "$(node src/main.ts get task --id $NEW | sed -n 's/^status: //p')" = "pending"

# ---- 3) editing a PENDING task's file still applies (`updated`)

sed -i '' 's/^title: .*/title: Idle task retitled/' $G/task-idle.md
node src/main.ts import graph $G --apply --initiative $INIT --bind source=$REPO
node src/main.ts get task --id $IDLE | grep -q '^title: Idle task retitled'

# ---- 4) editing a COMPLETED task's file is refused as `locked`, not silently applied

sed -i '' 's/^title: .*/title: Ran task retitled/' $G/task-ran.md
! node src/main.ts import graph $G --apply --initiative $INIT --bind source=$REPO >/dev/null 2>&1
node src/main.ts import graph $G --apply --initiative $INIT --bind source=$REPO 2>&1 \
  | grep -qE 'locked'
node src/main.ts get task --id $RAN | grep -vq 'Ran task retitled' # not written
cp /tmp/task-ran.bak $G/task-ran.md

# ---- 5) a real out-of-band content change is still caught as `drifted`

node src/main.ts add dependency --task $IDLE --dependency $RAN # mutates content behind the package
node src/main.ts import graph $G --apply --initiative $INIT --dry-run --bind source=$REPO 2>&1 \
  | grep -q "drifted: $IDLE"

echo "PROOF OK"

```

## Stories

1. **Remove `status` from the content hash** — drop the `status` field from
   `canonicalTask`'s parameter object and its hashed JSON (`src/domain/sha.ts:8-28`),
   and from all four call sites that pass it (`create-graph.ts:222-231`,
   `apply-graph.ts:147/171/201/235/443/554`,
   `sqlite-task-repository.ts:29` `#computeTaskSha` and `:57` `#stampSha`). Pure
   mechanical removal; no behavior added here.
2. **Explicit status predicate on both CAS paths** — change
   `compareAndApply(id, expectedSha, spec)` → `(id, expectedSha, expectedStatus, spec)`
   and `conditionalDeleteTask(id, expectedSha)` →
   `(id, expectedSha, expectedStatus)` in `src/storage/port.ts:122` and
   `sqlite-task-repository.ts:331` / `:343`. Replace the read-then-compare with one
   atomic `UPDATE … WHERE id = ? AND sha256 = ? AND status = ?` (and the
   `DELETE … WHERE` equivalent), treating `changes === 0` as `conflict`. Return a
   discriminated conflict reason (`"sha"` | `"status"`) so the caller can say which
   predicate failed. Pass the preflight-observed status from `apply-graph.ts:471`
   and `:592`.
3. **Migration 21 — re-stamp both DB sha stores in lockstep** — recompute
   `tasks.sha256` for every row under the new `canonicalTask`, **and** rewrite
   `graph_import_map.creation_sha` for every task row to the same new value, so a
   task whose content is untouched satisfies `liveSha === baselineSha` immediately
   after migrating. Objective and initiative shas are unaffected (their canonical
   forms never included status). Confirm which source `classifyNode` reads as
   `baselineSha` — the DB `creation_sha` or the on-disk manifest — and if the
   manifest is authoritative, Story 4 must cover it.
4. **Re-export stale manifests** — on-disk `.kanthord-export.json` files hold
   pre-change baselines and cannot be migrated. Make `import graph --apply` detect a
   manifest whose `formatVersion`/digest predates this change and fail with a
   single-line, actionable error naming `export initiative` as the remedy, rather
   than reporting every node as `drifted`.
5. **Distinguishable conflict reporting** — `apply-graph.ts` and the CLI must
   surface _which_ predicate failed: `refused: task <id> is no longer pending
(status: running)` for a status conflict vs `refused: task <id> changed outside
this package` for a sha conflict. Depends on Story 2's discriminated reason.
6. **`scripts/e2e/make-sha-graph.sh <dir> [--add-new-task]`** — emits the Proof's
   package: objective `sha-obj` with two independent tasks (`ran-task`,
   `idle-task`, no dependency between them so one can complete while the other
   stays `pending`) and a `.fake-agent.json` for the no-model daemon. With
   `--add-new-task` it additionally writes `task-new.md`
   (`ref: new-task`, title `Added after work already ran`, `context: source`) into
   an existing output dir **without** rewriting the other files — the Proof calls
   it a second time to prove a fresh insert lands on an initiative that has
   already run work. The flag exists because a heredoc containing a fenced
   `Verification` block cannot live inside the Proof's own markdown code fence.

## Non-goals

- Adding fields _to_ the content hash. The digest must still cover every
  declarative field (title, instructions, ac, agent, verification, dependencies,
  objectiveId) — verify that inventory is complete, but do not extend it. Trading
  today's false positive for a false negative (a real concurrent edit reading as
  `unchanged`) is the worse direction.
- Backward compatibility for existing `.kanthord-export.json` files or existing
  DBs beyond migration 21. Local development only; a clear error plus re-export is
  the supported path (Story 4).
- The `import graph --apply` false-success reporting and ref resolution — EPIC
  007.16 Story 3 (criteria D and E) already owns those.
- Sequencing edges and follow-up nodes — EPIC 007.17.
- `create task --context` (findings `F3`) — still unscheduled.
- Any change to when `save()` is called or to task lifecycle transitions.
