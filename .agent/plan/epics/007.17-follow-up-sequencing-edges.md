# EPIC 007.17 — Follow-up sequencing edges (initiative + objective)

## Goal

Today an engineer who realises initiative 2 missed something has no way to say
"do 2.1 next, before 3". Verified in
`.agent/findings/007.17-midway-insertion-findings.md`: there is no `order` /
`sequence` column on `initiatives` or `objectives`, task dependencies are
initiative-scoped (`add-dependency.ts:75` validates against
`listByInitiative`), and `EnqueueReadyTasks` works **every** non-paused
initiative concurrently (`enqueue-ready-tasks.ts:40-42`). Naming an initiative
"2.1" is decoration; `pause` is operator memory held outside the graph.

After this epic a follow-up node can be sequenced after an existing one, at both
the initiative and the objective level:

```sh
# create the follow-up already sequenced
create initiative --project P --name 2.1 --after $INIT2
# or sequence work that already exists (the real case: 3 and 4 are already planned)
add initiative-dependency --initiative $INIT3 --after $INIT21
```

An edge is satisfied only by the level's **successful terminal** status:

| Level      | Prereq must be                        | Never satisfied by                                           |
| ---------- | ------------------------------------- | ------------------------------------------------------------ |
| initiative | `landed`                              | `building`, `discarded`                                      |
| objective  | `integrated`                          | `building`, `awaiting_confirmation`, `conflict`, `discarded` |
| task       | `completed` (exists today, unchanged) | anything else                                                |

Task-level follow-up is **explicitly out of scope** — task dependencies already
exist and are unchanged by this epic.

### Decision record (human-confirmed)

- **Vocabulary is `after:` / `--after`, not `dependencies:`.** These edges are
  satisfied by `landed` / `integrated`, not `completed`. Reusing the task word for
  different satisfaction semantics invites exactly the class of bug 007.16 was
  written to prevent.
- **A `discarded` prerequisite blocks and reports; it does not cascade.** The
  dependent stays `building` and renders
  `waiting on: <id> (discarded — will never satisfy)`. The operator then chooses to
  discard the dependent or re-point the edge. Cascading whole initiatives on one
  discard is too coarse.
- **A retroactive edge is refused.** If the dependent has already started work, the
  command exits non-zero and names what already ran — an edge cannot make executed
  work happen later, and storing it would create a false ordering record. This
  mirrors the existing task-level rule: `add dependency` already refuses on a
  non-pending task via `assertDependenciesEditable`.
- **No new status.** "Blocked" is derived and rendered, never stored. EPIC 007.15
  had to delete `awaiting_pr` / `delivered` precisely because they were
  defined-but-undriven; this epic does not repeat that.
- **An edge is never deleted implicitly; the plan is sensitive.** An `after:`
  entry present in the DB but absent from the file does **not** get removed by
  `import graph --apply`. It is detected, named (`would remove edge: <owner> ->
<dep>`), and refused until `--confirm-delete` is given — the same two-phase gate
  the node path already uses for a node missing from the package
  (`import-graph.ts:216-230`). Absence from a file is never by itself a deletion
  instruction.
- **`after` belongs inside the content digest, and that is what makes the
  confirmation safe.** `canonicalInitiative` / `canonicalObjective` gain a sorted
  `after` field, so an edge written by `add objective-dependency` re-stamps the
  owner's sha. `--apply` then reads `liveSha !== baselineSha` → `drifted` → refuse.
  Without this, "the author deleted the edge from the file" and "someone added the
  edge to the DB after the export" are indistinguishable, and the confirmation
  would ask the human to approve reverting a change they never saw.
- **Reuse the existing cycle detector.** `validateGraph` (`graph.ts:41-60`) never
  reads `node.status`; it only checks duplicates, unknown deps and cycles. Extract
  a status-agnostic `validateDag` and delegate, rather than writing a second
  detector for each level.

## Verification Gate

Gates: `npm run verify` (typecheck + test + verify:handoff + lint + db status)

Proof:

```sh
scripts/e2e/sequencing-proof.sh
```

Must print `007.17 PROOF OK (sequencing)` and exit 0.

Hermetic and no-model: the script drives the real CLI through the
`KANTHORD_FAKE_AGENT` seam (`src/main.ts:35-45`) against real git in `mktemp`
dirs — this epic is about scheduling, not about what an LLM writes. It authors
its packages via `scripts/e2e/make-sequencing-graph.sh` (also committed with this
epic; `scripts/` is lane-forbidden to `/work`, so both scripts are maintainer
artifacts written alongside the epic, not story deliverables).

The eleven claims the script asserts, in order:

1. an edge can be added to initiatives that **already exist** — the real
   2.1-before-3 case: `add initiative-dependency --initiative $B --after $A`,
   then `get initiative --id $B` shows `after: $A`.
2. the dependent is visibly blocked with **no new status invented**: `$B` is
   still `building` and renders `waiting on: $A`.
3. a **cycle is refused** — asserted while nothing has started, so the
   already-started gate cannot mask it (`Cycle detected`).
4. the daemon does **not** enqueue `$B`'s task while `$A` is `building`: the task
   stays `pending` and **zero** `task.ready` events carry its id (while `$A`'s
   task got exactly one).
5. landing `$A` (via `approve objective`) makes `$B` runnable — its task reaches
   `completed` on the next daemon pass.
6. a **retroactive edge is refused** and names what already ran: the _same_
   command as claim 3, now that `$A` has a completed task, fails with both
   `has already started` and `ordering can no longer be guaranteed`, and names
   the offending task id. (One command, two distinct refusals, because the checks
   are ordered idempotence → already-started → cycle.)
7. objective-level `after:` is read from the **graph package**, not just the CLI.
8. reordering `after:` in the file is a **no-op, not drift** — `--apply
--dry-run` on the reordered variant reports `unchanged` and zero `drifted`.
9. a file that **drops** an edge never deletes it implicitly: the apply is
   refused, names the edge (`would remove edge: <o> -> <d>`), asks for
   `--confirm-delete`, and the edge **survives**.
10. with `--confirm-delete` the edge removal **is** applied and reported
    (`removed edge: <o> -> <d>`). This runs **before the daemon executes any
    task**, and the order is load-bearing: a task that has run differs from its
    create-time baseline and is therefore permanently `drifted` (finding `F1`,
    whose root cause is EPIC 007.18), and a drifted node refuses the whole apply
    — so after execution this claim can never pass. Because the removal consumes
    the edge claim 11 needs, the script re-adds it with
    `add objective-dependency` immediately afterwards, which is safe while
    `obj-2`'s task is still `pending`.
11. an objective's task stays `pending` until **all** its prerequisites are
    `integrated` — `obj-2` has two, and integrating only the first leaves the task
    `pending`; integrating both releases it. (`after` is a set: every member must
    be satisfied. A single-prerequisite package could not prove this, and could not
    make claim 8 meaningful either, since reversing a one-element list is a no-op.)

Both `--apply` variants (reordered, edge-dropped) are derived **after** the
`--create` import, by copying the package and rewriting `obj-2`'s `after:` line.
A variant authored up front has no `.kanthord-export.json` baseline and no ULIDs,
so it cannot be applied at all.

## Stories

1. **`validateDag` extraction + edge domain** (pure, no I/O) — extract the
   status-agnostic duplicate/unknown-dep/cycle checks out of `validateGraph`
   (`src/domain/graph.ts:41-60`) into
   `validateDag(nodes: Array<{id: string; dependencies: string[]}>)`, have
   `validateGraph` delegate with zero behavior change, and add the per-level
   satisfaction predicates (`initiative → landed`, `objective → integrated`,
   including the rule that `discarded` never satisfies).
2. **Persistence** — migration **20** adding two edge tables, each with exactly
   two columns and a composite primary key:

   ```sql
   CREATE TABLE initiative_dependencies (
     initiativeId TEXT NOT NULL REFERENCES initiatives(id),
     dependency   TEXT NOT NULL REFERENCES initiatives(id),
     PRIMARY KEY (initiativeId, dependency)
   );
   CREATE TABLE objective_dependencies (
     objectiveId TEXT NOT NULL REFERENCES objectives(id),
     dependency  TEXT NOT NULL REFERENCES objectives(id),
     PRIMARY KEY (objectiveId, dependency)
   );
   ```

   **No `position` column** — unlike `task_dependencies` (`migrations.ts:50`), which
   carries one to preserve the declared order of a single task's dependency list.
   An `after` set is a set: every member must be satisfied, so order within it can
   never affect execution. Reads return the set sorted by `dependency` id, and the
   parser (Story 5) canonicalises `after:` by sorting at parse time so the content
   digest is computed on the canonical form and `after: [b, a]` never reads as drift
   against `after: [a, b]`.

   **No column is added to `initiatives` or `objectives`** — in particular no
   `order` / `sequence` / `rank`. The edge is the only ordering mechanism; the
   findings file (`F5`) records why a rank column is the wrong model.

3. **Readiness gate at EVERY enqueue site** — `EnqueueReadyTasks.execute()`
   (`enqueue-ready-tasks.ts:40-53`) skips an initiative whose `after` set is not all
   `landed`, and skips a task whose objective's `after` set is not all `integrated`;
   **and** the same objective gate applies to all three inline re-scans, or a
   completing task will unblock work in a still-blocked objective:
   `run-next-task.ts:257-268` and `:333-344` (byte-identical, factored into one
   private method) and `approve-task.ts:359-371`.
   `approve-task.ts` is load-bearing, not extra scope: `approve objective` is the
   command the Proof itself drives, so leaving it ungated would make claim 4 false
   through a sibling path. `retry-task.ts:120-123`/`:137-140` and
   `recover-interrupted-tasks.ts:40-43` are **not** re-scans — they enqueue only
   their own named task — and are out of scope.
4. **CLI: create-with-edge, add-edge, and the refusals** — `--after <id>` on
   `create initiative` / `create objective`; new `add initiative-dependency
--initiative <id> --after <id>` and `add objective-dependency --objective <id>
--after <id>`; matching `remove` verbs; the retroactive refusal (dependent has any
   task past `pending`) with a typed error naming the offending task ids; scope
   validation (objective edges within one initiative, initiative edges within one
   project); cycle refusal via Story 1's `validateDag`.
   Graph package support is three stories, split because one story covering the codec,
   both import paths and the deletion gate was too large to execute in a single TDD
   cycle:

5a. **Codec** — parse `after: [ref]` in `initiative.md` and `objective.md`, add the
field to the parsed types, and serialize it back out.
**Canonicalisation is load-bearing, not cosmetic:** because Story 2 stores the edge
set with no `position` column, the parser must **sort the `after` list ascending**
before it reaches the digest or the DB, and the serializer must emit that same
sorted order. Without this, a file written `after: [b, a]` against a DB holding
`[a, b]` classifies as content drift, and per finding `F1` drift is a blocking
conflict — so a harmless reordering would silently refuse the whole apply. Sorting
makes it a true no-op.

5b. **`--create` path** — resolve refs to ids (package-local for objectives,
existing same-project ULIDs for initiatives), store the edge set, and rewrite
`after:` from slugs to sorted ULIDs during id handoff.
`import-graph.ts:421-434` does this resolution for tasks' `dependencies` but not
for objectives, so without it the file and the DB disagree and every later apply
reports drift on a package nobody edited. Export carries `after` back out so the
round trip is byte-stable.

5c. **`--apply` path** — classify against the package's resolved set, validate the
merged objective DAG, and write via a narrow `conditionalSet*After` CAS threaded
with the rename's fresh sha.
**Removal is gated, not implicit.** An edge in the DB but absent from the file is
detected, named (`would remove edge: <owner> -> <dep>`) and refused until
`--confirm-delete` is given — the same two-phase gate the node-deletion path uses.
A `drifted` owner is refused before the gate is even reached, so the human is never
asked to confirm reverting a change they did not make.

6. **Observability** — `get initiative` / `get objective` render `after:` and, when
   blocked, `waiting on: <id>`, appending `(discarded — will never satisfy)` when the
   prerequisite is `discarded`; `scripts/e2e/e2e-status.sh` shows the blocked reason.

   The two Proof scripts (`scripts/e2e/sequencing-proof.sh` and
   `scripts/e2e/make-sequencing-graph.sh`) are **not** part of this story:
   `scripts/*` is forbidden to both `/work` roles (`scripts/lane-check.sh:12`), so
   they are maintainer artifacts committed with this epic. `e2e-status.sh` is
   likewise a maintainer edit. Story 6's `/work` scope is the two use cases and
   the two renderers only.

## Non-goals

- **Task-level follow-up sequencing.** Task dependencies already exist; this epic
  does not touch `readiness()` (`graph.ts:156-177`) or `add dependency`.
- Cascading a discard through sequencing edges (decision record).
- Any new initiative or objective status — blocked is derived, never stored.
- Cross-project initiative edges.
- Reopening a `landed` initiative or an `integrated` objective. The findings file
  (`F4`) establishes why: the branch has landed in the bare home, publication state
  may exist, and `commitOid`/`parentOid` anchors may no longer match. Follow-up
  nodes are the supported model.
- Fixing `import graph --apply`'s false-success and unresolved-ref defects (`F1`,
  `F2` in the findings) — those fold into EPIC 007.16 Story 3, which already owns
  unhandled errors escaping as stack traces.
