## Goal

The operator opens a decision, reads the actual change the agent proposes, and
answers it — approve or reject — without leaving the browser. The evidence is a
real per-file diff served by the daemon, not a git command to retype. The
response is guarded twice: a verdict names the decision occurrence it answers
and the commit it reviewed, and the server refuses it when either has moved.

## Verified facts (measured on this tree, 2026-07-31 — do not re-litigate)

- `evidence.diffAvailable` is the **literal `false`** in the domain
  (`src/domain/decision-queue.ts:75,119`), and `evidence.inspect` is a
  `git -C <homeDir> diff <base>..<head>` argv (`:100-108`) — a terminal command,
  not data a browser can render.
- **No HTTP route exposes any verdict.** `src/apps/http/routes.ts` has no
  approve, reject, retry or abandon path. Verdicts are CLI-only today.
- `ApproveTask.execute({ taskId })` (`src/app/task/approve-task.ts:120`) takes
  the id and nothing else — **there is no freshness guard on task approval**.
  `ApproveObjective` requires `expectedCommit` and calls `assertCandidateFresh`
  (`src/domain/initiative.ts:143`) **twice**: before any git work
  (`approve-objective.ts:66`) and again inside the write transaction (`:129`),
  because SQLite cannot roll back a moved ref.
- **The per-task approve gate is no longer the ordinary delivery path.** The
  human gate moved to `approve objective` (`scripts/e2e/landing-proof.sh:63-64`);
  an initiative-clone task completes with no per-task confirmation
  (`src/apps/cli/agent-smoke.test.ts:335,596`). The decision an operator meets on
  most landings is therefore the **objective** candidate.
- A task reaches `awaiting_confirmation` by two distinct paths: **escalation**
  (`run-next-task.ts:452-481`) and **candidate** (`:482-530`). The queue names
  which in `cause: "candidate" | "escalation"`.
- An **escalated** task carries no persisted `ChangeCandidate` —
  `approve-task.ts:157-167` uses exactly that absence to tell the two apart, and
  the comment there records a past regression from conflating them. Its
  `proposalCommit` is also **optional**: `run-next-task.ts:465` sets the payload
  field only when defined and `:473` persists `proposalCommit ?? null`. So an
  approvable task may legitimately have **no commit at all**. **[debate]**
- The candidate commit is **not in the bare home** until something fetches it:
  `GitRepositoryLanding.preview` fetches `candidateSHA` from
  `candidate.workspace` into `homeDir` (`src/landing/git.ts:106-112`), and
  `GetConflict` passes `workspace: ""` precisely because approve already did.
  The daemon lands into that same home under a lock (`git.ts:44-71`).
- The workspace clone holds **both** OIDs already: `run-next-task.ts:507-516`
  persists `workspace`, `baseCommit` and the proposal commit together, and the
  clone was made from the home at `baseCommit`. **[debate]**
- `TaskDetailView.landingCandidate {state, baseSHA, candidateSHA, target}`
  (`views/task.ts:56-61`) already exposes a candidate's two OIDs.
- The queue sets `expectedCommit` from `o.commitOid` for **objectives only**
  (`decision-queue.ts:201,217`); task items get `expectedCommit: null` (`:169`).
- `TaskConflictView.files[] {path, hunks}` (`views/conflict.ts:4-15`) is the
  precedent per-file shape — but its `hunks` are **conflict-marker blob bodies**
  read from a merge result tree, not a unified diff. A candidate diff needs its
  own shape.
- `ApproveTask` returns **four** outcomes — `approved`, `conflict`,
  `target_moved`, `landing_failed` (`approve-task.ts:29-38`). Three of them are
  not request failures, and `ApproveObjective`'s own comment says the outcome is
  returned "so callers (the CLI) can report a conflict instead of announcing an
  integration that did not occur" (`approve-objective.ts:41-43`).
- `RejectTask` carries `dryRun`, `expectImpact` and `ImpactChangedError`, with a
  digest re-check **inside** the transaction (`reject-task.ts:190-205`). The
  digest is a **graph** guard: it is `discard`-only, `retry` has none, and two
  different attempts of the same task can produce the identical digest.
  **[debate]**
- The HTTP `If-Match` seam is **PATCH-only** (`src/apps/http/app.ts:234-258`,
  answering `428` then `412`). No POST route uses it.
- `GetConflict` answers **`409`** when the conflict has gone
  (`scripts/e2e/http-reads-proof.sh:254` pins `409 no_conflict_candidate`).
- `Target 023` (`.agent/plan/stories/019-http-server/retirement.md:87-96`)
  inventories `approve task`, `approve objective`, `reject task`,
  `reject objective` together and already prescribes
  `POST /api/task/:id/approval` and `…/rejection`. It is an **inventory, not an
  epic allocation** — it does not by itself put objective verdicts in 026.9.
  **[debate]**

## Decisions (binding)

1. **The diff is computed in the persisted workspace clone. The bare home is
   never opened.** The draft's permission to fetch objects into the home is
   withdrawn: a `GET` that writes loose objects and `FETCH_HEAD` into a
   directory the daemon lands into under a lock is a mutation, would grow the
   object store on every page load for candidates that are later rejected, and
   makes "leaves refs untouched" true only by a technicality. Every source pair
   already lives in a clone. **[debate]**

   | Subject            | Working directory       | Pair                         |
   | ------------------ | ----------------------- | ---------------------------- |
   | task, `candidate`  | `ChangeCandidate` clone | `baseSHA..candidateSHA`      |
   | task, `escalation` | task result `workspace` | `baseCommit..proposalCommit` |
   | objective          | `initiative.workspace`  | `parentOid..commitOid`       |

2. **The read model is one shape over a named source, never "the diff of a
   task".** `GET /api/task/:id/candidate` and `GET /api/objective/:id/candidate`
   return `{subject, source, base, head, available, unavailableReason, files[],
truncated, totalFiles, inspect}`. `source` names which row of decision 1 was
   read, so a candidate and an escalation are never silently interchanged.
3. **Unavailable is a state of the evidence, not a failed request.** `409
no_candidate` is reserved for a subject that has **no source pair at all** —
   the `409 no_conflict_candidate` precedent, "you addressed a thing that is not
   in that state". A subject that has a pair the server cannot read answers
   `200` with `available: false` and `unavailableReason` ∈ `workspace-missing`,
   `objects-unreachable`, `no-commit`. The two are different questions and get
   different answers; this split is deliberate. **[debate]**
4. **The diff is bounded at the server, with stated numbers.** `patch` is
   omitted for a file over **256 KiB** (`omitted: "too-large"`); the DTO carries
   at most **300** files and then sets `truncated: true` with the real
   `totalFiles`; the whole response body is capped at **8 MiB**, and reaching it
   sets `truncated: true` as well. `additions` and `deletions` come from
   `--numstat` and are present **even when the patch is omitted**. A binary file
   carries `binary: true` and no patch. Leaving these as adjectives would be a
   design decision deferred to build time. **[debate]**
5. **`diffAvailable` becomes structural, and the domain does no I/O.**
   `DecisionEvidence.diffAvailable` becomes a real `boolean` meaning **"a source
   pair is named for this subject"** — computed from data the app layer already
   passes into `QueueEvidenceInput`, with no filesystem access inside
   `src/domain/decision-queue.ts`. Whether the patch actually renders is
   answered only by the route of decision 2. Probing the filesystem per item
   would put git I/O in a pure projection and cost up to 500 probes per queue
   call. The DTO names the two meanings apart so the UI cannot confuse them.
   **[debate]**
6. **Verdicts are POST sub-resources, not PATCH**: `POST /api/task/:id/approval`,
   `POST /api/task/:id/rejection`, `POST /api/objective/:id/approval`,
   `POST /api/objective/:id/rejection` — the shapes Target 023 already
   prescribes. `If-Match` is rejected as the guard: it validates a
   **representation**, and what must be guarded is the identity of the attempt
   and its proposal commit, which no DTO fully determines.
7. **Every HTTP verdict carries the decision occurrence id, and the server
   refuses it unless that occurrence is still `open`** → `409 decision_closed`.
   This is the guard `expectImpact` cannot be: a stale tab addressing task `T`
   after a retry-and-refail would otherwise reject the **newer** attempt, and
   026.8 decision 1 already closes the old occurrence and opens a new one when
   the subject re-enters the state under a new opening event. The digest cannot
   catch it — the graph is unchanged, so the digest is identical. The occurrence
   id is required on all four routes, approvals and rejections alike. The CLI is
   unchanged: it has no occurrence and its operator is at the terminal.
   **[debate]**
8. **`expectedCommit` is REQUIRED on every approval, tasks included — and it is
   nullable, not optional.** `ApproveTask` gains it and applies the freshness
   check twice, before any git work and again inside the write transaction,
   matching `ApproveObjective` exactly. The expected value is
   `candidate.candidateSHA` for a candidate, `result.proposalCommit` for an
   escalation, and the explicit literal `null` for an escalation that has no
   commit (a real case — see the verified facts). The server verifies the claim
   both ways: a `null` sent for a subject that **does** have a commit is refused,
   exactly like a wrong OID. Making the field optional would silence the call
   sites this guard exists to enumerate. **[debate]**
9. **Rejection is guarded by occurrence and by impact, in that order.**
   `POST …/rejection` carries the occurrence id (decision 7), `resolution`,
   optional `reason`, and — for `discard` — the existing `expectImpact` digest.
   It does **not** carry `expectedCommit`: a rejection judges the attempt, and
   decision 7 already identifies the attempt. The draft's claim that
   `expectImpact` alone was enough is withdrawn. **[debate]**

   **The rejection route accepts a `failed` task, not only an
   `awaiting_confirmation` one.** `RejectTask` already admits `failed` for
   `discard` (`src/app/task/reject-task.ts:159-166`), a failed task is a real
   queue decision (`src/domain/actionability.ts:278-321`), and EPIC 026.10
   decision 15 wires its failed/escalated "stop permanently" control to this
   route. Scope is drawn by **route**, not by subject status: rejection is whole
   here, or 026.10 inherits half a route.

10. **Discard goes through the dry run.** The UI calls `dryRun: true`, renders
    the damage from the returned preview, and sends that `digest` as
    `expectImpact` on the real call. A discard control that skips the digest
    round trip is forbidden, in the API tests and in the UI tests.
11. **Approve's four outcomes get four honest representations.** `approved` →
    `200` with the canonical SHA. `conflict` → `200` with `outcome: "conflict"`
    and the conflict route for the same subject: a landing conflict is a **real
    reviewed result** with a recorded state change (`approve-task.ts:265-280`
    persists candidate state `conflict` and appends `task.conflict`), so a `4xx`
    would misreport it. `target_moved` → `409 target_moved`. `landing_failed` →
    `500 landing_failed`. Binding consequences: the response is a **discriminated
    command result** and the UI must render every non-approved success outcome —
    a client that treats `200` as "approved" is a defect the tests catch; and
    each `landing_failed` return point states its durable postcondition, with a
    **sanitised** body that never carries the adapter's `cause`. **[debate]**
12. **W3 Review is a child of the decision URL, not a rival to it.**
    `#/inbox/:decisionId` stays 026.8's decision detail; `#/inbox/:decisionId/review`
    is the W3 review screen, reachable as the detail's primary action and
    cold-loadable on its own. Evidence first, response last
    (`docs/ui-design.md:219,249-252`). Approve is inline; discard takes
    `AlertDialog` weight through `DangerConfirm`. On success the resolved state
    renders in place, "Next open item" primary — the UI never auto-navigates.
13. **An unavailable diff disables nothing.** When `available: false` the
    response controls still render, the screen states plainly what the operator
    is approving unseen, and the server's own `inspect` argv is offered as a
    `CommandHandoff`. Hard-blocking is rejected: an escalation with no proposal
    commit is a real, approvable decision today (`run-next-task.ts:465,473`), and
    blocking it would take a working CLI capability away from the browser.
14. **Objective review is in scope, with objective evidence, and this widens the
    roadmap row.** `docs/ui-design.md:109` scopes 026.9 to "task approve/reject".
    Measurement says the gate an operator actually meets is `approve objective`.
    Shipping objective **verdicts** without an objective **diff** would breach
    W3's evidence-first rule at capability level — the exact breach
    `docs/ui-design.md:120-123` forbids — so the objective source pair of
    decision 1 and the objective route of decision 2 are part of this epic, not
    a follow-up. Story S1 amends the roadmap row. Target 023 is an inventory and
    does not settle this by itself; the widening is a deliberate call.
    **[debate]**
15. **This epic owns the first registration of the verdict error codes, and no
    verdict route may answer `500` for a state.** `DOMAIN_ERROR_MAPPINGS`
    (`src/apps/http/error-registry.ts:42-91`) today has no entry for any of them,
    so `mapError` falls through to `internal` (`:170-192`). Registered here, all
    `409` unless stated: `stale_candidate` (`StaleCandidateError`,
    `src/domain/initiative.ts:105`), `decision_closed`, `no_candidate`,
    `target_moved`, `impact_changed` (`ImpactChangedError`), `illegal_transition`
    (`src/domain/task.ts:111`), `task_not_awaiting_confirmation`,
    `objective_not_awaiting_confirmation` (`src/app/errors.ts:38`); plus
    `landing_failed` → **`500`**, the one genuine server failure.
    **Cross-epic contact point**: EPIC 026.10 decision 10 lists
    `stale_candidate`, `illegal_transition` and
    `objective_not_awaiting_confirmation` as well, and reuses `decision_closed`
    from here. 026.9 runs first and adds them; 026.10 registers only what is
    still missing. A duplicate entry is a merge defect, not a tie.
16. **The CLI keeps parity.** `approve task` gains a **required**
    `--expect-commit`, matching `approve objective --expected-commit`, and
    accepts the literal `none` for the no-commit case of decision 8. This breaks
    the current CLI spelling; local development only, no back-compat (AGENTS.md).

## Verification Gate

Gates: `npm run verify`.

Hermetic coverage required beyond the Proof:

- **Domain/app**: `ApproveTask` refuses a stale `expectedCommit` before any git
  call and again inside the transaction, leaving no event and no transition;
  `null` is accepted only when the subject really has no commit and refused when
  it has one; the candidate and escalation sources are never confused; approve
  stays idempotent for an already-approved task.
- **Occurrence guard**: every verdict route refuses a closed or unknown
  occurrence with `409 decision_closed`, and the refusal happens **before** any
  git or domain work; a retry-and-refail scenario proves the digest alone would
  have let the stale verdict through.
- **Diff read model**: the source pair is chosen per decision 1; the bare home is
  never opened — asserted by a content hash of the whole home directory taken
  before and after, not by a ref listing; each of the three caps produces its
  documented marker at its stated number; a binary file is named, never patched;
  `additions`/`deletions` survive an omitted patch.
- **HTTP**: each of approve's four outcomes maps to its status and is
  distinguishable by code; `landing_failed` bodies carry no adapter `cause`; a
  discard without `expectImpact` after a changed graph is refused; the candidate
  route answers `409 no_candidate` for a subject with no source pair and `200
available:false` for each of the three unavailable reasons.
- **Queue**: `diffAvailable` is structural per decision 5, and a test asserts
  `src/domain/decision-queue.ts` performs no filesystem or git access.
- **UI**: the diff renders per file with its omission and truncation markers;
  approve sends the candidate DTO's own `head` as `expectedCommit` and the route
  param as the occurrence id; discard cannot be sent without a digest obtained
  from a dry run; a `409` renders `review-stale` with a refresh, never a generic
  error; a `200` whose outcome is `conflict` renders the conflict result, never
  a success; success renders in place and does not navigate.
- **Regression**: 026.7's and 026.8's Proofs still pass.

Proof: `scripts/e2e/ui-candidate-review-proof.sh` — deterministic, no model, no
outbound network, nothing left running.

```bash
scripts/e2e/ui-candidate-review-proof.sh
```

It must print `026.9 ok: …`. **Three independent subjects are provisioned in
phase B and never reused across a verdict**, because a verdict is terminal: one
subject for the HTTP approval (C, D, E), one for the discard path (F), one left
untouched for the browser (G). A single subject cannot satisfy both E and G.
**[debate]** Phases:

- **A** — build the UI; Chromium present, or exit with the install command.
- **B** — the fixture: `KANTHORD_FAKE_AGENT` + `make-landing-graph.sh` +
  `run daemon --until-idle`, run three times into **three projects, each with its
  own bare remote, its own managed mirror and its own imported graph** — so the
  subjects are independent by construction and one verdict cannot disturb
  another. Assert each objective's status from SQLite, and capture each subject
  id, before any UI assertion.
- **C** — `GET /api/objective/:id/candidate` returns real files with real
  patches; a content hash of the bare home directory is identical before and
  after the call.
- **D** — a verdict with a wrong `expectedCommit` is refused, and a verdict on a
  closed occurrence is refused with `409 decision_closed`; the subject is
  unchanged in SQLite afterwards.
- **E** — the correct verdict succeeds through HTTP on subject 1 and the
  objective really transitions in SQLite.
- **F** — on subject 2: a discard without a digest is refused; with the dry
  run's digest it succeeds.
- **G** — in the browser, on subject 3: the review screen renders the files,
  approve sends the DTO's `head` and the occurrence id, and the resolved state
  renders in place with no navigation.
- **H** — R3 holds: no request the page issued carried an `Authorization`
  header.

Ran against the CURRENT tree (2026-07-31): the script exits `1` in phase C with
`expected '200', got '404'` — `GET /api/objective/:id/candidate` does not exist
(`src/apps/http/routes.ts` has no candidate route and no verdict route). Phases A
and B pass: the build serves, and all three fixtures really reach
`awaiting_confirmation` with real commit pairs, so the failure is the missing
capability and not a broken fixture.

The Proof needs one harness field that did not exist: `scripts/e2e/ui-browser.mjs`
now records each request's `postData`, because a verdict proof must show **what**
the page sent — the occurrence id and the head OID — not merely that it posted.

## Non-goals

- **No reattempt, abandon, pause or resume** — 026.10 and 026.11.
- **No conflict resolution** — 026.7 shipped the read-only conflict screens and
  no route resolves a conflict; this epic only links to them.
- **No initiative publication** — a separate human-gated step (AGENTS.md).
- **No event feed** — 026.12.
- **No side-by-side or word-level diff rendering.** Unified patch text only; a
  richer viewer is a UI question to raise after the data exists.
