## Goal

When work stops, the operator responds in the browser instead of the terminal. A
failed task is reattempted with guidance. An escalated task — one where the agent
asked a human and left no candidate — is answered and reattempted, which no path
can do today. A stuck run is abandoned by lease and reason. An objective in
conflict is reattempted against the commit the operator actually looked at, and
the screen is told whether the conflict was really cleared. Every refusal comes
back as a named state, not a `500`.

## Verified facts (measured on this tree, 2026-07-31 — do not re-litigate)

- **`RetryTask` cannot reattempt an escalated task.** For an
  `awaiting_confirmation` task it requires a landing candidate in `conflict`, or
  `rebuild === true` with a `pending` candidate; otherwise
  `TaskNotRetryableError` (`src/app/task/retry-task.ts:90-96`). An escalation
  persists **no candidate**: `src/app/task/run-next-task.ts:452-481` never calls
  `saveCandidate`; only the candidate arm at `:530-539` does. So the escalation
  path has exactly one exit today — discard.
- `CandidateState` is a closed union of three values —
  `"pending" | "landed" | "conflict"` (`src/domain/landing.ts:4`). **[debate]**
- `awaiting_confirmation -> pending` is **already legal**
  (`src/domain/task.ts:97-109`), as are `failed -> pending` and
  `running -> pending`.
- **The guard is outside the transaction.** `RetryTask` reads the task at
  `src/app/task/retry-task.ts:85` and applies the `failed` guard at `:129-131`;
  the transaction opens at `:133`. The `awaiting_confirmation` guard (`:90-96`)
  sits outside its transaction (`:98`) the same way. `serve` and `run daemon` are
  **separate processes** over one SQLite file, so this is a real
  read-then-write window, not a theoretical one. **[debate]**
- **`AbandonTask` is about a running run, not about failed work.** It requires
  `status === "running"` (`src/app/task/abandon-task.ts:104-106`), exactly one
  running job (`:112-119`), a mandatory `reason` (`:94`), and returns
  `{outcome, taskId}` where outcome is `abandoning | already_abandoning`
  (`:52-54`) — **no task object**. It emits nothing itself.
- **Abandonment is asynchronous and is not idempotent across a requeue.** The
  effect lands at the next turn boundary; the CLI says so in its own words
  (`src/apps/cli/task.ts:491-495`). The drain requeues the task **before**
  appending `task.abandoned` (`src/app/task/run-next-task.ts:413-426`), so a task
  that was abandoned can be `running` again under a **new job id**. A second
  task-addressed abandon can therefore revoke a different run. **[debate]**
- `JobQueue` exposes the lease: `listRunningJobsForTask(taskId): RunningJob[]`
  (`src/queue/port.ts:70`), `revoke(...) -> "revoked" | "already_revoked" |
"not_found"` (`:78-81`). **`TaskDetailView` carries no job id**
  (`src/apps/http/views/task.ts:39-60`), so the browser cannot name a lease
  today. **[debate]**
- **`RetryObjective` returns `void` and its failure path is silent.** On gate
  pass it transitions to `awaiting_confirmation` and emits
  `objective.awaiting_confirmation` (`src/app/objective/retry-objective.ts:172-195`);
  on gate failure it records `conflictReason` and `note` and emits **nothing**
  (`:198-209`). A bare `200` would misreport a still-conflicted objective as
  recovered. **[debate]**
- `RetryObjective` requires `expectedCommit`
  (`src/app/objective/retry-objective.ts:81-85`) and calls `assertCandidateFresh`
  before any git work (`:118`) and again inside the transaction (`:175`).
- **A running task produces no queue action.** `decisionActions` has rules for
  `failed`, `awaiting_confirmation`, blocked `pending`, and two `completed`
  cases, then falls through with no action
  (`src/domain/actionability.ts:278-321`). `ActionKind` has **no `abandon`**
  (`:9-15`). (`:389` is `decisionKindLabel`, display only — the draft cited it
  wrongly. **[debate]**)
- **No recovery route exists.** `src/apps/http/routes.ts` has no `approval`,
  `rejection`, `reattempt`, `attempt`, `abandonment`, `pause` or `resume` row;
  `PATCH /api/initiative/:id` accepts `name` only (`:596-607`).
- **Every recovery error is a `500` today.** `DOMAIN_ERROR_MAPPINGS`
  (`src/apps/http/error-registry.ts:42-91`) has no entry for
  `TaskNotRetryableError` (`src/app/task/retry-task.ts:10`),
  `TaskNotAbandonableError` / `NoRunningJobError` / `AmbiguousRunningJobError`
  (`src/app/task/abandon-task.ts:16,28,38`), `ObjectiveNotRetryableError`
  (`src/app/objective/retry-objective.ts:16`),
  `ObjectiveNotAwaitingConfirmationError` (`src/app/errors.ts:38`),
  `StaleCandidateError` (`src/domain/initiative.ts:105`) or
  `IllegalTransitionError` (`src/domain/task.ts:111`), so `mapError` falls
  through to `TRANSPORT_ERRORS.internal` (`:170-192`).
- **`If-Match` is PATCH-only by construction.** `readRow` is "required iff
  `method === 'PATCH'`, forbidden otherwise" (`src/apps/http/routes.ts:117-122`);
  the dispatcher's pre-read/compare/write/re-read runs only for such rows
  (`src/apps/http/app.ts:234-261`). EPIC 026.9 decision 6 rejects `If-Match` as a
  verdict guard for the same reason.
- **026.9 is authored and owns the verdict routes.** It takes
  `POST /api/task/:id/approval`, `…/rejection`,
  `POST /api/objective/:id/approval`, `…/rejection` (026.9 decision 6), requires
  the **decision occurrence id on every verdict** with `409 decision_closed`
  when it is not open (026.9 decision 7), and requires the discard dry-run →
  `expectImpact` round trip (026.9 decision 10). Its non-goals hand reattempt and
  abandon to this epic. **[debate]**
- **No new event type is needed.** Reattempt emits `task.ready`
  (`src/app/task/retry-task.ts:123,138`), the drain emits `task.abandoned`
  (`src/app/task/run-next-task.ts:424`), objective recovery emits
  `objective.awaiting_confirmation` (`src/app/objective/retry-objective.ts:193-195`).
  All three are already admitted by the SQLite CHECK list
  (`src/storage/sqlite/migrations.ts:849-858`).
- **The fixtures are reachable with no model and no network.** An `escalate`
  turn is scriptable — the tool takes `{reason: string}`
  (`src/agent-runner/pi.ts:60`, handler `:554-568`) and yields
  `proposalCommit: undefined` when the workspace was not edited (`:718-742`). A
  running task is held by a background daemon plus bounded `sleep` turns, with
  the `poll()` helper (`scripts/e2e/abandon-run-proof.sh:21-24,39-70`). An
  objective in `conflict` comes from the CAS-mismatch recipe, which provisions a
  **second** objective and task itself
  (`scripts/e2e/decision-workbench-proof.sh:268-300`). **[debate]**
- **A task-level candidate conflict is not reachable from a proof.** With a
  repository-bound initiative and no workspace binding the task goes `completed`
  and the objective holds (`src/app/task/run-next-task.ts:482-500`, asserted at
  `scripts/e2e/landing-proof.sh:60-67`).

## Decisions (binding)

1. **Scope is drawn by route, never by subject status.** This epic adds exactly
   three rows: `POST /api/task/:id/reattempt`,
   `POST /api/task/:id/abandonment`, `POST /api/objective/:id/reattempt`.
   Approval and rejection are **026.9's, whole** — including rejection of a
   `failed` task. Splitting one route across two epics by status would leave
   026.9 shipping approve live and reject dead inside the W3 screen that
   introduces both, breaking `docs/ui-design.md`'s "evidence first, response
   last" within its own epic.
   **This widens the roadmap row.** `docs/ui-design.md:109` scopes 026.10 to
   "reattempt and abandonment for failed and escalated work". Objective conflict
   reattempt joins it: 026.7 shipped the objective conflict screen with a dead
   response region, 026.9 explicitly leaves conflict resolution alone, and
   `retry objective` is the only path in the program that clears an objective
   conflict. Left out, no epic owns it. Story S1 amends the row, following
   026.9's precedent.
2. **The noun is `reattempt`; `attempt` is rejected.** `retirement.md:92-94`
   offers both. `attempts` already names the runner's in-run retry counter
   (`src/app/task/run-next-task.ts:94,287,358`); one word for two concepts in one
   API is a defect, not a shortening.
3. **An escalated task becomes reattemptable — a domain change, and the whole
   candidate matrix is enumerated here.** `CandidateState` has three values, so
   the branch table is closed and no state is left to build time: **[debate]**

   | Task status                                 | Candidate  | `rebuild` | Behaviour                           |
   | ------------------------------------------- | ---------- | --------- | ----------------------------------- |
   | `failed`                                    | any / none | ignored   | reattempt (unchanged)               |
   | `awaiting_confirmation`                     | `conflict` | any       | reattempt (unchanged)               |
   | `awaiting_confirmation`                     | `pending`  | `true`    | reattempt (unchanged)               |
   | `awaiting_confirmation`                     | `pending`  | not set   | `TaskNotRetryableError`             |
   | `awaiting_confirmation`                     | `landed`   | any       | `TaskNotRetryableError`             |
   | `awaiting_confirmation`                     | **none**   | any       | **new: reattempt, `note` required** |
   | `pending`/`running`/`completed`/`discarded` | —          | —         | `TaskNotRetryableError`             |

   The new row does `retryTaskWithGuidance` → save → `enqueue` → `task.ready`,
   inside the existing transaction. A `landed` candidate stays refused: the task
   and its candidate disagree, and reattempting on top of a landed change is not
   a recovery.

4. **The required `note` lives in the use case, not in the route.** `RetryTask`
   gains `EscalationGuidanceRequiredError` for a missing or whitespace-only
   `note` on the new branch, so `retry task --note` becomes conditionally
   required for the CLI too (`src/apps/cli/commands/retry/task.ts:13` stays
   syntactically optional). An escalation is a question; reattempting it with no
   answer only escalates again. On every other branch `note` stays optional
   exactly as today. **[debate]**
5. **No new event type, and therefore no migration.** Consequence, and it is the
   point: `task.ready` is a verdict event in 026.8 decision 4, so a successful
   task reattempt **closes the decision occurrence as `resolved`** with that
   event as its closing event id. Objective recovery closes its occurrence only
   when the gate passes (decision 8).
6. **Each route names the thing it acts on. Three guards, one per shape.**
   `If-Match` is not available on a `POST` and is rejected for the same reason
   026.9 rejects it — it validates a representation, not an attempt. **[debate]**
   - **Task reattempt** carries the **decision occurrence id** and is refused
     with `409 decision_closed` unless that occurrence is open, exactly as
     026.9 decision 7. Without it, a task that failed, was reattempted and failed
     again is `failed` once more, and a stale tab reattempts the **newer**
     generation while believing it is acting on the old one. A status check
     cannot tell those generations apart.
   - **Objective reattempt** carries the occurrence id **and** a required
     `expectedCommit`. They are not redundant: the occurrence identifies the
     attempt, `assertCandidateFresh` is the git compare-and-swap.
   - **Abandonment** has no occurrence — a running task produces no queue item —
     so its token is the **lease**: a required `expectedJobId`, refused with
     `409 lease_moved` when it is not the task's current running job. This is
     what makes a late second press safe, because the drain requeues before
     emitting and a new run can already own the task.
7. **`runJobId` joins `TaskDetailView`.** The browser cannot name a lease it
   cannot read. `GET /api/task/:id` gains `runJobId: string | null`, from
   `listRunningJobsForTask` (`src/queue/port.ts:70`) — the single running job
   when the task is `running`, `null` otherwise. **Cross-worktree contact
   point**: this edits `src/apps/http/views/task.ts:39-60`, which a concurrent
   API epic may also touch; the story flags a collision to the human rather than
   resolving it (`CLAUDE.local.md`). It is the only field this epic
   adds to an existing read model.
8. **Every recovery response is a discriminated outcome, never a bare status.**
   - Task reattempt → `200 {outcome: "reattempted", task}`.
   - Objective reattempt → `200 {outcome: "recovered" | "still_conflicted",
objective, conflictReason?}`. `RetryObjective` succeeds silently when the gate
     fails, so a bare `200` would tell the operator the conflict is cleared when
     it is not. **[debate]**
   - Abandonment → **`202 Accepted`** `{outcome: "abandoning" |
"already_abandoning", jobId, task}`. `202` is the honest status: the lease is
     revoked now, the run stops at the next turn boundary. `200` would invite the
     screen to render the task as stopped while it is still running; `204` throws
     away the outcome the operator needs. **[debate]**
9. **Abandonment is idempotent per lease, and this epic says where that stops.**
   A repeat with the same `expectedJobId` answers `202 already_abandoning`. Once
   the run has drained, the same call answers `409 lease_moved`, and the UI
   renders "that run has already stopped" with a refresh — **not** a generic
   failure and **not** a claim that the task is idle, because the drain may have
   requeued it. Rendering any post-drain refusal as "already stopped, nothing
   running" is forbidden. **[debate]**
10. **Error mapping is half of this epic, not a tail chore.** Registered in
    `DOMAIN_ERROR_MAPPINGS` with stable machine codes, all `409` unless stated:
    `task_not_retryable`, `objective_not_retryable`,
    `objective_not_awaiting_confirmation`, `task_not_abandonable`,
    `no_running_job`, `ambiguous_running_job`, `stale_candidate`,
    `illegal_transition`, `lease_moved`; plus
    `escalation_guidance_required` → **`400`**. `decision_closed` is reused from
    026.9 unchanged. A `500` from any of the three routes is a bug, not a state;
    a screen can say nothing honest about one.
11. **The guard moves inside the transaction.** `RetryTask` re-reads the task and
    re-applies its branch table inside `this.#uow.transaction`, and the
    occurrence check of decision 6 happens there too. The current pre-transaction
    guard is not a compare-and-swap: two callers both read `failed`, both write
    `pending`, and the second answers `200` while `enqueue`'s dedupe quietly
    hides the double. The pre-transaction read stays as a cheap early refusal —
    it is an optimisation, and the epic says so rather than pretending it is the
    guard. **[debate]**
12. **Abandon takes `DangerConfirm`; reattempt does not.** The mandatory `reason`
    is the confirmation's content — blank or whitespace is `400 invalid_input`,
    never a defaulted string. Reattempt is recoverable and gets no ceremony
    (`docs/ui-design.md`: ceremony trains mechanical tapping).
13. **No optimistic update anywhere.** Every screen re-renders from the
    response body of decision 8. The Inbox stays manual-refresh (026.7
    decision 6), so a write may never mutate a list the server has not
    re-stated.
14. **The verdict inventory gains no `abandon` kind, and the abandon control is
    W2-only.** `ActionKind` stays as it is: a running task produces no queue
    action (`src/domain/actionability.ts:278-321`), so an abandon row in the
    Inbox would have nothing to attach to. The control lives on the task
    workspace, rendered **only** when `status === "running"` and `runJobId` is
    non-null. Manual refresh makes it transient, not unreachable — the task page
    has a refresh control by the binding freshness rules
    (`docs/ui-design.md:329-331`) — and the Proof renders it for real rather than
    proving it only by absence. **[debate]**
15. **Discard is wired, not built.** The failed/escalated "stop this
    permanently" control posts 026.9's `/rejection` with `resolution:
"discard"`, through 026.9 decision 10's dry-run → `expectImpact` round trip
    and 026.9 decision 7's occurrence id. This epic adds no rejection route and
    keeps **no** `OPEN:` escape hatch: 026.9 is authored and its contract is
    binding, so a missing field there is a predecessor regression that fails this
    epic's gate. **[debate]**

## Verification Gate

Gates: `npm run verify`.

Hermetic coverage required beyond the Proof:

- **Domain/app — the branch table of decision 3 in full**: one test per row,
  including `landed` staying refused and `pending` without `rebuild` staying
  refused; the escalated row transitions, enqueues and emits `task.ready`; a
  missing or whitespace `note` on that row raises
  `EscalationGuidanceRequiredError` and leaves **no** transition and **no**
  event.
- **Transactionality (decision 11)**: a test proves the status re-read happens
  inside the transaction — a task mutated to `pending` between the pre-read and
  the transaction is refused, not written twice.
- **Occurrence guard (decision 6)**: task and objective reattempt refuse a closed
  or unknown occurrence with `409 decision_closed`, **before** any git or domain
  work; a fail → reattempt → fail scenario proves a stale occurrence id is
  refused while the raw status check would have admitted it.
- **Lease guard (decisions 6, 9)**: abandonment with a stale `expectedJobId` is
  `409 lease_moved`; with the current one it is `202 abandoning`; a repeat with
  the same id is `202 already_abandoning`; after the drain the same id is
  `409 lease_moved`.
- **Objective outcome (decision 8)**: a gate-failing reattempt answers
  `still_conflicted` with the recorded `conflictReason` and asserts the objective
  did **not** transition and emitted **nothing**; a gate-passing one answers
  `recovered` and emits `objective.awaiting_confirmation`.
- **HTTP**: every error class in decision 10 maps to its code and status; **no
  recovery route can answer `500`**, proven by driving each error class through
  the dispatcher; blank `reason`, missing `expectedCommit`, missing occurrence id
  and missing `expectedJobId` are each `400`; the abandonment body carries
  `outcome` and `jobId`.
- **REST shape**: the three new paths pass the existing noun rule in
  `src/apps/http/routes.test.ts`.
- **Read model**: `runJobId` is the running job when the task is `running` and
  `null` in every other status.
- **UI**: reattempt posts once and re-renders from the response, never
  optimistically; a `409` renders `recovery-refused` with the server's code and
  leaves the screen usable; abandon renders only for `running` + non-null
  `runJobId`; a blank reason issues no request; `already_abandoning` renders as
  success while a post-drain `lease_moved` renders the decision 9 wording;
  `still_conflicted` renders as a non-success outcome.
- **Regression**: the Proofs of 026.7, 026.8 and 026.9 still pass.
