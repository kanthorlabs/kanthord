## Goal

The operator can stop and restart an initiative from the browser. Pause is the
gate that decides whether the daemon claims any work for an initiative at all,
and today it is reachable only from the terminal. After this epic the initiative
workspace carries a pause/resume control under the same conditional-edit rules
as rename, the project readiness page can act on its own `initiative/paused`
remediation instead of only printing the command, `paused` becomes safe to offer
at create time — the omission EPIC 026.4 decision 9 recorded on purpose — and a
pause becomes visible to the event feed, so a second tab's graph stops showing
paused work as runnable.

## Facts true on this tree today (measured 2026-07-31 — do not re-litigate)

- **The use cases already exist and are already wired to the CLI.**
  `PauseInitiative` (`src/app/initiative/pause-initiative.ts`) and
  `ResumeInitiative` (`src/app/initiative/resume-initiative.ts`) each resolve the
  kind, then call `repo.setPaused(id, true|false)`. Both throw
  `UnknownReferenceError` for an unknown id and `WrongTypeReferenceError` for a
  non-initiative id. **Neither takes an `EventFeed`** — the constructors are
  `(repo, resolver)`. CLI leaves `pause initiative` and `resume initiative`
  exist (`src/apps/cli/commands/pause.ts`, `.../resume.ts`;
  `src/apps/cli/initiative.ts:60,74`).
- **No HTTP route reaches them.** `src/apps/http/routes.ts` has no pause,
  resume or activation row; `initiative.patch` (`:595-607`) accepts `name`
  only, via `requireBodyString(body, "name")`.
- **`pause` and `resume` are BANNED_VERBS.** `src/apps/http/routes.test.ts:8-35`
  lists both, and `hasBannedVerbSegment` (`:91-97`) rejects any static path
  segment matching. `POST /api/initiative/:id/pause` is illegal by an existing,
  passing test.
- **Both error classes are already mapped.** `UnknownReferenceError` →
  `404 unknown_reference` and `WrongTypeReferenceError` →
  `400 wrong_type_reference` (`src/apps/http/error-registry.ts:47,64`). Unlike
  026.10, this epic needs **no** new error mapping.
- **`paused` is already on the wire in every read model that matters.**
  `initiativeView` and `initiativeDetailView` both carry it
  (`src/apps/http/views/initiative.ts:23,42`), the project overview carries it
  per initiative (`src/app/project/get-project-overview.ts:143,258,277`), the
  initiative graph carries it and derives
  `executionState: "runnable" | "paused"` per task node
  (`src/app/initiative/get-initiative-graph.ts:383-385`), and the decision queue
  carries it (`src/app/project/get-decision-queue.ts:265`).
- **It is NOT on the wire in the one place this epic's readiness button needs
  it.** `NextAction` carries `check`, `action`, `requiresInput` and an optional
  `command` only (`src/app/project/project-readiness.ts:154-164`), and
  `nextActionView` preserves exactly those four
  (`src/apps/http/views/readiness.ts:52-66`). The initiative id exists **only**
  as text interpolated into a shell command (`project-readiness.ts:546-557`).
  **[debate]**
- **Pause blocks the claim, not the run.** `SqliteJobQueue.claim()` joins to
  `initiatives` and filters `i.paused = 0` (`src/queue/sqlite.ts:24-45`), and
  `EnqueueReadyTasks` skips a paused initiative before it looks at any task
  (`src/app/task/enqueue-ready-tasks.ts:60`). Nothing revokes a lease already
  held: a task that is `running` when the pause lands runs to completion.
- **Pause is invisible to the event feed.** Neither use case touches the feed,
  and neither `EVENT_TYPES` (`src/domain/event.ts:4-31`) nor the `events.type`
  CHECK list (`src/storage/sqlite/migrations.ts:849-858`) has
  `initiative.paused` or `initiative.resumed`. The newest migration on this tree
  is version 31 (`migrations.ts:916`).
- **An event carrying `initiativeId` is project-scoped for free.**
  `SqliteEventFeed.append` derives `events.projectId` from the initiative row
  (`src/events/sqlite.ts:31-56`), and `digest.latest` is the newest project event
  id (`get-project-overview.ts:332`). So a pause event moves `latest`, which is
  the graph's refresh signal.
- **Readiness already asks for exactly this action.** `ACTION_TABLE`
  (`src/app/project/project-readiness.ts:503-513`) maps the `initiative/paused`
  check to `action: "resume the paused initiative"` with
  `command: "kanthord resume initiative --id {id}"`. It is the only template
  command in the table.
- **`POST /api/project/:id/initiative` already accepts `paused`**
  (`routes.ts:586`, `optionalBodyBool`); only the UI withholds it.
- **A deterministic, model-free daemon run is already a solved fixture.**
  `KANTHORD_FAKE_AGENT` plus a `.fake-agent.json` turn script drives real runs
  with no provider call (`scripts/e2e/abandon-run-proof.sh:42-59`), including a
  long-running one via `sleep` turns.

## Decisions (binding)

1. **The gate is a field on the initiative, so the route is
   `PATCH /api/initiative/:id` with a `paused` boolean.** No new path, no new
   segment, no `POST …/activation`. Three reasons, in order: `pause`/`resume`
   are banned verb segments by a passing test; `paused` is already a field of
   the initiative's own representation on both the read and the create; and a
   PATCH inherits the `If-Match` machinery (`routes.ts:117-122`,
   `app.ts:234-261`) instead of inventing a second concurrency story.
2. **`name` and `paused` are mutually exclusive, and at least one is
   required.** A body carrying both is `400 invalid_input`; a body carrying
   neither is `400 invalid_input`. **Unknown keys are ignored**, exactly as
   every other row ignores them (`src/apps/http/body.ts:8-12` reads named
   properties and never rejects extras) — this epic does not introduce an
   exact-key-set rule for one route. The honest name for the rule is mutual
   exclusion, not "one field per PATCH". **[debate]**

   The reason for the exclusion is a real hazard, but the earlier rationale
   overstated AGENTS.md: it forbids use-case-calls-use-case, which does not by
   itself forbid a single atomic `UpdateInitiative`. **[debate]** The actual
   reason: this tree has two CLI-wired mutators of `paused` already, and the
   route's `run` would have to call two of them in sequence with no unit of work
   around the pair — a rename that succeeds and a pause that throws would answer
   an error after a half-applied write. A future multi-field PATCH is legitimate
   **if** it first collapses rename/pause/resume into one atomic use case; that
   is a different epic, and it is named here so the exclusion is a choice, not
   an oversight.

3. **`paused: true` and `paused: false` are the same route and the same
   ceremony.** Resuming is as much an operator decision as pausing, and a UI
   that makes one path cheaper trains the other into a ritual.
4. **No `DangerConfirm` on either direction, and the concurrency claim is
   advisory — stated, not oversold.** **[debate]** `If-Match` here is the same
   mechanism 026.4 decision 1 describes and 026.4's own facts qualify: the
   dispatcher pre-reads, compares by string equality, writes, then re-reads, so
   two concurrent PATCHes can both read the same version and both pass
   (`.agent/plan/epics/026.4-ui-hierarchy-writes.md:25-31`). It reliably catches
   the **stale operator** — the common case, where one tab has been looking at a
   pre-pause DTO — and it does **not** make pause atomic against a true
   simultaneous race. The epic says exactly that on the screen's terms and no
   more. A repository-level compare-and-update for `paused` was considered and
   rejected: it would give this one field a concurrency behaviour no other write
   in the product has, and the damage it prevents is a flipped boolean that the
   next read shows plainly. Ceremony is still refused (`docs/ui-design.md`: a
   modal on a reversible action trains mechanical tapping).
5. **The screen states what pause actually does, in the daemon's words.** The
   control's helper text is fixed here: pausing means **"no new task will be
   claimed for this initiative"**, and a task already running continues. A
   screen that said "work stopped" would be false against
   `src/queue/sqlite.ts:24-45`. The operator who wants a running task stopped
   gets abandonment — 026.10's control, on the task workspace.
6. **`initiative.paused` and `initiative.resumed` are added, with the
   migration.** **[debate]** The draft deferred this and thereby broke a binding
   rule: 026.6 decision 7 refetches the graph **only** when `digest.latest`
   changes, so a second tab holding an initiative graph would keep rendering
   `executionState: "runnable"` for work the daemon will no longer claim —
   contradicting `docs/ui-design.md`'s freshness rules. Both events carry
   `initiativeId`, which is enough for `append` to derive `projectId`
   (`src/events/sqlite.ts:31-56`) and therefore to move `digest.latest`. Both use
   cases gain an `EventFeed`, so the **CLI path emits too** — the feed must not
   depend on which app made the call. The migration adds the two values to the
   `events.type` CHECK list; its version number is the next free integer at build
   time, because 026.8–026.10 may have taken 32 and beyond.
7. **Readiness gains a structured target, and the button never parses a shell
   command.** **[debate]** `NextAction` gains
   `target: { kind: "initiative"; id: string }`, mirrored in `nextActionView`.
   Following the file's own convention for `command`
   (`project-readiness.ts:158-163`), `target` is **property-absent** on a check
   whose action names no entity — and a hermetic test asserts it is **present**
   for `initiative/paused`, so absence there is a failure, not a fallback. The UI
   reads `next.target.id` and nothing else; the fallback to `CommandHandoff`
   applies to checks that legitimately have no target, never to a paused
   initiative. This is backend work with its own story and its own view tests,
   not a UI detail.
8. **The readiness resume runs a read-then-write, and its conflict recovery is
   NOT the three-version form.** **[debate]** A readiness response carries no
   initiative DTO and no `ETag`, so the button must `GET /api/initiative/:id`,
   use that response's `ETag`, then PATCH. On `412` it refetches once and
   re-issues once; a second `412` surfaces the conflict and stops. 026.4's
   three-version base/draft/current recovery is for a form with an operator's
   draft; a resume has no draft, and rendering an empty one would be theatre.
   The retry cap is one, so a fight between two tabs terminates.
9. **`paused` is exposed at initiative create, and 026.4 decision 9 is amended
   there, not silently overridden here.** Ulrich confirmed the amendment
   2026-07-31, and it is written into
   `.agent/plan/epics/026.4-ui-hierarchy-writes.md` on decision 9 and on its
   `paused` non-goal, because overriding a landed epic from a later file leaves
   the landed one reading as still binding. A checkbox, default unchecked,
   labelled with decision 5's sentence. `after` stays withheld — it is an edge,
   and edges are the dependency flow.
10. **No optimistic update.** The PATCH answers `200` with the fresh detail DTO
    (the dispatcher's post-write re-read); the page re-renders from that
    response and invalidates through the matrix.
11. **The invalidation matrix row is fixed here**, because pause changes more
    read models than a rename does:
    `["initiative", id]`, `["project", pid, "initiative"]`,
    `["project", pid, "overview"]`, `["project", pid, "readiness"]`,
    `["initiative", id, "graph"]` and `["project", pid, "queue"]` — the last two
    because `executionState` and the decision queue both read `paused`
    (`get-initiative-graph.ts:383`, `get-decision-queue.ts:265`).
12. **The paused state is visible on the workspace before it is actionable.**
    The Summary tab renders `paused` as a named state with decision 5's
    sentence, and the control sits beside it. A control with no state beside it
    is a switch with no label.

## Non-goals

- **No new route, no new path segment** (decision 1).
- **No multi-field PATCH and no `UpdateInitiative` use case** (decision 2).
- **No repository-level compare-and-update for `paused`** (decision 4).
- **No pause or resume at any other level** — no project-wide pause, no
  objective pause, no task pause. Nothing in the domain models them.
- **No stopping of a run in flight** — that is abandonment, 026.10 (decision 5).
- **No actionable control for any readiness check other than
  `initiative/paused`** (decision 7). Every other check keeps `CommandHandoff`.
- **No `after` at create** (decision 9).
- **No optimistic UI. No new polling** — the visible overview and graph keep the
  visibility-gated polling `docs/ui-design.md` already binds; this epic adds no
  new poller and no cross-project one. **[debate]**
