## Goal

Every entity the API can describe has a page, reachable by a URL that carries
its whole chain. Initiative, objective, task and resource render as W2
workspaces — header, summary, tabs — with honest empty states instead of blank
tabs. The task page turns the daemon's evidence into something an operator can
read without losing the exact facts underneath. Where the daemon says an action
is due but has no HTTP route, the page shows the control disabled and hands over
the exact CLI command the server itself supplies.

## Verified facts (measured on this tree, 2026-07-31 — do not re-litigate)

- **Detail DTOs have no ancestry.** `InitiativeDetailView`
  (`views/initiative.ts:40`) has no `projectId`; `ObjectiveDetailView`
  (`views/objective.ts:47`) has no `initiativeId`; `TaskDetailView` has
  `objectiveId` and nothing above it. A deep link cannot rebuild the breadcrumb
  from one GET, which is why the URL carries the chain. **[debate]**
- The list DTOs are richer in one place: `ObjectiveView` (the collection row,
  `views/objective.ts:16`) **does** carry `initiativeId`.
- `ActionView` (`views/shared.ts:1`) is `{kind, target {type,id},
targetDependencyId?, requiresInput[], command?}`. **`command` is the exact CLI
  invocation, supplied by the server** — so CommandHandoff never fabricates one.
  **[debate]**
- `taskDetailView` carries `status`, `agent?`, `objectiveId`, `dependencies[]`,
  `note?`, `instructions?`, `ac?`, `verification?`, `result`,
  `dependencyStatus[]`, `context?`, `landingCandidate {state,baseSHA,
candidateSHA,target} | null`, `abandoning`, `waiting[] {id,neverSatisfies}`,
  `blockedForever`, `downstream`, `action`.
- `objectiveDetailView` carries `integrations[]` per repository, `commitOid?`,
  `parentOid?`, conflict fields.
- Tasks are listed initiative-scoped only: `GET /api/initiative/:id/task`
  with `?objective=<id>`. There is no objective-scoped task route.
- `resourceView` always carries `type` and usually `projectId`.
- CORS `allowHeaders` omits `If-Match` (`app.ts:155`). **This is not a defect
  for the UI**: the browser is always same-origin with the daemon — the served
  build in production, the Vite proxy in dev — so no preflight happens. Recorded
  so nobody "fixes" it. This epic writes nothing anyway. **[debate]**

## Decisions (binding)

1. **Canonical nested routes carry the whole chain**, because no detail DTO
   carries its ancestry:
   - `#/project/:projectId/initiative/:initiativeId`
   - `#/project/:projectId/initiative/:initiativeId/objective/:objectiveId`
   - `…/objective/:objectiveId/task/:taskId`
   - `#/project/:projectId/resource/:type/:resourceId`
2. **A wrong chain is `scope mismatch`, not `missing`.** A URL naming a real
   task under the wrong objective is operationally different from a deleted
   task, and conflating them hides an operator error. This epic adds one
   component, `[data-testid="scope-mismatch"]`, which names the conflict and
   links to the entity's correct URL when it can be computed. **AsyncBoundary's
   seven-state union from 026.1 is NOT extended** — that contract stays fixed.
   **[debate]**
3. **Validate with the strongest available check, not one blanket rule.**
   **[debate]**
   - task → `taskDetail.objectiveId` must equal `:objectiveId` (direct field)
   - objective → the initiative's objective collection must contain it, and its
     row's `initiativeId` must equal `:initiativeId` (the row has the field)
   - initiative → the project's initiative collection must contain it
   - resource → `resource.type` must equal `:type`, and `projectId` must match
     when the DTO carries it
     The real fix is ancestry in the detail DTOs; it is listed for EPIC 026.8, and
     until then this epic pays one collection read per ancestor level.
4. **The breadcrumb is built from real names**, read from the chain's own
   endpoints (`/api/project/:id`, `/api/initiative/:id`, `/api/objective/:id`),
   never from ids alone and never from a client-side cache that may be cold on a
   deep link.
5. **Each W2 page has fixed tabs AND a fixed empty state per tab.** A tab is
   never an empty shell. **[debate]**
   - **initiative** — Summary (status, paused, branch, workspace) · Objectives
     (the collection; empty: "no objectives yet") · Dependencies (`after`,
     `waiting`; empty: "no dependencies")
   - **objective** — Summary (status, `commitOid`/`parentOid`, note, conflict
     fields) · Tasks (`?objective=` filtered; empty: "no tasks yet") ·
     Integration (`integrations[]` per repository; empty: "not integrated yet")
   - **task** — Summary · Instructions & AC (`instructions`, `ac`,
     `verification`, `context`; each with its own "not specified") ·
     Dependencies (`dependencyStatus`, `waiting`) · Result (empty for a task
     that has not run: "no result yet — this task has not run") · Landing
     (`landingCandidate === null`: "no candidate yet")
   - **resource** — Summary only. **"Edit" is an action, not a tab**, and it
     belongs to EPIC 026.5. **[debate]**
6. **Interpretation never replaces the exact fact.** `blockedForever`,
   `waiting[].neverSatisfies` and `downstream` render as operator sentences
   **and** keep the evidence beside them: the blocking entity's id (copyable and
   linked when it is in the same chain), and the exact `downstream` count. The
   UI does not re-derive actionability — that is the daemon's job and it already
   answered in `action`. **[debate]**
7. **The disabled-control inventory is driven by the server's `action`, not by
   a client status table.** When `action` is non-null and its `kind` has no HTTP
   route, the page renders that one control disabled, names why (the daemon has
   no HTTP action for it yet), and renders `CommandHandoff` with
   `action.command` when the server supplied one. When `action` is null, no
   control is rendered. A hard-coded "failed means retry" table is rejected:
   status alone does not establish that an action applies. **[debate]**
8. **Rare states are proven hermetically, not by the Proof.** A deterministic
   fixture can reach a pending task; it cannot reach `awaiting_confirmation` or
   `failed` without a real agent run. Those branches are Vitest cases over
   stubbed DTOs, and this epic says so plainly rather than pretending the
   browser Proof covers them. **[debate]**
9. **Still no writes.** No create, no rename, no dependency edit, no `ETag`
   capture. 026.4 and 026.5 own every mutation, and an unbuilt control is
   omitted rather than greyed out (026.2 decision 8).

### Contract with the Proof (binding names)

| Selector                                   | Meaning                                |
| ------------------------------------------ | -------------------------------------- |
| `[data-testid="entity-header"]`            | the W2 header, carries the entity name |
| `[data-testid="entity-tabs"] [role="tab"]` | the tab strip                          |
| `[data-testid="tab-panel"]`                | the active panel                       |
| `[data-testid="empty-result"]`             | task Result empty state                |
| `[data-testid="empty-landing"]`            | task Landing empty state               |
| `[data-testid="task-downstream"]`          | the exact `downstream` count           |
| `[data-testid="scope-mismatch"]`           | decision 2's state                     |
| `[data-testid="disabled-action"]`          | decision 7's disabled control          |
| `[data-testid="command-handoff"]`          | renders `action.command` verbatim      |

`[data-testid="breadcrumb"]`, `[data-testid="async-missing"]` and
`[data-testid="project-shell"]` keep their EPIC 026.1 meanings.

## Verification Gate

Gates: `npm run verify`.

Hermetic coverage required beyond the Proof (Vitest + jsdom, in `ui/`):

- **Scope validation**, one case per rule in decision 3, plus: a real entity
  under the wrong parent renders `scope-mismatch` and NOT `async-missing`, and a
  genuinely absent id renders `async-missing` and NOT `scope-mismatch`.
- **Every tab's empty state** from decision 5, one test per tab.
- **Task evidence**: `blockedForever` and `neverSatisfies` render their sentence
  **and** the blocking id; `downstream` renders the exact number.
- **The disabled inventory** (decision 7) over stubbed DTOs: `action === null`
  renders no control; an `action` with a `command` renders CommandHandoff with
  that exact string; an `action` without a `command` renders the disabled
  control and no fabricated command; the rare statuses of decision 8
  (`awaiting_confirmation`, `failed`, `abandoning`) each get a case here.
- **No mutation is possible**: no test may render a control that issues POST,
  PATCH or DELETE.

Proof: `scripts/e2e/ui-entities-proof.sh` — deterministic, no model, loopback
only, nothing left running:

```bash
scripts/e2e/ui-entities-proof.sh
```

It must print `026.3 ok: …`. Phases:

- **A** — build the UI; Chromium present, or exit with the install command.
- **B** — seed through the real API: a project, an initiative, an objective, two
  tasks (one depending on the other), a repository resource.
- **C** — cold-load the initiative URL: the breadcrumb shows the real project
  and initiative names, the Objectives tab lists the seeded objective, the
  Dependencies tab renders its empty state.
- **D** — cold-load the objective URL: the Tasks tab lists both seeded tasks and
  the Integration tab renders "not integrated yet".
- **E** — cold-load the task URL: the tab strip has five tabs; Result renders
  `empty-result` and Landing renders `empty-landing`, because a pending task has
  neither; the Dependencies tab names the blocking task's id; `task-downstream`
  shows the exact count the API returns for that task.
- **F** — the same task id under the OTHER objective's URL renders
  `scope-mismatch` and not `async-missing`; a made-up task id under the real
  objective renders `async-missing` and not `scope-mismatch`.
- **G** — the resource entity URL renders the repository summary, and the
  credential's secret appears nowhere in the document.
- **H** — R3 holds: no request the page issued carried an `Authorization`
  header, and no request used POST, PATCH or DELETE (decision 9).

Ran against the CURRENT tree (2026-07-31): the script exits `1` in phase A,
because `ui/` does not exist and `npm run build:ui` is not a script yet.

## Stories

- **S1 — nested routes + scope validation** (decisions 1–3) and the
  `scope-mismatch` component.
- **S2 — the breadcrumb** over the chain's real names (decision 4).
- **S3 — initiative W2** with its three tabs and empty states.
- **S4 — objective W2** with its three tabs and empty states.
- **S5 — task W2**: five tabs, interpreted evidence keeping exact facts
  (decision 6).
- **S6 — the disabled inventory** from `action` (decisions 7–8), with
  CommandHandoff getting its first consumer.
- **S7 — resource W2**, summary only.
- **S8 — the Proof**: `scripts/e2e/ui-entities-proof.sh` prints `026.3 ok: …`
  without its assertions being edited.
