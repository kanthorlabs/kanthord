# EPIC 026.4 — hierarchy writes + the conditional-edit layer

> Authored 2026-07-31. The design went through the debate engine (`pi`,
> read-only). Nine findings changed the shape and are marked **[debate]**. The
> largest: the draft called this "optimistic concurrency" when the server's
> guarantee is weaker, and the draft's ETag ownership would have made the
> conflict undetectable in the very case it existed for.
>
> Execution order: 026 → 026.1 → 026.2 → 026.3 → **026.4** → 026.5 → … → 026.8.
> Normal `/work`: writes only `ui/**` and `scripts/**`, installs nothing
> (EPIC 026 decision 9), adds no API route.

## Goal

The operator can build a plan in the browser: create projects, initiatives,
objectives and tasks, rename what has a rename route, and edit dependency edges
on all three aggregates. Every guarded write goes through one edit-session
layer that freezes the representation the edit started from, so a stale write is
caught and recovered without losing what the operator typed. What the server
actually guarantees — and what it does not — is stated on the screen and in this
epic, not assumed.

## Verified facts (measured on this tree, 2026-07-31 — do not re-litigate)

- **The precondition is sequential, not atomic.** `app.ts:223-247` reads the
  `readRow` representation, compares `If-Match` by **exact string equality**,
  writes, then re-reads for a fresh `ETag`. Two concurrent PATCHes can both read
  the same representation, both pass, and both write — last write wins. This
  matches EPIC 021 decision 3, already recorded: `If-Match` is **advisory
  against a stale editor**, not a serializable compare-and-swap. This epic
  therefore ships **conditional edit**, and never claims lost-update
  prevention. **[debate]**
- Consequences of that exactness: no `*`, no tag lists, no weak-validator
  semantics. The client must send the `ETag` **verbatim, quotes included**, and
  must never recompute one from JSON. **[debate]**
- The validator is over the **detail DTO** named by `readRow`, so it can return
  to a previous value (an ABA case), and state outside that DTO can change
  without changing it. **[debate]**
- A missing entity answers `404` before the missing-`If-Match` check, so a
  `428` cannot be the first thing a deleted-entity edit sees. **[debate]**
- `POST` returns `201` + `Location` and **no `ETag`** (`app.ts:283` sets `ETag`
  on `200` JSON only). Create-then-edit therefore requires a detail `GET`
  first. **[debate]**
- Dependency writes are `POST`/`DELETE` sub-resources with **no `If-Match` and
  no representation**, so they are outside the conditional-edit layer entirely.
  **[debate]**
- `fetch` does not reject on `412`. `api-client.ts` must read `response.status`
  and decode the error envelope itself. **[debate]**
- Create bodies: initiative accepts `name`, `paused`, `after[]`; objective
  accepts `name`, `after[]`; task accepts `title` plus `instructions`, `ac[]`,
  `verification[]`, `agent`, `dependencies[]`, `context{}`.
- `PATCH /api/initiative/:id` takes **`name` only**, so `paused` cannot be
  changed after creation.
- There is no task rename and no delete route for any entity.
- `error-registry.ts` gives dependency failures distinct stable codes; they are
  not one generic "invalid edge".

## Decisions (binding)

1. **The edit session owns the validator, and freezes it.** Opening a form
   snapshots `{baseData, baseEtag, draft}`. The submit uses `baseEtag`
   **verbatim**, never `queryClient.getQueryData()` and never the latest render
   — polling, a focus refetch or another mutation would otherwise replace the
   validator while the operator types, and the stale write would silently
   succeed. The cache may keep updating; a dirty form's `baseEtag` is immutable
   until conflict resolution or reset. **[debate]**
2. **Conflict recovery is a real three-version state**: base (what the edit
   started from), draft (what the operator typed), current (what the server has
   now), all three shown and labelled. Two-version "draft vs current" is
   rejected — it cannot tell an operator change from a server change, and 026.5's
   multi-field resource forms reuse this layer. Recovery does a fresh detail
   `GET` that bypasses the cache, and the resubmit uses **that** response's
   `ETag`. A second `412` repeats the cycle with the draft intact. **[debate]**
3. **`428` is a client defect only because decision 1 makes it impossible.**
   Every edit session begins from a detail `GET` — including after a create,
   which returns no `ETag`. If a `428` still arrives, it is reported as a bug in
   the UI, not as an operator conflict. **[debate]**
4. **Dependency writes are explicitly outside the conditional-edit layer**, and
   the epic says so where an operator can see it: they carry no precondition,
   they can race each other and any PATCH, and the UI does not pretend
   otherwise. **[debate]**
5. **Invalidation follows read models, through one documented matrix** — not
   "everywhere the name appears". The matrix is a real table in
   `ui/src/lib/invalidation.ts`, tested, and every future write must add its
   row: **[debate]**

   | Mutation          | Invalidates                                                        |
   | ----------------- | ------------------------------------------------------------------ |
   | project create    | `["project"]`                                                      |
   | project rename    | `["project"]`, `["project", id]`, `["project", id, "overview"]`    |
   | initiative create | `["project", pid, "initiative"]`, `["project", pid, "overview"]`   |
   | initiative rename | the above + `["initiative", id]`                                   |
   | objective create  | `["initiative", iid, "objective"]`, `["project", pid, "overview"]` |
   | objective rename  | the above + `["objective", id]`                                    |
   | task create       | `["initiative", iid, "task"]`, `["project", pid, "overview"]`      |
   | dependency add/rm | the source entity's detail + `["project", pid, "overview"]`        |

   A successful PATCH also writes its own detail cache from its own response.
   Surfaces added later (the graph in 026.6, readiness) add their rows in their
   own epic — the matrix is the place that makes the omission visible.

6. **Renames are entity-owned wherever the entity has a page.** Initiative
   rename on the initiative page, objective rename on the objective page.
   Project rename stays on the Projects collection, because a project has no W2
   page — its page is the Overview. **[debate]**
7. **Shared infrastructure, separate forms.** No generic entity-form
   abstraction; but transport, ETag snapshotting, conflict state, field-error
   mapping and invalidation are one shared layer, or six forms will drift into
   six concurrency behaviours. **[debate]**
8. **Task create is a full-page section with a stable URL**, not a Sheet, and
   its field contract is fixed here: `title` required; `instructions` a
   textarea; `ac[]` and `verification[]` ordered lists with add, remove and
   reorder; `context{}` key/value rows; `dependencies[]` a picker over the
   initiative's task collection; `agent` a free-text field with a hint, because
   **there is no agent API to enumerate** (listed for 026.8). The three
   name-only renames stay `Sheet`s. **[debate]**
9. **`paused` and `after` are deliberately NOT exposed at create.** `paused`
   cannot be undone — `initiative.patch` takes `name` only — so offering it
   would create a state the UI cannot leave. `after` is an edge, and edges are
   the dependency flow. Both are recorded here as deliberate omissions, not
   oversights. **[debate]**

   **AMENDED by EPIC 026.11 decision 9 (Ulrich, 2026-07-31), for `paused`
   only.** 026.11 makes `paused` writable through `PATCH /api/initiative/:id`,
   so the reason this decision gave — "a state the UI cannot leave" — no longer
   holds, and the create checkbox lands there. `after` stays withheld,
   unchanged. Nothing in 026.4's own scope moves; this note exists so the
   landed decision does not read as still binding.

10. **Dependency errors render distinctly and inline.** A cycle, an unknown
    reference and a scope violation each render their own message against the
    form from the server's own error code — never one generic toast.
    **[debate]**
11. **Dependency removal does NOT take DangerConfirm.** It is reversible
    through the add route, and J1 says fewer decisions per item. It gets an
    inline confirm that names the exact source and dependency. DangerConfirm
    stays for genuinely destructive operations — `reclone`, in 026.5. The UI
    does **not** claim what a removal unblocks: no read model proves that.
    **[debate]**
12. **Task rename is not part of the product action inventory.** Task content
    comes from the graph package the operator authors outside the app; the
    daemon owns the task after import. So there is no rename control and no
    026.8 gap entry — this is a decision, not an omission. **[debate]**

## Verification Gate

Gates: `npm run verify`.

Hermetic coverage required beyond the Proof (Vitest + jsdom, in `ui/`):

- **The frozen validator** (decision 1): a cache update while the form is dirty
  does not change the submitted `If-Match`; the header is byte-identical to the
  received `ETag`, quotes included; a form reset re-arms from a fresh `GET`.
- **Three-version conflict** (decision 2): a stubbed `412` keeps the draft,
  renders base, draft and current distinctly, and the resubmit carries the
  recovery `GET`'s ETag — not the original and not a cached one.
- **`428`** renders the client-defect state, not the conflict state.
- **A `404` during recovery** renders missing and does not strand the operator
  in a retry delay.
- **The invalidation matrix** (decision 5) is asserted against the query cache,
  one case per row; a mutation with no row fails the matrix's own guard test.
- **Dependency errors**: each server error code maps to its own message; no
  code falls through to a generic string.
- **Create contracts**: task create sends only the fields it collected, `ac`
  and `verification` keep their order, and `paused`/`after` are never sent
  (decision 9).

Proof: `scripts/e2e/ui-writes-proof.sh` — deterministic, no model, loopback
only, nothing left running:

```bash
scripts/e2e/ui-writes-proof.sh
```

It must print `026.4 ok: …`. Phases:

- **A** — build the UI; Chromium present, or exit with the install command.
- **B** — seed a project through the API and start the daemon on the build.
- **C** — create an initiative, an objective and a task **through the UI**: the
  initiative on the project Overview, the objective on the initiative page's
  `objectives` tab, the task through the full-page create form of decision 8.
- **C2** — verify all three through the API, not only on screen. Ids are
  resolved by name with the Proof's own `lookup.mjs`, which fails on zero or on
  more than one match.
- **D** — the deterministic `412`, with no race and no timing trick:
  1. open the project's rename form in the browser and type a draft;
  2. from the Proof's own HTTP client, `GET` the project, capture its `ETag`,
     and `PATCH` a different name with it — the intervening version;
  3. submit the still-open form;
  4. the browser's PATCH response is `412`, observed on the response stream;
  5. the draft is still on screen, and base, draft and current all render;
  6. reload current, resubmit, get `200`, and the new name appears in the
     collection **and** in the breadcrumb — proving the invalidation matrix.
- **E** — dependency add through the UI succeeds; adding an edge that closes a
  cycle renders the server's specific error inline and no generic toast.
- **F** — R3 holds: no request the page issued carried an `Authorization`
  header.

Ran against the CURRENT tree (2026-07-31, after EPIC 026.1 landed the shell):
phases A and B pass — the build exists, Chromium is installed, the daemon serves
the build and the seed succeeds — and the run exits `1` in phase C, waiting for
`[data-testid="create-initiative"]`, which no screen renders yet. The script is
complete: no story adds an assertion to it, and story 08 only makes it pass.

## Stories

- **S1 — the edit-session layer**: `{baseData, baseEtag, draft}`, verbatim
  `If-Match`, status handling in `api-client.ts` (decisions 1, 3).
- **S2 — the three-version conflict state** (decision 2).
- **S3 — the invalidation matrix** module and its guard test (decision 5).
- **S4 — project create + rename** on the Projects collection.
- **S5 — initiative and objective create + rename**, entity-owned (decision 6).
- **S6 — task create**, the full-page form of decision 8.
- **S7 — dependency add/remove** on the three aggregates, with code-specific
  errors (decisions 4, 10, 11).
- **S8 — the Proof**: `scripts/e2e/ui-writes-proof.sh` prints `026.4 ok: …`
  without its assertions being edited.

## Non-goals

- **No resource writes, no secrets, no `reclone`** — EPIC 026.5.
- **No claim of lost-update prevention.** The server's precondition is
  sequential (021 decision 3). An atomic revision compare-and-write in
  persistence would be a backend epic, and is not this one.
- **No delete of any entity** — no route exists.
- **No `paused` toggle** — `initiative.patch` cannot express it. (EPIC 026.11
  makes it expressible and ships the toggle; see the amendment on decision 9.)
- **No task rename** (decision 12).
- **No graph, import, readiness, inbox or conflict** — 026.6 and 026.7.
