# Midway insertion — capability evaluation

Verified 2026-07-25 against the E2E DB `.data/e2e-00716/kanthord.db` (real CLI
runs, not code reading). Question: can we insert an initiative / objective / task
into an existing plan midway — e.g. add initiative **2.1** to fix what we missed
in initiative 2, with 3 and 4 already planned?

**Verdict: no, not reliably.** (Findings F1, F2, F4, F5 stand. **F3 is retracted
as invalid** — see its section.) Task insertion into an _untouched_ initiative
works. Insertion into an initiative that has _made progress_ silently does
nothing. Objective insertion works but falsifies the parent's terminal status.
Initiative-level ordering does not exist as a concept at all.

---

## F1 (critical) — `import graph --apply` reports success and writes nothing

`import graph --apply --initiative <id>` is the designed incremental path. Its
safety model is sound in intent: `apply-graph.ts:83-85` classifies a node
`drifted` when `liveSha !== baselineSha`, and `:390` treats `drifted | locked` as
blocking conflicts so no CAS write happens.

The defect is that the live sha is computed from **content + live DB status**
(`apply-graph.ts:70-75`). Every task that has already run therefore differs from
its create-time manifest baseline and is permanently `drifted`. On any initiative
that has progressed, the apply is always refused — and the refusal is invisible.

Reproduced on a copy of the E2E DB:

```sh
cp .data/e2e-00716/kanthord.db .data/e2e-00716/probe.db
export KANTHORD_DB="$PWD/.data/e2e-00716/probe.db"
. .data/e2e-00716/ids.env          # PROJECT / REPO / PROV / CRED_OAUTH
# graph-a = the imported TODO graph package + one extra task file (ref: health-task, no deps)
node src/main.ts import graph .data/e2e-00716/graph-a \
  --apply --initiative 01KYB1A2T5CRCW35G2PEAFBAC6 \
  --bind source=$REPO --bind provider=$PROV --bind cred=$CRED_OAUTH
echo "EXIT=$?"
```

Output — 8 classified nodes, exit **0**:

```
unchanged: 01KYB1A2T5CRCW35G2PEAFBAC6 (initiative.md)
unchanged: 01KYB1A2T6540GHHWRWT750AA1 (objective.md)
drifted:   01KYB1A2T6540GHHWRWT750AA2 (task-create.md)
drifted:   ...AA3, ...AA4, ...AA5, ...AA6        # 5 drifted in total
created:   health-task (task-health.md)
1 created, 0 updated, 2 unchanged, 0 missing
EXIT=0
```

Nothing was written. Confirmed by direct SQL:

```sh
node -e '
const {DatabaseSync}=require("node:sqlite");
const db=new DatabaseSync(".data/e2e-00716/probe.db");
console.log(db.prepare("select title from tasks t join objectives o on o.id=t.objectiveId where o.initiativeId=?")
  .all("01KYB1A2T5CRCW35G2PEAFBAC6").map(r=>r.title).join(" | "));'
# => the 5 original tasks + one CLI-created task. No "Health — GET /health".
```

Count reconciliation: **8** nodes classified (initiative + objective + 5 tasks +
health-task); the summary accounts for only **3** of them (1 created, 2 unchanged)
and omits all **5** `drifted` — the ones that actually decided the outcome. The
**6** task rows in the DB afterwards are the 5 original tasks plus the separate
CLI-created task from F3, not the applied one.

Precisely stated: the storage layer behaved correctly (the CAS guard did its job).
The defect is the **report** — `created:` in the per-node list, `1 created` in the
summary, and exit **0**, all while blocking conflicts prevented every write. No
stored data was lost; the operator's intent was silently dropped.

**Fix:** non-empty conflicts must exit non-zero and print
`refused: N drifted node(s)` before anything else. Small, independent, and it
converts a silent failure into a visible one.

## F2 (major) — a new node cannot depend on an existing one by graph `ref`

The same graph file that imports cleanly under `--create` fails under `--apply`:

```
UnknownDependencyError: Task health-task depends on unknown task create-task
    at validateGraph (src/domain/graph.ts:57:15)
    at ApplyGraph.execute (src/app/graph/apply-graph.ts:386:5)
```

`create-task` is in the same package directory and exists in the DB. Refs are
resolved on the create path but not the apply path. Referencing the dependency by
its **ULID** works instead — so inserting a task that depends on existing work
requires hand-editing ULIDs into graph files, defeating the purpose of refs. The
failure also escapes as a raw Node stack trace, the same unhandled-error class as
the `publish` crash in EPIC 007.16 (`B8`).

## ~~F3 (major) — `create task` cannot bind context~~ — RETRACTED (invalid finding)

**This finding was wrong. `create task --context <type=resource-id>` exists, is
documented in `--help`, and works.** Retracted 2026-07-25.

How the error was made: `create task --help` was read through `sed -n '4,14p'`,
and the `--context <type=resource-id>` line sits at lines **15-16** — it was
truncated off. A task was then created _without_ `--context`, and the resulting
`CredentialError: task has no credential context` was attributed to a missing
capability rather than to the omitted flag.

The plumbing is complete end to end: the CLI parses repeated
`--context type=resourceId` entries (`src/apps/cli/task.ts:72-93`),
`CreateTask.execute` accepts `context?: Record<string, string>`
(`src/app/task/create-task.ts:38`), validates each resource reference, and
persists it via `saveTaskContext` (`:70`).

Verified against the real model:

```sh
T=$(node src/main.ts create task --objective $OBJ --title "Ctx probe — health endpoint" \
  --agent generic@1 --instructions "Add a GET /health route to src/todo.mjs…" \
  --ac "GET /health returns 200" --verification "node --check src/todo.mjs" \
  --context repository=$REPO --context ai_provider=$PROV --context credential=$CRED_OAUTH | head -1)
# task_context rows: ai_provider=…, credential=…, repository=…
node src/main.ts run daemon --until-idle --poll-interval 2000
# task 01KYBC5RZZ2DYFT0SGQKYBVGRP: agent finished: turns=4 tokensIn=6368 tokensOut=211
# task 01KYBC5RZZ2DYFT0SGQKYBVGRP: completed
```

### Residual (real, minor) — context is validated late, not at creation

`create task` **without** `--context` still succeeds. The failure surfaces only
when the daemon claims the task and the runner aborts
(`src/agent-runner/pi.ts:398,405`), spending a claim and an event cycle on work
that could never run.

`CreateTask` already receives an `AgentCatalog`, but that port exposes only
`has(ref): boolean` (`src/agent-runner/port.ts:6-8`) — it does not declare which
context types an agent requires, so creation-time validation is not currently
possible without extending it. Fixing this would also have made the mistake above
self-correcting.

Not scheduled. It is a fail-fast improvement, not a capability gap.

## F4 (major) — adding work to a terminal initiative falsifies its status

```sh
node src/main.ts create objective --initiative 01KYB1A2T5CRCW35G2PEAFBAC6 --name late-addition
# => objective created
node src/main.ts get initiative --id 01KYB1A2T5CRCW35G2PEAFBAC6
# => status: landed     (with a `building` objective inside it)
```

`CreateObjective` has no initiative-status guard, and `transitionInitiative`
(`src/domain/initiative.ts:53-55`) has only `building->landed` — nothing can walk
it back. The status board then shows `initiative: landed` above
`building late-addition`.

The daemon also **does** claim and run work inside a `landed` initiative (verified:
it ran the late task and failed it). So `landed` is not a freeze — just a label
that stopped being true.

**Do not fix this with a `landed->building` transition.** Reopening is not a label
change: the objective branch has landed in the bare home, per-target publication
state may already exist, and the objective's `commitOid`/`parentOid` anchors may no
longer match. A bare status edge would make the Git state _less_ honest. The
correct model is a **follow-up** initiative/objective, with the terminal parent
left immutable.

## F5 (major) — initiative and objective ordering do not exist

- No `order` / `sequence` / `rank` column on `initiatives` or `objectives`.
  Verified schema: `initiatives(id, projectId, name, paused, sha256, status,
workspace)`, `objectives(id, initiativeId, name, sha256, status, commitOid,
parentOid)`. The only `position` column is `task_dependencies.position`, which
  orders one task's dep list.
- The task DAG is the only ordering mechanism and it is **initiative-scoped**:
  `AddDependency` validates against `listByInitiative(objective.initiativeId)`
  (`add-dependency.ts:75`), so a cross-initiative edge cannot be expressed.
- `EnqueueReadyTasks` iterates `listAllInitiatives()` and skips only `paused` ones
  (`enqueue-ready-tasks.ts:40-42`) — **all non-paused initiatives are worked
  concurrently**, in DB order.

So "2.1" is decoration. There is no way to state "2.1 must finish before 3".

`pause initiative` is **not** an adequate substitute:

- it records no causal relationship — it is operator memory outside the graph;
- nothing stops 3 being unpaused before 2.1 finishes;
- a restart or re-import gives no explanation of _why_ 3 is paused;
- it does not extend to objective-level insertion;
- it cannot safely handle work in 3 that is already queued or running.

## Recommended design (post-debate)

### 1. Three-axis classification for apply

Lifecycle status must not participate in the content digest. Separate three facts:
content provenance, intended package change, and lifecycle state.

| Live state | Intended vs baseline | Live content vs baseline | Result                                  |
| ---------- | -------------------- | ------------------------ | --------------------------------------- |
| absent     | any                  | n/a                      | `created`                               |
| existing   | same                 | same                     | `unchanged` — _regardless of lifecycle_ |
| existing   | changed              | same                     | `updated` if mutable, else `locked`     |
| existing   | any                  | different                | `drifted`                               |

The load-bearing detail: **`locked` applies only when the package wants to modify
an existing node.** A completed task whose file is unchanged must never block
adding a _different_ task.

The content digest must exclude runtime fields (status, queue state, commit OIDs,
failure details) and include **all** declarative graph data — dependencies,
context bindings, acceptance criteria, verification commands, parent links —
otherwise a genuine concurrent edit is mistaken for `unchanged`. The DB must
persist a comparable live content revision. With no compatibility obligation,
change the manifest and DB hash contract directly rather than layering
compatibility logic.

### 2. Causal dependencies at all three levels

```text
initiative 3   dependsOn  initiative 2.1
objective  B   dependsOn  objective  A.1
task       Y   dependsOn  task       X      # exists today
```

Readiness composes by level:

- an initiative may enqueue work only when all prerequisite initiatives are `landed`;
- an objective may enqueue tasks only when prerequisite objectives are `integrated`;
- a task may run only when its task dependencies are `completed`.

**Retroactive ordering must be rejected.** Adding a dependency to work already
running or completed cannot make executed work happen later; the command must
refuse and say so, or require an explicit drain/cancel. If initiative 3 has not
started, adding `3 dependsOn 2.1` is safe; if it has started, kanthord must report
that the requested ordering can no longer be guaranteed.

A convenience `--after <ref>` flag could make insertion ergonomic while storing a
real dependency edge — worth considering, not yet required.

### 3. Follow-up, never reopen

Model the real case as `initiative 2 → initiative 2.1 → initiative 3`, leaving
initiative 2 immutable. Likewise, adding work to an `integrated` objective needs a
**new** objective — reopening one can invalidate its approved squash commit and
parent OID.

## Fix order

1. Define insertion semantics: dependency levels, and the behavior when downstream
   work has already started. **Design first** — building the apply mechanism before
   this risks an importer that cannot express the requirement.
2. Make conflict/refusal output unambiguous and exit non-zero (F1). Independent and
   tiny; can ship immediately, ahead of the design work, as it only stops a silent
   failure.
3. Correct the content-provenance vs lifecycle classification model (F1 root cause).
4. Resolve existing nodes by graph `ref` during apply (F2).
5. Persist initiative + objective dependencies: validation, readiness gates,
   CLI/import syntax (F5).
6. Decide terminal-parent policy — prefer follow-up nodes over reopening (F4).
7. ~~Add task context flags~~ — **void**: `F3` is retracted, the flags already
   exist. Optional replacement: validate an agent's required context types at
   creation time (fail fast instead of failing in the runner), which first needs
   `AgentCatalog` to declare requirements rather than only `has(ref)`.
