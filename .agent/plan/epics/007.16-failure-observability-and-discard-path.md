# EPIC 007.16 — Failure observability + a terminal discard path

## Goal

The real-model E2E run (`.agent/findings/007.16-e2e-findings.md`) built the
5-endpoint TODO API from an empty `main` and delivered it to the real remote with
zero defects in the _work_. Every finding was in the **operator** surface: what a
human can see when something goes wrong, and what a human can do about it.

After this epic:

1. **A failed task explains itself.** The failure path persists a `task_results`
   row carrying `reason`, and `get task` renders `reason:` — instead of printing
   only `status: failed` and leaving the operator to page the event feed with a
   cursor. (Verified: today **no** `task_results` row is written on failure at
   all, so this is a write-path fix, not a rendering fix.)
2. **Terminal commands tell the truth.** `approve objective` on an already-
   `integrated` objective fails with a domain conflict (no transition occurred);
   `publish repository` on an already-published OID succeeds with
   `already published` and emits no second event; `publish repository` on an
   unknown ref returns a typed `UnknownReferenceError` instead of an unhandled
   `execSync` stack trace; `repository.published` carries a `repositoryId`
   subject like every other event row.
3. **Failed work can be discarded.** The existing terminal-but-unsuccessful
   `discarded` task status becomes reachable via `reject task --resolution
discard` from `failed` (today only from `awaiting_confirmation`), `discarded`
   is added to the objective and initiative status sets, and `reject objective`
   exists beside `approve objective` / `retry objective`. An initiative holding
   unachievable work can finally reach a terminal state instead of living in
   `building` forever with `pause` as its only escape.

### Decision record (human-confirmed after adversarial debate)

- **Reuse the existing `discarded` status; do not add `abandoned`.** `discarded`
  already exists (`src/domain/task.ts:10`) with a `task.discarded` event and
  matches the existing `--resolution discard` verb. Adding `abandoned` beside it
  would leave two names for one concept.
- **`discarded` is terminal but UNSUCCESSFUL. Only `completed` satisfies a
  dependency edge.** An earlier draft of this epic proposed proving the fix by
  showing "the objective completing with `abandoned` + `completed` tasks" — that
  encodes the exact bug the epic must prevent: a discarded prerequisite did not
  produce the artifact its dependents need, so treating it as completion would
  unblock invalid downstream work and then mark an incomplete objective
  `integrated`.
- **Cascade discard.** Discarding a task discards its dependent subtree, and the
  objective becomes `discarded` (not `completed`). Chosen over "block, don't
  cascade" (which re-introduces the non-terminal problem this epic exists to fix)
  and "refuse the discard" (most keystrokes, same end state).
- **Idempotency is asymmetric by design:** `approve objective` is a state
  transition, so a no-op is an error; `publish repository` is a sync, so a no-op
  is a success. Confirmed deliberately, not derived.
- **No `delivered` initiative status and no initiative-level publication
  rendering** — see `S2` in the findings file.
- **No `attempts:` line.** The only available counter (`run-next-task.ts:193`) is
  an in-run _provider transient-retry_ count, not a human-retry count, and is
  never persisted; rendering it as `attempts:` would read as human retries. Ship
  `reason:` alone rather than a misleading field.
- **No coverage story here.** `retry objective` / conflict, daemon-crash
  recovery, and multi-repo remain untested; "file whatever that finds" is
  unbounded scope and belongs to a separate E2E investigation.

## Verification Gate

Gates: `npm run verify` (typecheck + test + verify:handoff + lint + db status)

Proof: two scripts, each hermetic and repeatable — real CLI, real git in temp
dirs, isolated `KANTHORD_DB`, and the **no-model** fake-agent path (the discard
path is about state transitions, not about what an LLM writes). Both are
copy-paste-runnable from the repo root and self-assert every claim with
`set -euo pipefail`:

```sh
scripts/e2e/discard-proof.sh              # NEW in this epic
scripts/e2e/publish-idempotency-proof.sh  # NEW in this epic
```

Must print, respectively:

```
007.16 PROOF PART 1 OK (discard)
007.16 PROOF PART 2 OK (publish)
```

`discard-proof.sh` builds its graph with `scripts/e2e/make-discard-graph.sh`
(also new in this epic: a root task whose Verification can never pass, plus one
dependent) and asserts:

1. the failed task **explains itself** — `status: failed` and
   `reason: VerificationFailedError…` on `get task` (`B3`);
2. discard from `failed` reaches a terminal state and **cascades** — root and
   dependent both `discarded` (`B5`);
3. `discarded` is **unsuccessful** — objective and initiative both `discarded`,
   and zero `objective.integrated` events were ever appended;
4. `reject objective` exists beside approve/retry (`B6`);
5. `approve objective` on a terminal objective is a **conflict**, not a fake
   success — a single-line `error: …` at a non-zero exit, never
   `objective integrated`, never a stack trace (`B1`);
6. an unknown ref is a **typed one-line error** — `no branch with id
nope/missing`, no `execSync` stack trace (`B8`).

`publish-idempotency-proof.sh` drives the smallest graph that can reach `landed`
(1 initiative → 1 objective → 1 task) and asserts:

7. the first `publish repository` succeeds;
8. a re-publish is an **idempotent success** with the distinct
   `already published @<oid>` message at exit 0 (`B2`);
9. …and appends **no second** `repository.published` event;
10. the event is **attributable** to its repository — a `repositoryId` subject
    (`B7`);
11. the text renderer prints that id instead of `undefined`.

Assertion wording follows the **real program**, deliberately: an unknown ref
renders through `UnknownReferenceError`'s uniform `no <kind> with id <ref>` form
(`src/app/errors.ts:71`) rather than a per-noun special case, and
`publish repository` writes its human line to **stderr** while the OID goes to
stdout (`src/apps/cli/commands/publish/repository.ts:28-37`). Counts are compared
with `test`, not `wc -l | grep -qx`, because BSD `wc` left-pads its output.

## Stories

Ordered so the risky state-machine work sits behind two green slices. Story 1 is
a **design** slice with no production code; Story 5 must not start before it.

1. **Rejection/discard state contract** (design only, no product code) — write the
   full transition table to `.agent/plan/stories/007.16-.../contract.md`: valid
   source states for `reject task --resolution discard` and `reject objective`;
   the cascade rule and its interaction with `readiness()` dependency edges (only
   `completed` satisfies an edge); the resulting objective and initiative status;
   whether discarded work can later be retried; and the new event types. No story
   below may leave any of these to build time.
2. **Failed-task diagnostics** — persist a `task_results` row with `reason` on the
   failure path, and render `reason:` on `get task`, mirroring how `summary:` is
   rendered for `completed`. No `attempts:` line.
3. **Truthful terminal commands** — five distinct acceptance criteria in one
   story: `approve objective` on a non-`awaiting_confirmation` objective throws
   `ObjectiveNotAwaitingConfirmationError`; `publish repository` pre-checks the
   ref and throws `UnknownReferenceError("branch", …)`; `publish repository` on an
   already-published OID prints `already published @<oid>`, exits 0, and appends
   no event; **`import graph --apply` exits non-zero and prints
   `refused: N drifted node(s)` when blocking conflicts prevented every write,
   instead of printing `created:` and exiting 0**; and **a new graph node may
   depend on an existing one by package `ref` on the apply path, not only by
   ULID**. The last two are folded in from
   `.agent/findings/007.17-midway-insertion-findings.md` (`F1`, `F2`) — same
   defect class: a command reporting an outcome it did not achieve, or letting a
   raw error escape as a stack trace.
4. **Event attribution** — add a `repositoryId` subject to the `events` schema and
   emit it on `repository.published`; the text renderer prints the id instead of
   `undefined`. Includes the migration.
5. **Terminal discard path** — implement Story 1's contract: `discarded` task /
   objective / initiative status (widening three SQL `CHECK` constraints), `reject task --resolution discard` accepted from
   `failed`, cascade to the dependent subtree, `reject objective
--resolution retry|discard --reason`, and `scripts/e2e/make-discard-graph.sh`
   for the Proof.
6. **Docs + small surface fixes** — `--note` on `retry objective` (passed to the
   re-queued tasks); correct `list event --help` to describe the
   `{"events":[…],"nextCursor":…}` envelope rather than "newline-delimited JSON";
   fix the three `/e2e` skill-doc drifts (`retry objective --note`, the event page
   default is 5 not ~100, OAuth writes a DB credential row and never
   `~/.kanthord/accounts.json`).
7. **Run-scoped daemon accounting** — LAST, and only after defining "run" in a
   concurrency-safe way: the closing summary counts only initiatives this run
   touched, and reports failures first (`1 task(s) failed: <id> — <reason>`)
   instead of a whole-DB `1 initiative(s) landed` while the run's only task failed.
   If the "run scope" definition cannot be pinned down against retries, recovered
   tasks, and concurrent daemons, this story is cut rather than guessed.

## Non-goals

- A `delivered` initiative status, or rendering per-target publication state on
  `get initiative` (findings `S2`).
- Changing the `list event --json` output _shape_ — the `nextCursor` envelope is
  the better contract; only the help text is wrong.
- **Reclassifying lifecycle-progressed graph nodes.** Story 3 makes
  `import graph --apply` _report_ its refusal honestly; it does **not** change the
  drift classification itself. The root cause — the content sha including live DB
  status, so any task that has run is permanently `drifted`
  (`apply-graph.ts:70-75`, findings `F1`) — needs the three-axis content/lifecycle
  split and belongs to the sequencing/insertion work, not here.
- Strengthening per-task `Verification` commands. The weak `node --check` gates in
  the E2E graph were an _authoring_ choice; the model met the acceptance criteria
  anyway. Verification-command policy is EPIC 009.3's subject.
- Exercising `retry objective` / conflict, daemon-crash recovery, or multi-repo
  initiatives — a separate E2E investigation, deliberately not scoped here.
- Any change to the objective-branch build workflow (007.12), which worked
  correctly with zero sibling conflicts.
