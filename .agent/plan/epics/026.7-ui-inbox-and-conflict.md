# EPIC 026.7 — the decision Inbox (W1) and the conflict screens (W3)

> Authored 2026-07-31. The design went through the debate engine (`pi`,
> read-only). It rejected two of the draft's decisions outright — a per-row name
> fetch, and an Inbox whose rows only link elsewhere — and caught the draft
> claiming a field the conflict DTO does not have. Twelve findings are marked
> **[debate]**. One draft claim was also wrong in the other direction and is
> corrected here: a **paused initiative produces no queue item**.
>
> Execution order: 026 → … → 026.6 → **026.7** → 026.8.
> Normal `/work`: writes only `ui/**` and `scripts/**`, installs nothing
> (EPIC 026 decision 9), adds no API route.

## Goal

The operator opens one cross-project list and sees every decision the daemon is
waiting on, in the server's own order, with the exact CLI command for the ones
the daemon can already name. Conflicts get their own screens: a task conflict
shows the real per-file diff, an objective conflict shows its commit chain. No
screen claims to resolve anything, because no route can — and each says so in
operator language rather than by greying a button.

## Verified facts (measured on this tree, 2026-07-31 — do not re-litigate)

- `GET /api/queue` takes only `?limit` (1–500) and returns
  `{items[], counts {total, byKind}, truncated, warnings[]}`. `counts.total` is
  computed **before** slicing, so it is the true total.
- `DecisionItemView` (`views/queue.ts:11`) has **no id and no title**. It has
  `verdicts[]` (each an `ActionView` with `kind`, `target`, `requiresInput[]`
  and an optional **exact `command`**), `kindLabel`, `cause?`, `projectId`,
  `projectName`, `initiativeId`, `objectiveId?`, `taskId?`, `downstream`,
  `actionableSince`, `evidence {basis, diffAvailable: false, inspect}` and
  `expectedCommit?`.
- **`GetDecisionQueue` already reads task titles and objective/initiative names
  server-side and then discards them** in the DTO. A per-row fetch in the
  browser would be compensating for a projection gap — up to 500 extra requests,
  with an inconsistent snapshot. Naming is `docs/ui-design.md` prerequisite 1.
  **[debate]**
- A queue item exists only when a task is `awaiting_confirmation` or `failed`,
  an objective is `conflict` or `awaiting_confirmation`, or an initiative is
  `landed` with publication `unpublished`/`diverged`
  (`src/domain/actionability.ts:389`). **A paused initiative produces nothing** —
  measured, correcting the draft.
- Order is `downstream` desc, then `actionableSince` asc (null last), then id
  (`src/domain/decision-queue.ts:252`). `downstream` is a **dependent count**,
  not an impact score, and the toolbar must not upgrade it into one. **[debate]**
- `TaskConflictView` (`views/conflict.ts:4`) is `{taskId, branch, targetOID,
candidateOID, files[] {path, hunks}}` — **there is no `inspect` and no action
  metadata on it.** `inspect` lives on _queue_ evidence. The draft claimed
  otherwise. **[debate]**
- `GetConflict` succeeds only for a persisted task-linked candidate already in
  `conflict` state, recomputes the preview, and answers **`409`** when the
  conflict has gone (`http-reads-proof.sh:254` pins `409
no_conflict_candidate`; the objective route pins `409
objective_not_in_conflict`). A conflicted path can also come back with
  **empty `hunks`**. **[debate]**
- `ObjectiveConflictView` has **no files**: oids, `conflictCause`,
  `tipMovedSinceAnchor`, `conflictReason`, `note`, and an `evidence` whose
  `diffAvailable` is a boolean and whose `inspect` may be `null`.
- There is **no approve, reject, retry, abandon or resolve route** in the HTTP
  API. Every response control here is disabled or a CLI handoff.
- A real queue item is reachable **deterministically, with no model and no
  network**: `KANTHORD_FAKE_AGENT` plus `scripts/e2e/make-landing-graph.sh` and
  `run daemon --until-idle` drive a task to `failed` — the recipe
  `scripts/e2e/decision-workbench-proof.sh` already uses.

## Decisions (binding)

1. **The row key is a render key, nothing more.** `projectId|initiativeId|
objectiveId|taskId|kindLabel` keys the list and the selection. It is not
   identity: it moves if `kindLabel` changes, and it cannot support history or
   retrieval. `#/inbox/:itemId` is **unsupported until 026.8**, not forbidden
   forever — and this decision does **not** block entity-keyed conflict routes,
   which have real ids today. **[debate]**
2. **No per-row fetch.** The row renders what the DTO gives: `kindLabel`,
   `projectName`, the target's type and shortened id, `downstream`, and the age
   from `actionableSince`. Rows are honest about being id-labelled until 026.8
   adds names. **[debate]**
3. **The toolbar states the order literally**: "ordered by downstream
   dependents, highest first; then the oldest actionable item; items with no
   actionable time last". No sort control, no filter control, and the capped
   window is disclosed. The words "impact" and "priority" do not appear.
   **[debate]**
4. **Truncation is a banner on a successful table, not a replacement screen** —
   "showing N of `counts.total`" — and `warnings[]` render above the rows as
   degradation notices, with the table still visible. Warnings can carry paths
   and exception text, so the layout handles several long strings. **[debate]**
5. **Selecting a row opens a detail pane built from `verdicts`.** This is the
   Inbox's real value with no mutation routes: each verdict renders its kind and
   target; a verdict carrying a `command` renders a copyable `CommandHandoff`; a
   verdict without one renders disabled and **names the missing inputs** from
   `requiresInput[]`. "Open the task/objective" is a secondary link, not the
   primary behaviour — a queue that only links elsewhere throws away the
   server's action projection. **[debate]**
6. **The Inbox is manual refresh** (binding in `docs/ui-design.md`; `/api/queue`
   has no change signal, so every probe would be a full refetch). Operationally:
   refresh is disabled while in flight; a failed refresh keeps the current rows;
   `FreshnessBar` advances only on success; there is no refetch on focus; and a
   changed total is announced accessibly. **[debate]**
7. **One W3 shell, two typed evidence variants.** The shell owns the layout
   (evidence first, response last), the loading/missing/stale states and the
   response inventory. The task variant renders `files[] {path, hunks}`; the
   objective variant renders the oid chain, `conflictCause`,
   `tipMovedSinceAnchor`, `conflictReason` and `note`. Two separate screens
   would duplicate four states. **[debate]**
8. **The conflict screens are entity-keyed routes**:
   `#/project/:pid/initiative/:iid/objective/:oid/task/:tid/conflict` and
   `…/objective/:oid/conflict`, consistent with 026.3's canonical chain.
9. **`409` is a first-class state, not an error.** "This conflict is no longer
   present" for `no_conflict_candidate` / `objective_not_in_conflict`, with a
   link back to the entity. A conflicted file with **empty `hunks`** renders
   "the conflict body could not be read" and still lists the path. A `null`
   `inspect` or `null` oid renders as absent, never as an empty command box.
   **[debate]**
10. **No fabricated commands.** The task conflict DTO carries none, so the
    response region says plainly that resolution happens through the CLI and
    offers a command **only** when one is available from the queue verdict for
    the same entity. The UI never assembles a git line of its own. **[debate]**

## Verification Gate

Gates: `npm run verify`.

Hermetic coverage required beyond the Proof (Vitest + jsdom, in `ui/`):

- **Row grammar** (decision 2): every rendered field comes from the DTO; no test
  may stub a per-row entity fetch, and a rendering test fails if the component
  issues one.
- **Verdict inventory** (decision 5): a verdict with a `command` renders
  CommandHandoff verbatim; one without renders disabled and lists
  `requiresInput`; an item with an empty `verdicts[]` renders an explicit
  "nothing the daemon can name yet".
- **Truncation and warnings** (decision 4): the table stays visible; the banner
  shows `counts.total`; several long warnings render without breaking layout.
- **Order disclosure** (decision 3): the literal wording is asserted, and the
  words "impact" and "priority" are asserted absent.
- **Conflict variants** (decisions 7, 9): the task variant renders files and
  hunks — **this is where the diff rendering is proven**, because arranging a
  real task-linked conflicted candidate needs an agent run (see the Proof note);
  a file with empty `hunks` renders its path and the unreadable-body message;
  the objective variant renders the oid chain; a `409` renders `conflict-gone`
  for both.
- **Manual refresh** (decision 6), all five behaviours.

Proof: `scripts/e2e/ui-inbox-proof.sh` — deterministic, no model, **no outbound
network**, nothing left running. It drives a **real** queue item through the
production path with `KANTHORD_FAKE_AGENT`:

```bash
scripts/e2e/ui-inbox-proof.sh
```

It must print `026.7 ok: …`. Phases:

- **A** — build the UI; Chromium present, or exit with the install command.
- **B** — the fixture: a project, a local git repository, a registered provider
  whose key is never read, `make-landing-graph.sh` imported, and
  `run daemon --until-idle` with a no-op fake agent, which drives the root task
  to `failed` through the real verification path. Assert the task really is
  `failed` **before** any UI assertion, so a broken fixture cannot be mistaken
  for the defect under test.
- **C** — `GET /api/queue` returns at least one item; the Inbox renders exactly
  `items.length` rows, and the row for that task shows the API's `kindLabel`,
  `projectName` and exact `downstream`.
- **D** — the order statement is rendered and contains neither "impact" nor
  "priority".
- **E** — selecting the row opens the pane and renders one `verdict` per API
  verdict; where the API supplied a `command`, it appears verbatim in a
  CommandHandoff.
- **F** — the task's conflict route renders `conflict-gone`, because this task
  has no conflicted candidate and the API answers `409 no_conflict_candidate` —
  the honest state, proven against the real error.
- **G** — R3 holds: no request the page issued carried an `Authorization`
  header.

**Stated plainly:** the Proof does **not** render a real diff. Producing a
task-linked candidate in `conflict` state needs a runner result, and no public
HTTP or CLI path creates one. The diff rendering is proven hermetically
(decision 7's Gate entry) and this limit is disclosed rather than papered over.

because `ui/` does not exist and `npm run build:ui` is not a script yet.

## Non-goals

- **No approve, reject, retry, abandon or resolve** — no route exists; 026.8.
- **No decision deep link, no resolved/expired history, no filter or sort** —
  items have no id and the route takes only `limit`; 026.8.
- **No entity-name enrichment in rows** — the server must carry it; 026.8.
- **No polling** (decision 6).
- **No fabricated git command** (decision 10).
