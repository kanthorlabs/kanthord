Write the rules of a repository

Write the conventions of one repository once, so that every native agent that works on it reads them. The coder swe@1 follows the rules, and the reviewer re@1 judges the work against the same rules. A violation of a work-product rule is a blocker, so the node goes back to the coder.

The rules live in the repository binding of the project, in the key prompts. KanthorD reads them into the system prompt of each execution. The prompt explains the whole system prompt.

Before you start

  • A project with a repository binding and its base branch. See project bindings.
  • The kanthord CLI with a human token, or the dashboard.
  • The rules of your repository, for example from a code review checklist or an existing AGENTS.md.

1. Decide where each rule goes

The system prompt of an agent holds three prompt layers. An agent reads them from the most general to the most specific, and a later text governs an earlier text.

Layer Name Where you write it Who reads it
1 KanthorD prompt Shipped with KanthorD. An operator can replace a file in agent.prompt.agent_directory on the server host. Every native agent of every project
2 Repository prompt The instruction file that prompts.instruction_file names, then the text prompts.repository Every native agent on the repository
3 Binding prompt prompts.agents[<agent>] One agent on the repository

The full order, from the lowest precedence to the highest, is the reading order: base.md, the Role, workbench.md, the instruction file, the stored Repository prompt, the Binding prompt, and the framing of KanthorD. So the stored Repository prompt can override a rule of the instruction file, and a Binding prompt can override a rule of the Repository prompt for its own agent. No text overrides the framing. The framing states that the worker owns the commit, the branch, the push, the verification and the release.

Put each rule into one place:

The rule Put it into Why
A rule of the work product that the team already keeps in a file of the repository The instruction file The team edits one file, and the base branch versions it.
A rule of the work product that applies only when KanthorD does the work, or a correction of the instruction file prompts.repository It comes after the instruction file, so it governs that file.
A rule that the reviewer judges The instruction file or prompts.repository, never only a Binding prompt The coder and the reviewer read the same layer 2. A rule in the re@1 Binding prompt only reaches the reviewer, so the coder never sees the rule that blocks it.
A relaxation of how the reviewer weighs a rule prompts.agents["re@1"] This is the one judgement statement that layer 3 permits. See Relax a rule for the reviewer.
An extra hint for one agent, for example a note for env@1 about the toolchain of the repository prompts.agents[<agent>] Only that agent reads it.
A secret, a token or a password Nowhere A prompt holds no secret. Every human of the project and each model provider reads a prompt, and KanthorD scans no prompt for a secret.

2. Write each sentence as a rule

A layer 2 or layer 3 text joins the default standard of the agent. The first paragraph of base.md holds these sentences: "This text, the rules of your role, and the repository prompt and the binding prompt of each repository of the work form the default standard. The default standard binds every work product." So the reviewer reads each work-product sentence as a rule. A violation is a blocker, and the node goes back to the coder.

Write each sentence so that a reviewer can decide yes or no. Replace advice with a rule:

Advice (avoid) Rule (write)
Try to keep functions short. A function holds at most 40 lines.
Prefer descriptive names. Write every name outside the code in snake_case.
Tests are nice to have. A test file sits beside its source file.
Consider error handling. Every HTTP handler answers an error with the shared error envelope.

A rule binds the work product: its language, its style, its conventions and its structure. A rule about the method, the tools, the repository operations or the release is no ground for a blocker. The reviewer reports a violation of such a rule with action: no, so it causes no rework. The coder still reads it as guidance.

Sentence Kind What the reviewer does with a violation
Every exported function has a type annotation. Work product A blocker
Run pnpm lint before you commit. Method A suggestion with action: no
Use the GitHub CLI to open a pull request. Repository operation A suggestion with action: no. The worker opens the pull request, not the agent.
Bump the version in package.json at a release. Release A suggestion with action: no

A verification command of a node is the place for a check that a command can run. A rule in a prompt is the place for a convention that a reviewer reads.

3. Choose the instruction file

Name an instruction file when the repository already keeps its rules in a file, for example AGENTS.md. Leave the key absent when the file holds advice or instructions for an interactive tool, because every sentence of the file then binds the work.

  • Name exactly one file. KanthorD has no fallback list, so a repository with only CLAUDE.md names CLAUDE.md.
  • Write a relative path with /, for example docs/agent-rules.md. The path holds no . or .. segment, no empty segment, no backslash and no control character, and at most 255 bytes.
  • Keep the file at most 32768 bytes of UTF-8 text, with LF line ends. A carriage return is a control character, so a file with CRLF line ends is invalid.
  • Put every rule into the named file. To scope a rule to one directory, name the directory in the rule, for example "Every handler in src/api validates its input." KanthorD reads no nested file, for example src/api/AGENTS.md, because it composes the system prompt before the agent opens a directory.
  • Do not rely on an @ import. KanthorD expands no @ import, so a CLAUDE.md that holds only @AGENTS.md gives the text @AGENTS.md. Name AGENTS.md instead.
  • A symbolic link inside the repository works. KanthorD reads the target, so AGENTS.md -> docs/agents.md reads docs/agents.md.
  • KanthorD reads no *.local.md file and no file of a home directory, because no commit holds a personal file.

Commit the file to the base branch. KanthorD reads the file from the base branch, never from the node branch.

4. Set the prompts of the binding

Every key of prompts is optional and absent by default: 

{
  "prompts": {
    "instruction_file": "AGENTS.md",
    "repository": "Write every name outside the code in snake_case. A test file sits beside its source file. Each change adds an entry to CHANGELOG.md.",
    "agents": {
      "re@1": "A missing changelog entry gives a suggestion, not a blocker."
    }
  }
}

repository and each text of agents hold at most 32768 UTF-8 bytes, with no control character other than a tab and a newline. The keys of agents are swe@1, re@1 and env@1.

With the CLI

  1. Export the binding set of the project: 
    kanthord project binding export <project-id> > bindings.json
  2. Add the prompts object to the config of the repository binding in bindings.json.
  3. Check the instruction file before the apply. Write the config of the repository binding into check.json as { "kind": "repository", "config": { ... } }, then run: 
    kanthord project binding check <project-id> --file check.json
    The answer holds instruction_file: { path, commit, state, reason }. Continue when state is present. The state absent also passes the apply, but the agents then read no instruction file until the file exists on the base branch. When the configuration names no instruction file and the base head holds a valid AGENTS.md, the answer holds instruction_file_hint: "AGENTS.md exists at the base head.".
  4. Apply the binding set: 
    kanthord project binding apply <project-id> --file bindings.json

The apply reads the instruction file at the base head. It refuses an invalid file with 400 project.bindings.repository.prompt_invalid and stores nothing. An absent file passes, and the agents read no instruction file until the file exists.

With the dashboard

  1. Open the project, then open the repository binding. The sheet holds the section Prompts.
  2. Write the path into the field Instruction file. Select Verify. The field shows AGENTS.md found at <commit>., an absent state or an invalid state with its reason.
  3. Select the edit button of the row Repository prompt or of a row Binding prompt. Write the text, then select Apply. The dialog button Apply changes the draft of the sheet only and stores nothing. The dialog shows the byte count against the 32768-byte limit.
  4. Select Save binding to store the texts.
  5. Open the edit dialog again and select the tab Preview. It lists the parts that an agent reads, in reading order. Each layer 2 and layer 3 part has the label Default standard. The preview reads the stored binding, so it works only after the first save.

Each save that changes a prompts key stores a new binding revision. A node keeps the texts of the revision that it pins until mission node rebind moves it to the current revision, at its next attempt.

5. Check what each agent reads

Read the system prompt that the next attempt of a node on this binding gets: 

kanthord agent get re@1 --project <project-id> --binding-id <binding-id> --view final

The read takes the instruction file at the current base head. Read the stack that the agent of a node reads now, at the commit that its attempt pins: 

kanthord agent get re@1 --node <node-id>

Without --view final, the answer lists each part with its layer, heading, state and text. A part with the state invalid or unreachable shows a file that the server cannot read. final is then null.

After an execution, rebuild the exact system prompt that it served: 

kanthord agent prompt resolve --execution <execution-id> --agent re@1

Result

  • The system prompt of each native agent on the repository holds the heading Repository prompt of repository <name>, file <path>: and the text of the file, then Repository prompt of repository <name>, set in KanthorD: and the stored text. The agent of a Binding prompt also reads Binding prompt of repository <name>: and its text.
  • For native agents, the coder and the reviewer of one attempt read the instruction file at the same base commit. The worker calls worker.handover once after each claim, before the execution setup, and the first handover of the attempt pins that commit. A rework and a review round stay inside the attempt, so they read the same commit. A change that a human merges into the base branch later reaches the node at its next attempt.
  • The reviewer judges a violation of a work-product rule as a blocker. An unrequested change of the instruction file by the coder is also a blocker, because the instruction file is a gate input.

Relax a rule for the reviewer

A Binding prompt comes after the Repository prompt, so it governs it for its own agent. Use the re@1 Binding prompt to change how the reviewer weighs a rule, not to add a rule: 

{
  "prompts": {
    "repository": "Each change adds an entry to CHANGELOG.md.",
    "agents": {
      "re@1": "A missing changelog entry gives a suggestion, not a blocker."
    }
  }
}

The coder reads the changelog rule and follows it. The reviewer reads the rule and the relaxation, so a missing entry gives a suggestion and no rework.

A claude-code@1 coder

KanthorD sends no prompt text to the external harness claude-code@1. Claude Code loads its own CLAUDE.md files from its working directory, which is the candidate on the node branch. When a project runs claude-code@1 as the coder, add the line @<path>, for example @AGENTS.md, where <path> is the instruction file of the binding, to the CLAUDE.md of the base branch, so the coder reads the instruction file of the binding. When the binding names CLAUDE.md itself, Claude Code loads that file with no import.

  • The claude-code@1 coder reads the file from the node branch, not from a pinned commit. It reads no prompts.repository and no Binding prompt. Put every rule that the reviewer judges into the instruction file.
  • The harness calls no handover, so the first native execution of the attempt, usually the reviewer, pins the base head. The reviewer can thus read a later base commit than the coder.

Troubleshooting

Symptom Cause Fix
The apply answers 400 project.bindings.repository.prompt_invalid with reason: path_invalid The path is absolute, holds a . or .. segment, an empty segment, a backslash or a control character, or is longer than 255 bytes. Write a relative path such as AGENTS.md.
The apply answers prompt_invalid with prompt: "instruction_file" and reason: control_character The file at the base head holds a carriage return or another control character. CRLF line ends cause this. Convert the file to LF line ends, commit it to the base branch and apply again.
The apply answers prompt_invalid with reason: too_large The file or the text is larger than 32768 bytes. Shorten the text. Move the extra rules into another source, for example prompts.repository.
The worker logs agent.prompt.source_invalid and takes no more work The execution setup answered 409 agent.prompt.source_invalid: the instruction file is invalid at the commit that the attempt pins. details.reason names the defect: too_large, not_utf8, unreadable or control_character. A retried setup also answers reason: changed when a stored part, for example a file of the agent directory, changed since the first setup of the execution. A retry of the same attempt reads the same commit. Fix the file on the base branch. A new attempt pins the new base head, for example the attempt that a human unblock opens. Today a refused setup releases no stop, and the worker instance takes no more work. After the fix, restart kanthord serve worker for an instance at the worker placement. For the server or the container placement, restart the server with kanthord serve. See the prompt record.
A running node does not follow a new rule The node pins its binding revision, and the attempt pins the commit of the instruction file. For a prompts change, move the node to the new binding revision with kanthord mission node rebind <mission-id> <binding-id> --node <node-id> --file <path>. See node rebind. A save alone does not move a node. For an instruction file change, no command is necessary. Both changes reach the node at its next attempt. A rework inside the current attempt keeps the old texts.
The reviewer blocks a candidate that edits the instruction file Rule 8 of re@1.md: an unrequested change to a gate input is a blocker. Name the change in the requirement of the node, or change the file outside KanthorD.
The reviewer reports a rule violation with action: no The rule is about the method, the tools, the repository operations or the release. Rewrite the rule as a rule of the work product, or keep it as guidance.
The coder does not follow a rule that the reviewer blocks on The rule stands only in the re@1 Binding prompt. Move the rule into prompts.repository or the instruction file.
The dashboard shows no hint for an existing AGENTS.md The hint shows only when the field is empty and a valid AGENTS.md is present at the base head. An invalid file or a failed read gives no hint. Write AGENTS.md into the field and select Verify to see its state.

For each field and code, see Prompts of the binding reference and Get an agent declaration.
