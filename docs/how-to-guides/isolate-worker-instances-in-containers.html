Isolate worker instances in containers

Run worker instances at the container placement. The server starts one container for each such instance on its own host, with Podman or Docker. It runs the container from the create of the instance until its archive.

At the server placement, an agent command runs as the server user. It can read every credential of the server, master_key and the database. At the container placement, an agent command runs in the container of its instance. It reads no file of the server and cannot signal the server process. Each instance runs in the container kanthord_slot_<name> and keeps its state in its own volume kanthord_slot_<name>. <name> is the instance name.

The server must run as the kanthord binary on the host. A server inside a container cannot start containers, so container is off there. To install the binary, use Run kanthord on a Mac with Tailscale or Run kanthord on a VPS.

Before you start

  • The kanthord server binary, installed and started on the host.
  • One container runtime on the same host, for the user that runs the server:
    • On a Mac: a Podman machine or Docker Desktop.
    • On Linux: rootless Podman 4.1.0 or later. The server refuses a rootful runtime when the server user is not root.
  • The image of the server version. The default is docker.io/kanthorlabs/kanthord:<version>. For a toolchain such as Node.js, follow step 4 of Add a toolchain to the worker image.

Replace each placeholder with your value:

Placeholder Value
<version> The version of the server, for example 28.0.1.
<project-id> The Identity value under Details on the project page, for example project_01M5….
<binding-id> The id of the repository binding that kanthord project binding list <project-id> --kind repository --token '<human token>' prints.
<human token> The token of auth jwt generate.
<name> The name of a container instance, for example coder-box-1. podman ps --filter label=io.kanthord.owner --format '{{.Names}}' prints it after kanthord_slot_.
<execution_id> The identity of an execution, for example execution_01M5….

The commands use Podman. With Docker, write docker in place of podman.

1. Prepare the container runtime

On a Mac with Podman

brew install podman
podman machine init --memory 8192
podman machine start

The default machine holds 2 GiB of memory, and every container shares it. Two or more instances that run npm need 8 GiB. To change an existing machine, stop it first: 

podman machine stop
podman machine set --memory 8192
podman machine start

Start the machine again after each restart of the Mac. While the machine is stopped, the instances do not start. They start by themselves after podman machine start.

On Linux, as a desktop user

Install Podman with the package manager of the distribution, for example sudo apt install podman. Rootless Podman then works with no other step.

Install the binary kanthord-linux-x64 or kanthord-linux-arm64 as step 1 of Run kanthord on a VPS shows. Then run kanthord config init and kanthord serve in a terminal as your user.

On a VPS with the service user

The service user kanthord of Run kanthord on a VPS is a system user. It has no subordinate uid range and no user session, so Podman needs these four steps:

  1. Install Podman and the uid map tools:

    sudo apt install podman uidmap

    Read /etc/subuid and /etc/subgid. Choose a free range of 65536 ids, for example 1000000-1065535. Give that range to the user: 

    sudo usermod --add-subuids 1000000-1065535 --add-subgids 1000000-1065535 kanthord

  2. Write /var/lib/kanthord/.config/containers/containers.conf as the user kanthord. The file replaces the systemd user session that the user lacks: 

    sudo -u kanthord -H mkdir -p /var/lib/kanthord/.config/containers
printf '[engine]\ncgroup_manager = "cgroupfs"\nevents_logger = "file"\n' | sudo -u kanthord -H tee /var/lib/kanthord/.config/containers/containers.conf

  3. Add these lines to the [Service] section of /etc/systemd/system/kanthord.service. XDG_RUNTIME_DIR gives Podman the runtime directory that a user session gives otherwise: 

    RuntimeDirectory=kanthord
RuntimeDirectoryMode=0700
Environment=XDG_RUNTIME_DIR=/run/kanthord
KillMode=mixed

  4. Restart the server:

    sudo systemctl daemon-reload
sudo systemctl restart kanthord

KillMode=mixed sends the stop signal to the server process only. The server then stops each instance itself, and a live execution ends cleanly.

On the VPS, run every podman command of this guide as sudo -u kanthord -H env XDG_RUNTIME_DIR=/run/kanthord podman ….

2. Pull the image

Pull the image as the user that runs the server. The first start of an instance pulls it too, but that pull can take minutes. 

podman pull docker.io/kanthorlabs/kanthord:<version>

On the VPS, run sudo -u kanthord -H env XDG_RUNTIME_DIR=/run/kanthord podman pull docker.io/kanthorlabs/kanthord:<version>.

The server adds its own version as the tag to the name in worker.container_image. The server builds an image from the environment of each repository binding, and copies kanthord and tini from this image into it. A container waits until that environment is ready, then runs the environment image. Put a toolchain into the environment, not into this image. See step 4 of Add a toolchain to the worker image.

3. Check the placement

Open Workers, then the worker, for example coder@1, and select Add instance. Placement shows the Container option on, with the runtime that the server uses, for example "with Podman". When the option is off, it shows the reason. Under runtime_failed, the option stays on and shows the detail, because a create passes and the instance starts after the runtime recovers or a human fixes the host. See Troubleshooting.

4. Add the instances and the worker binding

  1. In the Add instance sheet, enter a Name, for example coder-box-1.
  2. Select the Placement Container.
  3. Select Create instance. Repeat steps 1 to 3 for each execution that runs at once, for example coder-box-2.
  4. In the project, open the Bindings tab. Select Add in the Workers section, or open the existing binding of the worker.
  5. Choose the Worker, for example coder@1.
  6. In Instances, select the container instances. With two repository bindings or more, choose the Environment.
  7. Select Save binding.

The placement belongs to the instance and never changes. To move a binding to containers, list the new container instances and remove the old instances from the binding. Each removed instance finishes its execution first. A container instance serves one live binding at most. A second binding that lists it fails with project.bindings.worker.instance_shared, because one container runs the image of one environment.

The first container of the binding starts its work only after the environment of its repository binding is ready. The first build pulls a devcontainer image, and it can take several minutes. Read the status of each repository binding: 

kanthord project environment list <project-id> --token '<human token>'

Wait until status is ready. Then the Workers page shows each instance with · container. The runtime lists the containers of the server: 

podman ps --filter label=io.kanthord.owner

On the VPS, run sudo -u kanthord -H env XDG_RUNTIME_DIR=/run/kanthord podman ps --filter label=io.kanthord.owner.

Read the files of an instance

The server writes the output of each instance to workers/<name>/stderr.log of its state directory, for example ~/.local/state/kanthord/workers/coder-box-1/stderr.log. On the VPS, the state directory is /var/lib/kanthord/.local/state/kanthord.

The Conversation tab of the trace page of the dashboard shows the session entries of each execution. The pi session files stay in workers/<name>/sessions/ of the state directory. The container mounts that directory, and the instance keeps every execution directory. To list the files of one execution: 

ls ~/.local/state/kanthord/workers/<name>/sessions/execution/<execution_id>

On the VPS, run sudo -u kanthord ls /var/lib/kanthord/.local/state/kanthord/workers/<name>/sessions/execution/<execution_id>.

Limits

  • An instance reaches the network through the default network of the runtime. It cannot reach 127.0.0.1 of the host. A provider, an OAuth endpoint or an S3 endpoint on the host loopback address, for example a local Ollama or MinIO, fails at the container placement. Use instances at the server placement for such a binding.
  • An agent command still reaches the memory of its own instance and every network that the container reaches.
  • An agent command at the server placement on the same server reaches every container of the server through the runtime. Do not mix server instances for untrusted repositories with container instances on one server.
  • The server removes the container, the volume kanthord_slot_<name> and the directory workers/<name>/ at the archive of the instance. A removal of the instance from a binding keeps all three, and the container keeps running with no binding.

Troubleshooting

Symptom Cause and fix
Create instance fails with worker.instance.placement_unavailable The server cannot run containers. error.details.reason names the cause: server_in_container, runtime_absent or runtime_rootful. The reason runtime_failed never refuses a create, because the runtime can recover or a human can fix the host. See the rows below.
The sheet shows "Off. This server runs in a container…", or reason: server_in_container The server runs in a container. Install the binary on the host, or keep the server placement.
The sheet shows "Install Podman or Docker on the server host…", or reason: runtime_absent No podman and no docker is on the PATH of the server. Do step 1, then restart the server.
The sheet shows "Cannot connect to Podman…", or reason: runtime_failed with that text The Podman machine is stopped. Run podman machine start. The instances start by themselves.
The sheet or reason: runtime_failed shows "the subordinate uid range of <user> does not cover the container uid 10001…" The user has no subordinate uid range that covers uid 10001 of the container. Do item 1 of On a VPS with the service user.
The sheet or reason: runtime_failed shows "rootless Docker cannot map the container uid 10001 to the server user. Use rootless Podman or a rootful runtime." The server runs rootless Docker on Linux. Do On Linux, as a desktop user or On a VPS with the service user, then restart the server. The server checks Podman before Docker.
The sheet or reason: runtime_failed shows "podman <version> refuses --userns=auto:uidmapping=. Upgrade Podman to 4.1.0 or later." Rootless Podman is below 4.1.0. Upgrade Podman to 4.1.0 or later, then restart the server.
The sheet or reason: runtime_failed shows "docker client <version> is below 23. Upgrade the Docker client to 23 or later." The Docker client is below 23. Upgrade the Docker client to 23 or later, then restart the server.
The sheet or reason: runtime_failed shows "docker answers no server version. Remove the podman-docker shim, or point docker at a Docker Engine." docker on the PATH of the server is the podman-docker shim. Remove the shim, or point docker at a Docker Engine. Then restart the server.
The sheet shows "… runs as root on this host…", or reason: runtime_rootful The runtime runs as root on this Linux host. Use rootless Podman. A Linux VM runtime other than Docker Desktop, for example Rancher Desktop, gets this refusal too. Use Podman there.
reason: runtime_failed stays while podman machine list shows a running machine The server runs with a custom XDG_CONFIG_HOME or XDG_DATA_HOME. The check runs with the full server environment and loses the Podman machine connection. Remove both variables from the server environment, then restart the server.
An instance never shows on the Workers page Read workers/<name>/stderr.log. A failed pull shows there. Pull the image as the user of the server, then wait for the next start of the instance. The server tries again after a pause of up to 30 s.
On rootless Podman, a container instance does not start while other container instances run, and its stderr.log shows a user namespace error A default subordinate range of 65536 ids runs at most 6 KanthorD containers at the same time. The other --userns=auto containers of the user lower that count. For more instances, raise the range with sudo usermod --add-subuids <range> --add-subgids <range> <user>, then run podman system migrate as the user.
An instance never starts, and environment list shows status: failed The build or the proof of the environment failed. failure holds the class and the last output. Run kanthord project environment show <project-id> <binding-id> --token '<human token>' to read the source and the document. Fix the stored document with kanthord project environment set. Push a fix in the repository to the base branch. The server reads the commit of the base branch every 60 s and runs the environment again at a new commit. To force a run at the same commit, run kanthord project environment rebuild <project-id> <binding-id> --token '<human token>'.
A node fails with a provider or storage error that names 127.0.0.1 or localhost The endpoint is on the host loopback address. See Limits.
On a Mac, nodes fail at random during npm ci The Podman machine has too little memory. Set 8 GiB with the commands of On a Mac with Podman.
