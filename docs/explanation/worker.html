How a worker works

A worker is the part of KanthorD that does the work of a mission. A human writes the work as nodes: what to build, how to judge it, and which commands check it. A worker takes one node, changes the code of a repository with an LLM agent, proves the change with those commands, and reports the result. A second worker then judges the result independently.

This page is the entry point. Read it first. It explains the worker concept from the top down. Two pages go deeper:

  • How the coder@1 worker works: every step of one execution of the worker that writes the code.
  • How the native agent works: how KanthorD builds the LLM agent that the worker drives.

The idea in five sentences

  1. A human imports a mission: a graph of nodes with dependency edges. Each node holds a requirement, a criterion, verification commands and an intent, implement or examine.
  2. The Scheduler gives one node at a time to one worker instance. That grant is a claim, and the work under it is an execution.
  3. The worker coder@1 opens an LLM agent, swe@1, in a git checkout. The agent edits files. The worker code commits after every turn of the agent and runs the verification commands of each task itself.
  4. When every verification of the node passes in a clean clone, the worker pushes a branch, records the head commit as evidence and releases the claim. The node now waits for review.
  5. The worker reviewer@1 checks out that commit in a clean directory, runs every verification again, and asks a read-only agent, re@1, for an assessment. A passing assessment completes the node, or first opens a pull request when the project requires one.

The rest of this page explains each of these sentences.

The words you need

The terms below appear on every worker page. Each term has exactly one meaning.

Term Meaning
Mission All the work of one project, as a graph of nodes.
Node One vertex of the mission. It holds an intent, tags, its bindings and, for an implement node, its tasks.
Intent The kind of work that a node asks for: implement or examine. The intent of the pinned revision selects the form of the method.
implement node A node that changes its repositories through its tasks. It names one or more repository bindings, and the convention is one binding. Most worker activity is on an implement node.
examine node A node that changes no repository. It checks out the base-branch head of each repository binding that it names, reads its direct dependencies and reports its findings.
Task One step of an implement node, with a task_<ulid> identity. A task has a criterion and verifications, but no state. A worker never claims a task alone. An implement node with no task is its own single work unit.
Tags of a node The list of tags that a worker binding needs to claim the node, for example platform.macos.
Tag A fact of the host of a worker binding. The Scheduler admits a node only when the tags of the binding include every tag of the node.
Requirement The text that states what the node must achieve.
Criterion The text that states how to judge the result.
Verification One bash command that checks the result, for example npm test. Exit code 0 is a pass.
Node revision One version of the content of a node. An execution reads the revision that its attempt pins, so a later edit does not change a running execution.
Attempt One try at a node. It holds one or more executions. The first claim opens attempt 1. A human unblock opens the next attempt.
Worker A template that defines how work happens: its method, its agents, the node states that it claims, the intents that it takes and its default budget. coder@1 and reviewer@1 are workers.
Worker binding The project configuration that turns a worker on for one project. It lists the worker instances, the tags, the model of each agent and an optional budget. The count of listed instances is the instance count.
Worker instance One named copy of a worker with one placement. It pulls work and holds at most one execution at a time. To run more work at once, add an instance.
Claim The grant of one node to one instance. It has a fixed deadline, expired_at.
Execution The work under one claim, from the claim to the release. It has an identity, for example execution_01JZ8R2B….
Agent An LLM participant that the worker drives, for example swe@1. swe@1 edits files, and re@1 judges. An agent decides nothing about the node.
Node branch The git branch of an implement node, kanthord/<node_id>. Every execution of the node continues on it.
Evidence A result that an execution records, for example the head commit of the node branch.
Assessment The judgement of the evidence against the criterion: success, criterion-not-met or undetermined.
Outcome The final record of an attempt. A successful outcome completes the node.
Release The end of an execution that returns the node to the Mission Service, with further_work: true or false.
Budget The resource limit of one execution: 200 model turns and 2 hours of wall time by default. A model turn is one reply of the model with the tool calls of that reply.
Stop The reason in a release that the execution ended early, for example { "reason": "budget_end", "code": "turns" }. A stop can carry detail, the cause text. A release with no stop has stop: null.
Revision instruction A message from the worker to the agent that asks for more work on a task, for example after a failed verification or a review. It is not a node revision.

Who does what

A worker is one of several actors. Each actor owns one concern, and no actor does the job of another one.

Actor Owns Does not own
Human The WHAT: the requirement, the criterion and the verifications. Pause, unblock, override. How the work is done.
Mission Service The node states, the attempts, the evidence, the assessments and the outcomes. Which instance does the work.
Scheduler Service The work queue, the claim, its deadline and the execution record. The content of the work.
Worker Service The registration, the heartbeat, the credential handover, the execution setup and the action requests. The node state and the claim.
Worker (the code) The method: the order of the steps, git, the verifications, the decision that a task ends. The node state. It releases or submits an assessment.
Agent swe@1 The file edits, inside one session. Git, the verifications, the release, the budget.
Agent re@1 The judgement of a criterion and the default standard, in a read-only session. Any file edit, any command, the assessment record.
Project Service, custody The bindings, the credentials and the model configuration. The execution.

The most important line is the split between the worker and the agent. The agent can claim that its work is done. The worker does not trust that claim and asks the agent no question. The worker commits the work after every turn of the agent, runs the verification commands itself, and releases only after every verification of the node passes in a clean clone. Only re@1, in the separate execution of reviewer@1, judges a criterion.

The life of an implement node

A node moves through states. Each worker claims only from the states that it declares: coder@1 claims Available, and reviewer@1 claims Waiting and External.Requested. No worker sets a state directly. A worker releases or submits an assessment, and the Mission Service picks the next state from it. The Mission Service makes every move of the diagram, also the moves that no worker causes, for example Pending to Available when the last dependency completes. A claim also needs the match of the Scheduler. The worker declares the intent of the node, and the tags of the binding include every tag of the node.

An examine node moves through the same states. Its coder@1 execution submits a report as produced evidence and pushes no branch. It requires no external action, so a passing assessment completes it.

These facts explain most of the diagram:

  • Two workers, two claims. coder@1 and reviewer@1 never share a claim. The coder does the work and releases. The reviewer judges later in its own execution, from a clean checkout.
  • Further work is normal. One execution does not need to finish the node. When the budget ends, the coder commits a checkpoint, pushes it and releases with further_work: true. The node returns to Available, and the next execution continues on the same node branch.
  • A conflict sends the work back. A pull request that conflicts with the base branch returns the node to Available in the same attempt. coder@1 merges the base at its next start and resolves the conflict.
  • A failed required check sends the work back. A required check of the base branch that fails on the head commit also returns the node to Available in the same attempt. This applies to both landings. coder@1 reads the names of the failed checks as its verdict.
  • The merge comes from outside. After the reviewer opens a pull request, no worker acts until the pull request ends. The Intake Service checks the pull request on the git host. A human starts that check with kanthord mission node check. An Intake inbound of the repository, when one is configured, starts it on an event of the git host. The Mission Service also checks the pull request at the reviewer release. While a required check is pending or a check call fails, it checks again every 60 seconds, at most 60 rounds. With the landing kanthord, it merges the pull request when the required checks pass; see the deferred check. A merge moves the node to External.Success, and the Mission Service then completes it with the passing assessment of the attempt. A closed pull request, or a pull request with a change request, moves the node to External.Failed and then to Blocked.
  • A human closes the loop. A node in Blocked waits for a human. The human reads the reason, edits the node or not, and unblocks it. The unblock opens the next attempt.

Two more states can interrupt any step. A human can pause a node, which sets Paused and stops a running execution within one model turn. The Mission Service also pauses a node that fails too often, as Limits that stop a loop explains. Discarded and Completed are the two final states.

One execution, from pull to release

A native worker instance runs as one kanthord serve worker process, as one worker thread of the server, or as one container on the server host. It talks to the server only through the API. It repeats the same cycle for every execution:

The steps in plain words:

  1. Register. The instance registers with the Worker Service once for each worker binding that it serves, and sends a heartbeat every 60 seconds. A thread or a container of the server starts with the machine identity of its binding. A kanthord serve worker process starts from its instance configuration and receives a client token for each binding that lists the instance.
  2. Pull. The instance asks for work. The Scheduler answers when a node in a declared state is ready and the match admits the node, or answers "no work" after 90 seconds.
  3. Claim. The Scheduler grants the node. The Mission Service opens attempt 1 when the node has no attempt, and pins the node revision. The claim holds a fixed deadline: expired_at is the start time, plus the wall-time budget of the binding, plus scheduler.release_reserve, 10 minutes by default, for the cleanup.
  4. Setup. The process receives the credentials of the execution through the credential handover of the Worker Service. It then reads the execution setup: the worker name, the model configuration, the composed prompt, the prompt templates, the intent, the repository bindings and the budget. The process reads no configuration file of its own.
  5. Method. The process runs the method of its worker: steps for coder@1, evaluation for reviewer@1. Each method holds one form for each intent, and the intent of the pinned revision selects the form. The method opens one agent session and drives it.
  6. Claim check. After each model turn, and before each turn of the agent on a task, the process reads its claim. A claim that is no longer running ends the execution at once as revoked. A revoked execution pushes nothing and releases nothing, because the node is no longer its own.
  7. Report. The method records evidence or an assessment in the Mission Service.
  8. Release. coder@1 releases the claim with further_work and an optional stop, and the Mission Service picks the next node state. reviewer@1 releases only after a success that requires an external action. Its other assessments move the node and end the claim at once, with no release. Either way, the instance is idle again and pulls the next node.

What a worker reports to KanthorD lists each operation of this cycle and the telemetry that the worker writes beside it.

The three workers

Worker Host Method Agent Claims from Job
coder@1 KanthorD (native) steps swe@1 Available Does the tasks of an implement node, or writes the report of an examine node.
reviewer@1 KanthorD (native) evaluation re@1 Waiting, External.Requested Judges the result, then requests the pull request.
claude-code@1 External harness (Claude Code) Its own skill None of KanthorD Available, Waiting, External.Requested Does the work in a third-party agent program.

A native worker runs its agent inside KanthorD on the pi runtime. An external harness runs a third-party agent program, and KanthorD configures none of its agent, prompt or tools. Each of the three workers declares the intents implement and examine. Both kinds use the same claim, evidence and release operations. This page and the two pages below it cover the native workers.

How reviewer@1 judges

reviewer@1 has its own execution. It trusts no result that coder@1 recorded, except the head commit that the evidence names.

  1. It reads the pinned revision and the evidence of the attempt. For an implement node, the evidence names the head commit of each node branch. For an examine node, it also reads the outcome and the evidence of each direct dependency.
  2. It makes a fresh directory. For an implement node, it makes a clean checkout of each commit under checkouts/<binding name>/. For an examine node, it checks out the base-branch head of each repository binding of the node in the same way. It places the produced evidence in evidence/, beside checkouts/ and outside the agent root.
  3. Its code runs the verifications of the node, then the verifications of each task, in order. The first failure stops the run. A command that a signal ends, or that exits with a code from 129 to 192, or that does not spawn, is an infrastructure failure. It runs once more, and a pass on that rerun is a pass. A second infrastructure failure stops the execution with operation_failed and the code worker.verification.infrastructure_failed. Any other failed command runs up to two more times, only to detect a flaky test, unless its limit of 10 minutes ended it. A pass on such a rerun still counts as a failure, and the rationale names the test as flaky. A command that the list holds again copies the result of its first run. The reviewer reads no verification memo, so each rerun runs its command.
  4. It records the results as evidence.
  5. When a command failed, it writes a criterion-not-met assessment at once, with no agent. The rationale names the command and holds the last 4 KiB of its output.
  6. For an implement node, when every command passes, its code runs the affected test run of each checkout. It records the result as the evidence Affected test results when at least one repository declares a command. The verdict failed gives a criterion-not-met assessment at once, with no agent. The rationale holds the failed tests and the last 4 KiB of the output.
  7. When every command passes and no affected test run fails, the agent re@1 judges the evidence against the criterion of the node, each task criterion and the default standard. Its evaluation prompt also holds the affected test results. The prompt asks re@1 to weigh a base_red verdict, each flaky test and each excluded e2e test as facts about the change. It also asks re@1 to judge a change to a file that selects or runs tests against the criterion. re@1 can read files but cannot write a file or run a command. When the repository binding names an instruction file, its system prompt holds that file at the base commit that the attempt pins. Its prompt takes no nested instruction file and no file of the workspace.
  8. It submits the assessment. The assessment itself moves the node: the reviewer does not release, except in one case. A success with no required external action completes the node. A success with a required action, for example a pull request, makes the reviewer request the action through the Intake Service and release. The node then waits in External.Requested until the action ends.

Each assessment of reviewer@1 is one review round of the attempt. The reviewer writes each blocker and each suggestion as a review finding, and the Mission Service records each finding. A criterion-not-met assessment returns the node to coder@1 as a rework, in the same attempt. On an implement node, a success assessment also causes a rework when it holds a finding with action: yes, or when it leaves an open finding of the attempt unfixed. A rework happens only while the attempt holds fewer reworks than the limit and no requested action.

The next coder@1 execution reads the rationale of that assessment and the open findings of the attempt as its verdict. It sends both to swe@1 in one revision turn of the node, and it sends the node to review again only when the head holds new work after the judged commit, when the checkout still holds that commit. The verdict unit explains the rule. A later round of an implement node reviews only the patch since the tested commit of the latest base round. A base round has the result success, holds a reviewer finding or holds a fix-node proposal. The reviewer lists each finding that the patch fixes.

The round after the last permitted rework is the final round. Each round after a requested action is also final. A final round causes no rework. Its findings with action: yes and the open findings of the attempt wait for a human decision. An undetermined assessment, or a criterion-not-met of the final round, moves the node to Blocked.

A criterion-not-met assessment with a cause of the category plan gets no rework. The reviewer gives such a cause, plan.requirement_conflict or plan.criterion_unstated, for a defect of the plan. The assessment moves the node to Blocked at each rework count, with the transition rule plan_defect. The plan belongs to the human, and the execution belongs to KanthorD. The human corrects the plan with kanthord mission node unblock and a change.

A fix-node proposal. An undetermined assessment of an examine node can hold up to 10 fix-node proposals. Each proposal names one defect of a direct implement dependency in dependency_id. A human decides every proposal of the assessment in one decision. Each approved proposal creates an implement node with its one task and records it in created_node_id. Every other open proposal becomes rejected. The examine node then depends on each new node, and the decision unblocks it once into the next attempt.

A chained action. A project can require two actions in order, for example a pull request and then a second action that follows its merge. When the first action reaches its expected end, the node is claimable again in External.Requested. reviewer@1 claims it, requests the next eligible action and releases. This claim performs no evaluation, because a current passing assessment already stands. Today reviewer@1 runs the full evaluation again at this claim. A criterion-not-met there blocks the node, because the attempt already holds a requested action.

When the reviewer fails. A reviewer execution can stop before it has an assessment. It then releases with further_work: true and a stop, and the node returns to Waiting for the next reviewer execution:

Stop Cause
assessment_absent The budget ends before the assessment.
judgement_invalid re@1 gives a second reply with no valid judgement line.
action_unsettled The request of an external action fails or has an uncertain result.
operation_failed Any other failure, for example a failed checkout.

Each of these stops counts toward mission.consecutive_failure_limit. A provider_failed stop of the reviewer follows the same rules as for coder@1.

Limits that stop a loop

Without limits, a node could cycle between the coder and the reviewer forever. Three limits in the server configuration stop that. Each limit counts inside one attempt.

Limit Default Counts At the limit
mission.rework_limit 2 Earlier execution assessments of the attempt: the review round minus 1 With the default, rounds 1 and 2 can cause a rework, and round 3 is final. A criterion-not-met of round 3 moves the node to Blocked. A success of round 3 causes no rework, and its open findings wait for a human. A plan cause moves the node to Blocked at each count. The value 0 turns rework off.
mission.further_work_limit 3 Releases in a row with the stop budget_end, which means that no unit completed The third such release in a row moves the node to Paused.
mission.consecutive_failure_limit 3 Executions in a row, coder or reviewer, that stopped on a failure or lost their claim The third failure in a row moves the node to Paused.

A human resumes a Paused node with kanthord mission node resume, which grants one more try and resets no count. A failure is a lost claim or a release with any stop except budget_end and a busy provider. The failure stops are operation_failed, no_progress, judgement_invalid, report_absent, action_unsettled, assessment_absent and provider_failed with the code bad_request or unauthorized. A stop because the provider is busy (rate_limited, quota_exhausted or unavailable) does not count as a failure. It moves the agent to the next model of its fallback chain instead. How the native agent works explains the fallback chain.

The two counters of an attempt have separate reset rules:

Counter Limit Counts Resets the count Neither counts nor resets
Failures mission.consecutive_failure_limit A lost claim, and a release with a stop other than budget_end An execution that ends before expired_at with no stop or with the stop budget_end: a release with no stop, a budget_end release, and a revoked claim A provider_failed stop with rate_limited, quota_exhausted or unavailable
Stalls mission.further_work_limit A release with the stop budget_end Any other end of an execution: a release with no stop, a release with any other stop, a revoked claim and a lost claim None

A revoked claim, for example after a human pause, is no failure. The Scheduler ends that execution with no stop before expired_at, so it resets both counts.

Rules that hold in every execution

These rules explain most behavior that looks surprising at first.

  • The worker decides, the agent works. The worker code commits, runs the verifications that count, pushes, records evidence and releases. The agent cannot mark a task complete. The worker does not depend on the agent for git: swe@1 has bash, so nothing blocks a git commit by the agent, but gate G folds every agent commit into the worker commit after the turn.
  • Commands before opinions. coder@1 asks no agent for a judgement. re@1 judges a criterion only after every verification of the node passes. A failed command never reaches a judgement.
  • A fresh agent for each execution. Each execution opens a new agent session with an empty conversation. The execution can lose its claim or its process at any time, so nothing durable lives in the agent. The next execution rebuilds its context from the node branch and from the records of the Mission Service.
  • Git is the memory of the work. The node branch carries the work from one execution to the next. A Kanthord-Done trailer on a worker commit marks each unit that passed with a change, so the next execution skips it. A budget end writes a checkpoint commit and pushes it, so no work is lost.
  • No history rewrite. No execution deletes, renames or force-pushes a node branch. No execution rewrites a commit that it pushed, because a record can name that commit.
  • One instance, one execution. An instance holds at most one execution at a time, at every placement, over all the bindings that list it. Capacity comes only from the count of instances. No rank and no weight exist between instances. At the worker placement, one kanthord serve worker process hosts one instance, so a binding that lists 3 such instances needs 3 processes.
  • A lost claim is a failure. A claim that reaches expired_at with no release is lost. The Scheduler ends the execution and returns the node to Available (or Waiting for a reviewer claim). The loss counts toward mission.consecutive_failure_limit. The worker process that still runs learns of the loss at its next call and stops.

Where the state lives

The agent forgets everything at the end of an execution. The next execution reads the state from these places:

State Where it lives Durable
The work: every worker commit and its done records The node branch on the git remote Yes
The node state, the attempt and the pinned revision The Mission Service Yes
The evidence, the assessments and their rationales The Mission Service Yes
The claim, its deadline and the selected model The Scheduler execution record Yes
The cooldown of a busy credential The Agent component on the server, in Custody Yes
The checkout itself workspaces/ on the worker host No, a cache of one host
The agent conversation The Tracking Service, and a pi session file on the worker host Telemetry, never read to decide

The start of coder@1 reads the done records of the node branch, so it needs only the durable rows. The checkout saves a clone and installed dependencies, and its loss repeats no work.

  • Tasks are not scheduled. The Scheduler grants a node. The worker orders and runs the tasks of an implement node inside its own execution.
  • Telemetry decides nothing. The worker writes spans of its phases, tasks, turns and tool calls. No service reads them to move a node. Only the release and the records move a node.

Where a worker runs

Each worker instance holds one placement: server, container or worker. The placement is set at the create of the instance and never changes. A worker binding holds no placement. It lists its instances in worker_instances, and one binding can list instances of different placements.

  • At the server placement, the server runs the instance as a worker thread. A human generates no token and starts no process.
  • At the container placement, the server runs the instance in its own container on the server host, with Podman or Docker. A human generates no token and starts no process. The container waits until the environment of the repository binding of its listing binding is ready, then runs the image of that environment. That image takes kanthord and tini from <worker.container_image>:<server version>. With no listing binding, or in a project with no repository binding, the container runs <worker.container_image>:<server version>. One live worker binding at most lists a container instance, because one container runs one image.
  • At the worker placement, each instance is a separate kanthord serve worker process. The process can run on the server host or on another host.

The server runs each server and container instance from its create until its archive, also while no binding lists it. A create at worker.server_instance_limit (default 16) refuses. The server runs at most that many server and container instances at once. A removal of an instance from a binding drains it for that binding: its live execution finishes, and the binding gets no new claim from that instance.

Every placement runs the same worker unit. A server thread and a container instance reach the server through the same API operations, under a machine identity of the same project and binding scope. The container reaches the server through a channel that the server holds, and it holds no token.

The server checks the placement container with a runtime check. The check answers a reason when the server cannot host containers:

reason Condition
server_in_container The server runs inside a container.
runtime_absent Neither podman nor docker resolves on the PATH of the server.
runtime_failed The runtime does not answer or fails a check. A runtime that does not answer is transient: a stopped Podman machine, Docker ServerErrors, a nonzero info exit, or a Podman answer with no host. A failed check stays until a human changes the host: the uid 10001 cover check, a Docker client below 23, a Docker answer with no server version (the podman-docker shim), rootless Docker on Linux and a Podman below 6.0.0. The pool host retries with a backoff in both cases.
runtime_rootful A Linux host runs a rootful runtime and the server user is not root.

Worker placements lists the answer of the check. Isolate worker instances in containers shows the steps.

To run 3 instances of coder@1 for one project at the server placement:

  1. Enable the agent swe@1 with a provider and a model. See agent enablement.
  2. Add the instances coder-1, coder-2 and coder-3 of coder@1 at the server placement on the worker page, or with kanthord worker instance create coder-1 --worker coder@1 --placement server. See worker instances.
  3. Add a worker binding with "worker": "coder@1" and "worker_instances": ["coder-1", "coder-2", "coder-3"] to the project. See project bindings.

The server starts the 3 threads at their create. To run more work at once, add an instance and list it. To run less, remove an instance from the list: an idle instance stops taking work of the binding at once, and a busy instance finishes its execution first. The instance still runs until its archive. A server restart starts each thread again under the same client identity, and a live registration resumes its running execution.

An archive refuses while a binding lists the instance. Remove the instance from each binding first. An archive with --force also stops the live execution of the instance. The node returns to Available or Waiting, and the revocation counts as no loss and no failure.

To run 3 instances of coder@1 at the container placement, create the instances with --placement container, and list them as above. The server starts the 3 containers, and a server restart starts each container again under the same client identity.

To run 3 instances of coder@1 at the worker placement:

  1. Enable the agent swe@1.
  2. Add 3 instances of coder@1 at the worker placement on the worker page, and start one kanthord serve worker process for each. The host needs bash, git 2.40 or later, and OpenSSH 9.0 or later with ssh, ssh-agent and ssh-add. The binary supplies rg and fd, which the agent tools grep and find call.
  3. Give each instance its own copy of the LLM credential of the agent.
  4. Add the worker binding with the 3 instance names in worker_instances.

Run a worker on another host shows the steps, and worker instances lists the operations.

A worker host needs no SSH key, no SSH configuration and no known_hosts entry. The server keeps each SSH key in custody. For each execution:

  1. For an instance at the server or the container placement, the credential handover carries the SSH key of each repository binding of the node, in the sealed envelope. At the worker placement, the key stays on the server. The instance sends each SSH signature request to the server through the SSH signature relay.
  2. The execution setup carries the pinned host key of each repository address. An address host with no pin refuses the setup with 409 repository.host_key.unpinned, and a host outside the SSH host set with 400 project.bindings.repository.address_invalid. The execution then does not start.
  3. The worker keeps both in memory. Each clone, fetch and push starts a private SSH agent, and ends the agent after the git command. At the server and container placements, the agent loads the key. At the worker placement, the agent relays the signature request. The worker writes no private key file.

The worker host must reach the SSH port of each repository address host. The SSH port is 443 for ssh.github.com, altssh.gitlab.com and altssh.bitbucket.org, and 22 for every other host. See SSH host keys. No binding check proves that path from the worker host. The worker reads no file under ~/.ssh, so a key or an alias in the SSH configuration of the host has no effect. A temporary directory path above 75 bytes makes every SSH operation fail; see the temporary directory limit.

An instance keeps its files in a data directory. A process at the worker placement uses $XDG_DATA_HOME/kanthord/workers/<name>/ of its host, by default ~/.local/share/kanthord/workers/<name>/. <name> is the instance name. A thread at the server placement uses state/kanthord/ under its slot root, workers/<name>/ of the state directory of the server. A container at the container placement uses state/kanthord/ of its volume, which carries the instance name. The container mounts sessions/ of its slot root, workers/<name>/sessions/ of the state directory of the server, as pi/sessions/. The archive of the instance removes the volume and the slot root. Two instances share no file.

Path Content
workspaces/<node_id>/ The workspace of one implement node: checkouts/<binding name>/ for each repository binding, and release/ for the clean clones of the release gate during a run. The next execution of the node on this host reuses it. The instance removes it 7 days after its last use.
workspaces/<execution_id>/ The fresh directory of one evaluation execution or one examine execution. It holds checkouts/<binding name>/ for each checkout and evidence/ for the placed evidence. The instance removes it at the end.
pi/ The private directory of the pi runtime. It is separate from any pi installation of the user. pi/sessions/execution/<execution_id>/ holds the pi session files of one execution. The instance keeps every execution directory.

The agent root is the directory that the agent works from. A node with no repository binding uses the workspace as the agent root. A node with one repository binding uses its checkout as the agent root. A node with two or more repository bindings uses checkouts/ as the agent root.

The head commit of an implement node with two or more repository bindings is the set of the heads of its node branches. Each required external action resolves on its own.

The workspace and the pi session files are local conveniences, not records. The worker sends every session entry to the Tracking Service when the agent appends it. Another instance can take the next execution of the same node. It then clones the repository and checks out the pushed node branch.

The agent tools and the verification commands run with the rights of the worker process. At the server placement, those rights are the rights of the server user. A command can read the files of that user and can signal the server process. At the container placement, a command runs in the container of its instance. It reads no file of the server and cannot signal the server process. It still reaches every network that the container reaches. KanthorD has no other sandbox. Run a worker on a host that you trust with the repository and its credentials.
