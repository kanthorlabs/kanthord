How the native agent works

A native agent is an LLM agent that KanthorD runs inside its own process. A worker drives it: the worker sends it a task, and the agent edits files with its tools. reviewer@1 and an examine execution read the last reply of the agent. An external harness, for example claude-code@1, runs a third-party agent program instead.

Read How a worker works first. That page explains where the agent sits in an execution. This page explains how KanthorD builds the agent, what the agent can see and do, and where its limits are.

KanthorD does not implement the agent loop itself. It embeds pi (@earendil-works/pi-coding-agent 1.1.0) as the runtime. pi supplies the loop, the built-in tools, the session file and the resume. KanthorD supplies the configuration, the credentials, the prompt, the tool set and the budget. KanthorD builds only what pi does not serve.

In short

  • Four agents exist: swe@1 writes code, re@1 reviews code with read-only tools, pe@1 repairs the environment of a repository binding, and ops@1 (Yumi) reports and changes the state of projects and missions through operation tools.
  • A human picks the provider, the model and the reasoning effort of each agent. The agent itself holds none of these values.
  • When a provider is busy, the next execution uses the next model of a fallback chain.
  • A human controls three prompt layers: the KanthorD prompt, the Repository prompt of each repository and the Binding prompt of each agent on a repository. KanthorD composes them into the system prompt, and the task comes last.
  • The tool set, not the prompt, limits what an agent can do. A tool outside the set does not exist for the agent.
  • In a worker execution, the agent has a budget of 200 model turns and 2 hours. pi persists its conversation to a session file, and the Tracking Service holds its entries.

The agents

The agent catalog is static and holds four declarations. An agent name names a role, not a worker. Each declaration also holds a display name that a human uses in a mention: SWE, RE, PE and Yumi.

Agent Role Built-in tools Host tools Operation tools Used by
swe@1 Software engineer read, edit, write, grep, find, ls, bash evidence-upload 6 node-review reads Worker coder@1, the Workbench
re@1 Reviewer read, grep, find, ls none 6 node-review reads Worker reviewer@1, the Workbench
pe@1 Platform engineer read, grep, find, ls none none The environment run of the Project Service
ops@1 (Yumi) Operations assistant none none 36 tools The Workbench

re@1 has no tool that writes a file or runs a command. Its prompt also forbids a change to the repository. The tool set enforces that rule; the prompt only states it.

Each declaration holds a shipped Role text and its tool set. A declaration holds no provider, no model and no reasoning effort. A human selects those values.

Two consumers

The Agent component belongs to no service. A consumer opens an agent session for its own purpose, under its own authority:

  • Worker execution. A Worker execution of coder@1 or reviewer@1 opens a session to do or to judge the work of one node. No human is present during the run.
  • Workbench session. A human opens a session from the dashboard and talks to the agent. The agent can call KanthorD operations for the human.

Both consumers use the same open path. They differ in these points:

Point Worker execution Workbench session
Working directory The workspace of the execution ~/.local/state/kanthord/workbench/<agent_name>
Last pinned message The work prompt of the task or the node None
Extra tools evidence-upload for swe@1 Only the operation tools that the declaration of the agent lists
Approval of a change None, because no human is present The human approves each operation that changes state
Budget 200 model turns and 2 hours None
Conversation storage A pi session file of the execution, and the session entries of its trace A pi session file that survives a restart

Configuration: which model answers

An agent is usable only when a human enables it. The agent enablement is global to the server and keyed by agent name. It holds:

  • One or more agent providers. Each one pairs a provider platform, for example anthropic or openai-compatible, with one credential.
  • One default configuration: an agent provider, a model identifier and a reasoning effort.
  • A fallback list: up to 7 more configurations, tried in order when a provider is busy. An empty list means no fallback.

A consumer can supply an entry that overrides any of these fields. A Worker execution takes the entry from its worker binding. A Workbench session takes the values that the human picked. The Agent component merges the entry over the default and validates the whole result:

  • The agent provider exists in the enablement.
  • Custody accepts the credential for the platform.
  • The model belongs to the built-in model list of the platform. For openai-compatible, the model belongs to the approved models of the credential.
  • The reasoning effort is one of the levels that the model supports.

The result is the effective configuration. The same check runs at enablement write, at worker binding write and at resolution. A configuration that passes once can therefore fail later only when a human changes the enablement or the credential. An enablement change that breaks a worker binding is refused, so that case does not occur in practice. Disablement is the only stop switch: it refuses every later resolution.

The fallback chain

The effective configuration is the head of a fallback chain. The fallback list is its tail. A worker binding entry that names its own fallback list replaces the list of the enablement whole; the two lists never merge.

  1. At each claim, the Scheduler picks the first chain entry whose credential has no live cooldown. The execution record pins the chain position and the enablement revision of that entry, and the execution uses that selection until it ends.
  2. A worker execution that stops with provider_failed and the code rate_limited, quota_exhausted or unavailable puts the credential of its selection into a cooldown. The cooldown covers every model of that credential.
  3. The next claim skips every entry of a cooling credential. When the cooldown ends, the next claim returns to the earlier entry.
  4. A repeated failure on the same credential doubles the cooldown, up to one day. A release with no provider failure clears it, whatever model the execution used.
  5. When the credential of every entry cools down, the work pull answers "no work". No node blocks or pauses.

A busy provider therefore does not count as a failure of the node. The codes bad_request and unauthorized do not advance the chain: they point to a broken configuration, and they count toward the failure limit of the node. The Cooldown section of the LLM credential page in the dashboard shows the cooldown of that credential: its strike and its end time. The Details tab of an Available node names each agent of the project whose every chain credential cools down, with the end time. kanthord agent cooldown list shows the cooldowns, and kanthord agent cooldown clear <credential> clears one. The design adds a cooldown badge and a Clear action to the agent page. Until then, use the CLI to clear a cooldown.

Model runtime

The LLM component turns the effective configuration into a pi ModelRuntime and one model:

  • The runtime reads secrets through a credential store that custody hands over for this one session. The agent never sees the secret as a value.
  • The runtime makes no network call to refresh model lists (allowModelNetwork: false). The model must already be known.
  • For openai-compatible, KanthorD registers a provider from the credential metadata: its base URL, its models and the reasoning levels of each model. These models use the OpenAI Responses API and report zero cost.
  • Some platforms need extra values, for example AWS_REGION for Amazon Bedrock. KanthorD takes these values from the credential metadata, not from the server environment.

The runtime refuses the setup when the credential does not match the configuration or when the model or the effort is unknown. The refusal reasons are credential_absent, credential_revision_mismatch, model_unknown and reasoning_effort_unsupported.

Isolation from the host pi installation

The host can have its own pi installation with extensions, skills and settings. The native agent ignores all of them:

  • pi runs with its own agent directory, through PI_CODING_AGENT_DIR. On the server, the directory is ~/.local/state/kanthord/pi. A worker instance at the worker placement uses pi/ of its data directory, $XDG_DATA_HOME/kanthord/workers/<name>/pi/, by default ~/.local/share/kanthord/workers/<name>/pi/.
  • pi runs offline (PI_OFFLINE=1), with telemetry and analytics off.
  • The session loads no extension, no skill, no prompt template, no theme and no context file. KanthorD supplies the system prompt and its own hooks only.
  • The system prompt shows the working directory relative to the home directory, for example ~/work/repo, not the absolute path.

The prompt

What the model reads

Start with the result. A worker execution of swe@1 on a node with one repository binding app sends the model this sequence of messages. The binding names the instruction file AGENTS.md, a Repository prompt and a Binding prompt of swe@1: 

[system]
…the text of base.md…

…the text of swe@1.md…

Repository prompt of repository app, file AGENTS.md:

…the text of AGENTS.md at the base commit that the attempt pins…

Repository prompt of repository app, set in KanthorD:

…the text of prompts.repository of the binding…

Binding prompt of repository app:

…the text of prompts.agents["swe@1"] of the binding…

…the framing…

[user]
…the task…

The system prompt holds three prompt layers, read from the most general text to the most specific text. A fixed paragraph, the framing, closes the system prompt. The framing states the precedence and the protocol of the worker. The task comes last, as a message.

The server writes a heading line before each layer 2 and layer 3 text, so the model sees which repository and which source each rule comes from. A layer 1 text and the framing have no heading. A blank line separates two parts.

The same order, as a table:

# Part Layer Worker execution Workbench session
1 standard 1 base.md base.md
2 role 1 <agent>.md <agent>.md
3 workbench 1 None workbench.md
4 instruction_file 2 The file that prompts.instruction_file of the binding names, when the file exists None
5 repository 2 The nonblank text of prompts.repository of the binding None
6 binding 3 The nonblank text of prompts.agents[<agent>] of the binding None
7 framing None framing-worker.md framing-workbench.md
8 Pinned message None Work prompt None
9 Conversation None Later instructions and replies Human messages and replies

Rows 1 to 7 form the system prompt. Rows 4, 5 and 6 repeat for each repository binding of the node, in the order of the repository bindings of the node revision. So the rules of one repository stay together in one block. A row with no text adds no part.

The work prompt is the task message of a Worker execution: the name, the requirement, the criterion and the verification commands of one pinned node revision. For an implement node, it also holds the section ## Affected tests. That section lists the affected test command of each repository with a valid declaration. The model receives it once, at row 8. Row 9 holds what comes after it: the revision instructions, the judgement instructions of reviewer@1 and the replies of the agent.

The agent pe@1 repairs a failed environment of a repository binding on the server. Its system prompt holds base.md, pe@1.md, layers 2 and 3 of its own binding and the worker framing. It reads the instruction file at the commit of its environment run. Its first message holds the failure. It has no Workbench session.

The three prompt layers

A human controls the prompt of a native agent through three layers. The framing and the prompt templates belong to the KanthorD protocol. They are no layer.

Layer Name Who reads it Sources, in reading order Owner
1 KanthorD prompt Every native agent The files base.md, <agent_name>.md and workbench.md The server host
2 Repository prompt Every native agent that works on the repository The instruction file that prompts.instruction_file names, then the stored text prompts.repository The repository binding of the project
3 Binding prompt One agent on the repository prompts.agents[<agent_name>], one text for each of swe@1, re@1 and pe@1 The repository binding of the project

KanthorD prompt (layer 1). Each file has a shipped text that is embedded in the binary. An upgrade replaces it together with the code that depends on it.

  • base.md is the Standard. Every agent reads it. It holds only the rules that every agent shares, so it holds no code rule.
  • The code and test rules stand in both swe@1.md and re@1.md, in the same words, because re@1 judges the work of swe@1. The finding rule differs, because re@1 writes its findings only in the judgement line.
  • <agent_name>.md is the Role, for example swe@1.md.
  • workbench.md is the Workbench behavior. Only a Workbench session reads it, and it is part of the system prompt.

A file of the same name in the directory agent.prompt.agent_directory replaces the shipped text of that file whole. The default directory is agents in the data directory of the server host, and an empty value selects the shipped texts only. The subdirectory prompts of the agent directory holds replacements of the shipped prompt templates, for example prompts/framing-worker.md. The worker process reads no prompt file. The server reads the files and sends the composed text.

Repository prompt (layer 2). The Repository prompt has two sources, and the server reads both, in this order:

  1. The instruction file: one file of the repository that prompts.instruction_file names, for example AGENTS.md, CLAUDE.md or docs/agent-rules.md. The key is absent by default, so KanthorD reads no repository file until a human names one.
  2. The stored text prompts.repository of the binding. It comes later, so it governs the instruction file.

The server reads the instruction file from the base branch, at the commit that the attempt pins. It never reads the file from the node branch, because the node branch holds the work of the candidate. The attempt prompt pin explains the commit.

  • An absent file adds no part. A path that names a directory, or a symbolic link that points outside the tree, also counts as an absent file.
  • The server follows a symbolic link inside the tree. So AGENTS.md -> docs/agents.md reads docs/agents.md.
  • A file that is larger than 32768 bytes, is not UTF-8, cannot be read or holds a control character other than a tab and a newline is invalid. A carriage return is a control character, so a file with CRLF line ends is invalid. An invalid file refuses the execution setup with 409 agent.prompt.source_invalid. A human fixes the file on the base branch.
  • KanthorD reads no nested per-directory file, no *.local.md file and no file of a home directory, and it expands no @ import. The reason: KanthorD composes the system prompt once per execution, before the agent opens a directory, and no commit holds a personal file. So no reference can pin such a file.

Binding prompt (layer 3). A human sets prompts.agents in the configuration of a repository binding, for example { "re@1": "A missing changelog entry gives a suggestion, not a blocker." }. Each key is the name of an agent of the catalog, and each text is optional. Only that agent reads the text.

A missing key, an empty text and a blank text add no part, for prompts.repository and for each text of prompts.agents. Every native agent of a node reads layers 2 and 3 of every repository binding of the node, at the binding revision that the node pins.

For native agents, the coder swe@1 and the reviewer re@1 read the same layer 2. Only the Role and layer 3 differ. So a rule that the reviewer judges goes into the Repository prompt, and the coder reads it too. A Binding prompt of re@1 holds only a relaxation of the judgement, for example the changelog text above.

claude-code@1 receives no KanthorD text: no layer, no framing. Claude Code loads its own CLAUDE.md files from its working directory, which is the candidate. A claude-code@1 coder thus reads the instruction file only through the CLAUDE.md of the candidate, and it reads no pinned commit.

The default standard

The first paragraph of base.md holds these sentences: "This text, the rules of your role, and the repository prompt and the binding prompt of each repository of the work form the default standard. The default standard binds every work product." So layers 2 and 3 are rules, not advice.

  • The reviewer judges against its own stack: base.md, the re@1 Role, the Repository prompt and the re@1 Binding prompt. The swe@1 Binding prompt is not part of it.
  • A finding that violates a rule about the work product, for example its language, its style, its conventions or its structure, is a blocker. The blocker names the default standard.
  • A rule about the method, the tools, the repository operations or the release is no ground for a blocker. The reviewer gives a finding on such a rule action: no, so it causes no rework. The coder still reads the rule as guidance. The framing states that the worker owns the commit, the branch, the push, the verification and the release.
  • Each instruction file is a gate input. Rule 8 of re@1.md makes an unrequested change to it a blocker. So a candidate cannot change the rules that the next attempt reads.

Write the rules of a repository shows how to write rules that fit this standard.

The attempt prompt pin

The coder and the reviewer of one attempt read the same instruction file text, also when a human merges a new AGENTS.md into the base branch between the two executions. The attempt prompt pin makes this true:

  1. The first worker.handover of an attempt reads the head commit of the base branch of each repository binding that names an instruction file. It reads all bindings in parallel, in at most 20 seconds.
  2. It writes the list of { binding_id, commit } into mission_attempt.prompt_commits, only when the stored value is null. It then reads the stored value back, so two concurrent handovers use one value.
  3. Each execution setup of the attempt reads the file at the pinned commit: the coder, the reviewer, each rework and each review round. A later handover of the attempt reads no head.
  4. A new attempt pins the base head again.
  • A rebind applies at the next attempt, so every layer 2 and layer 3 source moves at one boundary.
  • A base refresh can merge a newer AGENTS.md into the node branch. The framing states that an instruction file in the workspace is work product and no instruction.
  • An external harness calls no handover. When claude-code@1 is the coder, the first native handover, usually the reviewer, writes the pin at that later base head.
  • A setup that finds no pin entry for a binding that names an instruction file answers 409 worker.execution.prompt_not_pinned.
  • A failed head read answers 422 project.bindings.repository.ssh_unreachable, or 422 project.bindings.repository.base_branch_absent when the remote does not hold the base branch. A force-push that removes a pinned commit makes a later git read of that commit fail with ssh_unreachable, and that execution setup is refused. A file that the server still caches at that commit reads no git.

Layer 1 has no pin. A change of a file in the agent directory takes effect at the next composition. A refused setup releases a stop with the setup code, and the worker pulls the next work. When the release fails, the pull loop ends.

Precedence

Two rules decide which text wins a conflict:

  1. The system prompt outranks every message after it.
  2. A later text wins over an earlier text, inside the system prompt and among the messages.

The precedence inside the system prompt, from highest to lowest, is: the framing, the Binding prompt, the stored Repository prompt, the instruction file, workbench.md, the Role and the Standard. Then come the messages: a later message governs an earlier one.

  • A Binding prompt can relax a rule of the Repository prompt, for its own agent only.
  • A Repository prompt can relax a rule of base.md or of the Role. It cannot revoke an obligation of the framing.

An instruction of one repository governs only the work on the files of that repository. It never governs the reply format that a message demands. The reason is that a layer 2 or layer 3 text belongs to a repository, and a message belongs to the consumer that drives the agent.

No prompt authorizes an operation: the tool set and the authority of the consumer decide what the agent can do.

Where the prompt is composed

The server composes the whole system prompt for every consumer:

  • A Worker execution receives it in its execution setup as prompt: { final, sources }. final is the text, and sources lists the prompt reference of each part. The worker application reads no prompt file. It pins only the work prompt.
  • A Workbench session and a pe@1 run take it from the server process.

The setup reads the instruction file of each binding in parallel, under one deadline of 20 seconds. The server caches each file by the repository, the commit and the path. A cache hit reads no git, and a commit never changes, so an entry never goes stale.

An invalid file is a refusal, not a fallback. A file in the agent directory that is not a regular UTF-8 file, that is larger than 32 KiB, or that holds a control character other than a tab and a newline answers 409 agent.prompt.template_invalid, and details.file names the file. Every reader refuses in this way: agent.get, the execution setup, the Workbench session open and the pe@1 run. A reader never replaces the invalid file with the shipped text, because that would run an agent with other rules than the rules that the operator wrote. The same limits apply to prompts.repository and to each text of prompts.agents, and a violation answers 400 project.bindings.repository.prompt_invalid at the binding write.

The prompt record

KanthorD stores no copy of a prompt text. It stores a prompt reference for each part, and it resolves the reference to the text when a human asks for it. A prompt reference holds part, name, origin, path, binding_id, commit and digest, the SHA-256 hex digest of the exact text.

origin Parts The reference resolves from
binary Layer 1 and the framing, shipped text The current binary
file Layer 1 and the framing, override file The current file of the agent directory
database repository, binding The binding revision binding_id. A binding revision never changes.
repository instruction_file The file path at commit, read from git with the SSH access of the binding
  • The execution setup writes one agent.prompt span for each agent. The span holds kanthord.prompt.sources, the reference list in reading order, and kanthord.engine.version. It holds no text.
  • The span write is part of the setup. A failed write refuses the setup with 503 worker.execution.prompt_record_failed.
  • The first span of an execution and an agent wins. A retried setup answers the text of the stored references. When a stored part no longer resolves, for example after an edit in the agent directory, the retried setup answers 409 agent.prompt.source_invalid with reason: changed. A retry never answers a text that differs from the record.
  • The session entry kanthord.pinned_context holds only { part: "system_prompt" }. It holds no text, so the entry cut of the Tracking Service never removes a part of the system prompt.

kanthord agent prompt resolve --execution <id> --agent <name> reads the span, resolves each reference and checks each digest. A part whose text has another digest now answers the state changed and no text. A deploy that edits a shipped text thus turns every older trace into changed for that part, with final: null. The answer holds engine_version, so a human reads the old shipped text from the release tag v<engine_version>. Resolve the prompt of an execution gives the command.

After a refused execution setup, the worker releases the execution with a stop, the same as for worker.execution.credential_not_pinned. The stop holds the reason operation_failed and the setup code, and the worker pulls the next work. When the release fails, the pull loop ends. A gateway. refusal other than an execution end releases no stop and ends the pull loop.

Why the work prompt is pinned

The work prompt is pinned. Before each model call, a pi context hook inserts it as a message directly after the system prompt. A second guard on the stream function re-inserts the system prompt and the work prompt when a request lacks them.

Pinning has two effects. A pinned text survives when pi compacts a long conversation, because KanthorD inserts it again on each call. The work prompt can also change between tasks without a new session: each prompt or instruct call sets the current work, and the next model call carries it.

What a change of a prompt does

  • A change of an agent file takes effect at the next composition. A running execution keeps the system prompt of its setup.
  • A change of a prompts key is a change of the binding configuration. It stores the next binding revision. A node keeps the texts of the binding revision that it pins. Run mission node rebind to move the node to the current revision. The move applies at the next attempt.
  • A change of the instruction file on the base branch reaches a node at its next attempt, because the attempt pins the commit.
  • Environment onboarding treats the new binding ID of the revision as a changed binding. It clears environment_from_agent, the mark that a stored environment came from a session of pe@1.
  • A deploy upgrades the server and every worker host together, because they run the same execution setup contract.

Reading the composed prompt

agent.get answers every part of the system prompt, plus the final prompt. Each part holds its prompt reference and layer, heading, state and text. state is resolved, or invalid or unreachable for an instruction file that the server cannot read. A failed read is a part state, and the read answers 200. final is null when a part is not resolved.

  • kanthord agent get swe@1 answers the stack with no binding. --view final answers the final prompt only.
  • --project <project-id> --binding-id <binding-id> adds layers 2 and 3 of one binding, with the instruction file at the current base head, as the next attempt reads it.
  • --node <node-id> [--attempt <k>] answers the stack that the next execution of the attempt reads, with the instruction file at the commit that the attempt pins. To see what a past execution served, use kanthord agent prompt resolve. Without --attempt, the read takes the open attempt, else the latest attempt.

The dashboard shows layer 1 on the agent page as the card KanthorD prompt (layer 1). The binding sheet shows layers 2 and 3 in the section Prompts. Its Preview tab lists the parts in reading order and labels each layer 2 and layer 3 part Default standard.

Tools

The agent receives only the tools of its declaration. A tool outside the allowlist does not exist for the agent.

  • Built-in tools are the pi tools read, edit, write, grep, find, ls and bash. They act on the working directory. grep and find run rg and fd. The worker and the server install pinned copies into bin/ of the pi agent directory at startup and never take them from PATH.
  • bash runs commands on the host, as the user of the KanthorD process. KanthorD removes every provider API key, SSH_AUTH_SOCK and SSH_AGENT_PID from the environment of each command, so a command cannot read the credentials of the agent or reach an SSH agent of the host user. During a network git operation of KanthorD on the same host, a command can still sign through the SSH agent socket of that operation, because it runs as the same user. In a Worker execution, the timeout of each command is capped at the remaining budget and at 10 minutes.
  • evidence-upload (swe@1 in a Worker execution) uploads a workspace file as evidence of the attempt and returns its evidence_id, asset_id and uri.
  • Operation tools (Workbench only) expose KanthorD operations. Each call runs with the identity of the human who sent the last message. The operation tool reference lists every tool.

An operation becomes a tool when it meets all of these conditions:

  • Its access is human. A worker or machine operation is never a tool.
  • It is not a stream.
  • It handles no secret. An operation whose answer holds a presigned URL is secret material.
  • The declaration of the agent lists its id.

The tool name is the operation id with each . replaced by --, for example mission--node--create.

The agent cannot call these 16 human operations. Fifteen of them handle a secret. repository.host_key.pin confirms the trust of an SSH host, and only a human confirms a host key.

  • llm.credential.create, llm.credential.rotate, llm.credential.check, llm.credential.login_code
  • repository.credential.create, repository.credential.rotate, repository.credential.check, repository.credential.ssh_key_create, repository.credential.ssh_key_rotate, repository.host_key.pin
  • storage.credential.create, storage.credential.rotate, storage.credential.check
  • intake.inbound.get, intake.storage.get, mission.evidence.asset.content.get

The agent therefore cannot create a credential, change a secret, pin a host key, or finish an OAuth login. A human does that in the dashboard or the CLI.

The declaration of each agent lists its operation tools. swe@1 and re@1 hold the same 6 node-review reads: mission.node.get, mission.attempt.list, mission.outcome.list, mission.assessment.list, mission.evidence.list and mission.evidence.get. They read evidence metadata only. pe@1 lists no operation, so it has no Workbench session. ops@1 holds 36 tools by damage class:

Damage gates and duty selects. An operation of class R3 (loss or setup), C (control) or S (secret) is never a tool. A read is a tool when an operations duty needs it. An R1 or R2 mutation is a tool when an operations duty acts with it. A human changes no list.

A Workbench operation tool that changes state waits for the human. The dashboard shows the pending call, and the human approves or rejects it. A rejection, an abort or the end of the run counts as a rejection. A read operation and a built-in tool run without approval. A Worker execution has no approval step, because no human is present.

A session inside a Worker execution

A Worker execution opens one session per claim, in a workspace that the worker prepares. The worker method then drives the session with two calls:

  • prompt(work) sends the work prompt as the user message.
  • instruct(work, text) pins the work prompt and sends another instruction, for example a revision request.

The worker, not the agent, decides when the work is done. Only reviewer@1 asks its agent for a decision: a judgement of a criterion. That instruction asks for one last line that starts with kanthord-judgement: and holds JSON. A reply that does not parse gets one repair turn. A second invalid reply ends the execution with judgement_invalid. coder@1 reads no reply of swe@1 in an implement execution, and reads the last reply of an examine execution as the report.

Each method uses the session in its own way:

  • Steps (coder@1 with swe@1). The agent works on each unit of the node. After each turn, the worker commits the change and verifies the unit itself. How the coder@1 worker works shows the loop.
  • Evaluation (reviewer@1 with re@1). The worker runs the verification commands first. A failure ends the evaluation without the agent. On success, the agent receives the evidence and returns a JSON judgement.
  • Examine (coder@1 with swe@1). The agent checks out the base-branch head of each repository binding of the node. It runs tools and the verifications, and reads the outcome and the evidence of each direct dependency. It writes its findings as produced evidence.

Budget

Each native worker has a resource budget of 200 model turns and 2 hours of wall time. A worker binding can override both values. One model turn is one reply of the model with the tool calls of that reply. The wall time counts from the claim, and the wall deadline is also capped by the expiry of the claim. When the budget ends:

  • pi stops after the current turn, and KanthorD aborts the session.
  • Each later bash command is refused.
  • The worker method stops and releases or ends the execution.

A cancellation of the execution, for example a revoked claim or a server shutdown, also aborts the session.

A session inside the Workbench

A Workbench session is a conversation between one human and one agent, stored as a pi JSONL session file:

  • The working directory is ~/.local/state/kanthord/workbench/<agent_name>.
  • The session files live under ~/.local/state/kanthord/pi/sessions/workbench/<agent_name>.
  • The session identity that KanthorD assigns is also the pi session id.

KanthorD keeps no copy of the conversation. The session list, the history and the resume all come from pi. When the server restarts, KanthorD reopens the file by its session id; every completed turn is restored, and a turn that was running at the restart is lost. The session also answers a pi --session <file> command, so a human can continue the same conversation in a terminal.

The human can change the agent provider, the model and the reasoning effort between runs. KanthorD writes each change into the session file as a pi entry, so the file records which model answered which turn.

Limitations

  • No resume of a conversation. A Worker execution persists its pi session to a file, but it never opens that file again. When the worker process ends, a resumed execution starts a new session.
  • Transcript in the Tracking Service. pi persists each session entry to pi/sessions/execution/<execution_id>/ of the data directory of the instance. The instance keeps every execution directory. The worker sends each entry to the Tracking Service when pi appends it, with the secrets of the LLM credential of the agent removed. The spans agent.turn and agent.tool reference the entries and embed no content.
  • No sandbox. bash and the file tools run on the host with the rights of the KanthorD process. The tool set of re@1 limits what the reviewer can do. The working directory of swe@1 is only its default location, not a boundary.
  • No approval in a Worker execution. Only the Workbench asks a human before a call that changes state.
  • Static catalog. A new agent or a change of a tool set requires a new KanthorD release. A prompt change does not: a file in the agent directory replaces the shipped text, and layers 2 and 3 add rules for each repository.
