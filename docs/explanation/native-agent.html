How the native agent works

A native agent is one LLM working unit that KanthorD runs inside its own process. It runs one agent profile, for example swe@1, on one workspace. It holds no state of its own between runs and calls no KanthorD server. A consumer opens it for a purpose: the command kanthord run agent, a Worker execution, a Workbench session or the env@1 run of the Project Service.

KanthorD does not implement the agent loop. It embeds pi (@earendil-works/pi-coding-agent 1.1.0). pi supplies the loop, the built-in tools, the session file and the model runtime. KanthorD supplies the profiles, the prompt, the guards, the credential boundary, the budget and the result. KanthorD builds only what pi does not serve.

This page is the entry page. Three pages give the details:

  • How the agent evaluation works: how KanthorD measures swe@1 and proves each prompt rule.
  • The run agent CLI reference: each option, each refusal code and each exit code.
  • How the coder@1 worker works: how a Worker execution drives swe@1.

The idea

  1. An agent profile fixes the tools, the prompt and the start checks of one role.
  2. A consumer gives the input: the profile, one model, the workspace, the budget, the extra prompt text and the session file.
  3. KanthorD opens a pi session with guards that no consumer can remove, and sends one message.
  4. The session ends at one of four ends: completed, budget_end, stopped or failed.
  5. The consumer reads the result, and the session file stays as the only record of the work.

The rest of this page explains each of these sentences.

The words you need

Each term has exactly one meaning on this page.

Term Meaning
agent One LLM working unit that runs one agent profile on pi. It is stateless and calls no KanthorD server.
agent profile The catalog entry of one name of the form <role>@<version>, for example swe@1. It fixes the tools, the profile prompt, the start preconditions and the confinement.
consumer The code that opens an agent session for its own purpose: run agent, a worker, the Workbench Service or the Project Service.
agent contract The input and the output of one run: openAgent(input) in engine/src/agent/agent-contract.ts.
run One open-to-close of an agent session. A run of run agent sends one message. That message can cause many model calls and tool calls.
session file The pi session file of a run. It is the only record of the work. The consumer names its path and owns it.
workspace The working directory of the session. For a confined profile, the workspace roots are the directories that the file tools can reach.
start precondition A condition that the profile declares and that the agent checks before it opens the session. A failed condition refuses the start.
guard A pi extension that the agent runtime adds and that no consumer can remove, for example the tool allowlist.
profile prompt The fixed first part of the system prompt: the Standard base.md, the coding text coding.md and the Role of the profile.
known secret A credential value that the consumer gives to the run, for example the token of the --auth entry.
end How a run stopped: completed, budget_end, stopped or failed.
class The retry advice of an end: retryable (the same input can succeed later), terminal (a change is necessary) or null for completed.

Who does what

Actor Owns Does not own
The consumer The input: the profile, the model selection, the workspace, the budget, the extra prompt text, the session file path and the known secrets. It also owns the result and the retry decision. The profile prompt, the tool set and the guards. It cannot replace them.
The agent runtime (engine/src/agent/) The catalog, the start preconditions, the guards, the bash tool with its process groups, the budget limits and the end of the run. The model choice, the credential source and every server call. It resolves no fallback chain.
pi The agent loop, the built-in tools, the retry of a provider error, the compaction and the session file format. The credential file of a KanthorD run. It writes no auth.json.
The model The reply and the tool calls of each turn. Any decision about the end, the budget or the pass of the work.
The human operator The --auth file, the workspace and the files of the prompt. The session while it runs.

  • A refusal writes no result and exit 1. A refusal after the run directory exists, for example a failed start precondition, also removes the run directory. No model request leaves before the session opens, so a refusal costs nothing.
  • A signal before the message leaves gives exit 2 and no result.
  • A second signal during the 10-second abort wait forces the stop at once: exit 2 and no result. Each other end of an open session writes one result: completed (exit 0), budget_end (exit 4), stopped (exit 2), failed with the class terminal (exit 5) and failed with the class retryable (exit 75).

One run from command to result

A developer asks swe@1 to fix a bug in a clean git worktree ~/work/app, with Haiku 5.5, 30 minutes and 0.50 USD: 

kanthord run agent swe@1 \
  --model anthropic/claude-haiku-5-5:high \
  --budget 30m --budget 0.5usd \
  --workspace ~/work/app \
  --session ~/runs/fix-1.jsonl \
  --output ~/runs/results.jsonl \
  --prompt ./task.md

  1. The CLI refuses --token and a Node proxy setting first. Then it checks the form of each option. The prompt value ./task.md looks like a path, so the CLI reads the file as UTF-8 text.
  2. The CLI finds swe@1 in the catalog. It checks the session path, the pi directory and the output path. Each check runs before any file is created.
  3. The CLI checks the --auth file. The option is absent, so the file is ~/.config/kanthord/auth.json of the OS user. The CLI checks the schema of every entry of the file, uses only the anthropic entry and writes nothing to the file.
  4. The CLI makes a run directory in TMPDIR, with home/ and tmp/. It removes the ambient credential names and the proxy names from its environment. It points HOME and TMPDIR into the run directory.
  5. The CLI installs the pinned rg and fd binaries into the pi directory. It builds the model runtime from the entry, with no network call.
  6. The CLI reads the clock. The wall deadline is now plus 30 minutes. It refuses an oauth entry that expires before the deadline plus 5 minutes. It resolves claude-haiku-5-5 at high and accepts only an exact match.
  7. The CLI composes the system prompt: base.md, coding.md, the Role role/swe@1.md, and no context part. It calls openAgent.
  8. The agent runtime checks the three start preconditions of swe@1 on ~/work/app. Then it opens the pi session with the guards and the session file ~/runs/fix-1.jsonl.
  9. The CLI sends the text of task.md as one user message. pi calls the model and runs the tool calls until the model ends the turn. The guards check each tool call first.
  10. The turn ends completed. The runtime kills each live tool process and closes the session. The CLI removes the run directory.
  11. The CLI appends one JSON line to ~/runs/results.jsonl and exits 0. The line holds end completed, class null, the cost, the counts, the digests and the last reply text.

The developer now reads the change with git diff in ~/work/app. The agent commits nothing by itself unless the prompt asks for it. A second run needs a new --session path and a clean worktree.

The profiles

The catalog is static and holds three profiles. A profile name names a role, not a worker.

Profile Role Built-in tools Consumer tools Confined Start preconditions
swe@1 Software engineer read, edit, write, grep, find, ls, bash evidence-upload, link_update_list (worker tools) No workspace_directory, git_worktree, git_clean
re@1 Reviewer read, grep, find, ls None Yes workspace_directory
env@1 Environment repair read, grep, find, ls probe, environment_write (Project Service tools) Yes workspace_directory

The agent contract checks the start preconditions of the profile before it opens the session. A failed precondition refuses the start with a reason that starts with its id. Under run agent, the refusal is cli.run.agent.start_refused with exit 1.

Id Condition
workspace_directory The working directory and each root are directories that exist.
git_worktree Each root is the top level of its git worktree. A subdirectory of a worktree fails.
git_clean Each root has no uncommitted change and no untracked file. An ignored file is no change.

Each check runs git with an isolated environment, no hook and no fsmonitor, and a deadline of 30 seconds. It changes no file of the workspace.

  • A consumer tool is declared in the profile but implemented by the consumer. run agent implements no consumer tool. So a run of swe@1 through run agent has no evidence-upload and no link_update_list. pi then declares only the built-in tools to the model. A model call of such a name gets the pi result Tool <name> not found, and no tool runs.
  • A consumer that passes a tool that the profile does not declare makes the open fail with agent.tool_undeclared.
  • A profile holds no provider, no model and no reasoning effort. The consumer selects them.
  • A new profile or a change of a tool set needs a new KanthorD release.

The reviewer re@1

re@1 judges the work of swe@1. It is the second actor of each pair of work and judgement:

  • In a Worker execution, reviewer@1 runs re@1 and asks for one judgement line that starts with kanthord-judgement:.
  • In the agent evaluation, the runner runs re@1 through run agent as the Opus diagnosis of one run. The diagnosis explains it.

re@1 has no tool that writes a file or runs a command. Under run agent and in a Worker execution it is confined, so its file tools read only inside its workspace. A Workbench session does not confine it. Its prompt also forbids a change to the repository. The tool set enforces that rule; the prompt only states it.

re@1 reads the same base.md and the same code rules as swe@1, because it judges against them. Its Role states that a violation of the criterion or of the default standard is a blocker, and that a blocker fails the assessment.

The prompt

What the model reads

Start with the result. run agent swe@1 with one --system-prompt part sends the model this sequence: 

[system]
…the text of base.md…
…the text of coding.md…
…the text of role/swe@1.md…
…the text of the --system-prompt part…
[user]
…the --prompt parts, joined with one blank line…

A Worker execution of swe@1 on a node with one repository binding app sends this sequence. The binding names the instruction file AGENTS.md, a Repository prompt and a Binding prompt of swe@1: 

[system]
…the text of base.md…
…the text of swe@1.md…
Repository prompt of repository app, file AGENTS.md:
…the text of AGENTS.md at the base commit that the attempt pins…
Repository prompt of repository app, set in KanthorD:
…the text of prompts.repository of the binding…
Binding prompt of repository app:
…the text of prompts.agents["swe@1"] of the binding…
…the framing…
[user]
…the work prompt…
  • One function composes every system prompt: composeSystemPrompt(profile, instructions) of engine/src/agent/prompt-chain.ts. It puts the profile parts first, then the consumer parts. A blank line separates two parts. A part with a heading puts the heading line before its text.
  • run agent takes the profile prompt from profilePrompt: base.md, coding.md (not for env@1) and the Role role/<profile>.md (env@1.md for env@1). Each --system-prompt part follows, with no heading. A --system-prompt part never replaces the profile prompt.
  • A server consumer takes layer 1 from the agent declaration: base.md and the combined <agent_name>.md. For swe@1, the combined file holds the Role, the code rules and two sentences about the worker. Today the two paths therefore use two files for the Role. Each prompt change of the evaluation changes both files with the same text.
  • The digest system_prompt_digest of the result is the SHA-256 of the composed text. Equal digests mean the same system prompt.

The Role of swe@1 holds two rules that the agent evaluation kept:

  • Contract coverage. Before the end of a turn, list each rule of the task, name the test that proves it, and run it. Never edit a test so that a defect passes. Add no behavior that the task does not ask for.
  • Configuration stays. Change no lint, format, test or runner configuration, no package.json, no lock file and no .gitignore to make a check pass. Change the code instead.

Text or path

A --prompt or --system-prompt value is a path only when it looks like one: it starts with /, ./ or ../, or it holds no whitespace and holds a / or ends with a short extension such as .md. Each other value is text. When no file exists at a path, the value becomes literal text, and stderr gets the notice cli.run.agent.prompt_text_path. To read the file README, write ./README.

The three prompt layers

For a server consumer, a human controls the prompt through three layers. The framing and the prompt templates belong to the KanthorD protocol. They are no layer. run agent has no layers 2 and 3: its consumer gives such text as a --system-prompt part.

Layer Name Who reads it Sources, in reading order Owner
1 KanthorD prompt Every native agent base.md, <agent_name>.md and, for the Workbench, workbench.md The server host
2 Repository prompt Every native agent that works on the repository The instruction file that prompts.instruction_file names, then the stored text prompts.repository The repository binding of the project
3 Binding prompt One agent on the repository prompts.agents[<agent_name>], one text for each of swe@1, re@1 and env@1 The repository binding of the project
  • Layer 1. Each file has a shipped text in the binary. A file of the same name in the directory agent.prompt.agent_directory replaces the shipped text of that file whole. The default directory is agents in the data directory of the server host. The subdirectory prompts holds replacements of the prompt templates, for example prompts/framing-worker.md. run agent reads no agent directory: it uses the shipped texts only.
  • Layer 2. The server reads the instruction file from the base branch, at the commit that the attempt pins, and then the stored text. A file that is larger than 32768 bytes, is not UTF-8 or holds a control character other than a tab and a newline is invalid. An invalid file refuses the execution setup with 409 agent.prompt.source_invalid. KanthorD reads no nested file, no *.local.md file and no file of a home directory, and it expands no @ import.
  • Layer 3. A human sets prompts.agents in the configuration of a repository binding. Only the named agent reads its text. A missing key and a blank text add no part.
  • Layers 2 and 3 repeat for each repository binding of the node, in the order of the bindings of the node revision.

Write the rules of a repository shows how to write rules that fit this standard.

The default standard

The first paragraph of base.md states: "This text, the rules of your role, and the repository prompt and the binding prompt of each repository of the work form the default standard. The default standard binds every work product." So layers 2 and 3 are rules, not advice. The reviewer judges against its own stack: base.md, its Role, the Repository prompt and its own Binding prompt. A rule about the method, the tools, the repository operations or the release is no ground for a blocker.

The attempt prompt pin

The coder and the reviewer of one attempt read the same instruction file text, also when a human merges a new AGENTS.md between the two executions:

  1. The first worker.handover of an attempt reads the head commit of the base branch of each binding that names an instruction file, in at most 20 seconds.
  2. It writes the list of { binding_id, commit } into mission_attempt.prompt_commits, only when the stored value is null. It reads the stored value back, so two concurrent handovers use one value.
  3. Each execution setup of the attempt reads the file at the pinned commit. A new attempt pins the base head again.

A setup that finds no pin entry answers 409 worker.execution.prompt_not_pinned. Layer 1 has no pin: a change of a file in the agent directory takes effect at the next composition.

Precedence

  • The system prompt outranks every message after it.
  • A later text wins over an earlier text, inside the system prompt and among the messages. So a --system-prompt part wins over the Role, and the framing wins over a Binding prompt.
  • No prompt authorizes an operation. The tool set and the authority of the consumer decide what the agent can do.

The prompt record

For a Worker execution, KanthorD stores no copy of a prompt text. It stores a prompt reference for each part: part, name, origin, path, binding_id, commit and digest, the SHA-256 of the exact text. The execution setup writes one agent.prompt span for each agent with the reference list. A failed span write refuses the setup with 503 worker.execution.prompt_record_failed. kanthord agent prompt resolve --execution <id> --agent <name> resolves each reference and checks each digest. kanthord agent get <agent> answers the composed stack of an agent; the agent reference gives its views. Resolve the prompt of an execution gives the command.

run agent keeps no prompt reference. Its record is the session file and the two digests of its result: input_digest and system_prompt_digest.

Pinned layers

pi compacts a long conversation into a summary. A rule or a task that only the old messages hold can then disappear. Two pins stop that. The system prompt pin keeps the rules for each consumer that has it. Only a Worker execution also pins the task. Under run agent, a compaction can summarize the task message.

  • System prompt pin. A guard on the stream function inserts the system prompt before each model call when the request lacks it.
  • Work pin. A context hook inserts the work prompt as a message directly after the system prompt when the conversation lacks it. A Worker execution sets the work prompt. run agent sends no work prompt, so this pin is empty for it.

Configuration: which model answers

run agent takes one model from --model <provider>/<model>:<level>. It has no default model, no fallback and no cooldown. A server consumer resolves its model from the agent enablement instead:

  • A human enables an agent for the server. The agent enablement holds one or more agent providers, one default configuration (an agent provider, a model identifier and a reasoning effort) and a fallback list of up to 7 more configurations.
  • A Worker execution takes an override entry from its worker binding. A Workbench session takes the values that the human picked. The Agent component merges the entry over the default and validates the result: the provider exists, Custody accepts the credential, the model is known and the effort is a supported level.
  • The result is the effective configuration. Disablement is the only stop switch: it refuses every later resolution.

The fallback chain

The effective configuration is the head of a fallback chain, and the fallback list is its tail. A worker binding entry with its own fallback list replaces the list of the enablement whole.

  • At each claim, the Scheduler picks the first chain entry whose credential has no live cooldown. The execution uses that selection until it ends.
  • A worker execution that stops with provider_failed and the code rate_limited, quota_exhausted or unavailable puts the credential into a cooldown. A repeated failure doubles the cooldown, up to one day. A release with no provider failure clears it.
  • When the credential of every entry cools down, the work pull answers "no work". No node blocks.
  • kanthord agent cooldown list shows the cooldowns, and kanthord agent cooldown clear <credential> clears one. The Fallback chain card of the agent page in the dashboard shows the cooldown of each entry, but it has no Clear action yet. Until then, use the CLI to clear a cooldown.

Model runtime

The LLM component turns the selection into a pi ModelRuntime and one model. The runtime reads the secret through a credential store that holds only the one credential of the run. It makes no network call to refresh the model lists (allowModelNetwork: false). For openai-compatible, KanthorD registers a provider from the credential metadata, and the model has no price.

Isolation from the host pi installation

  • pi runs with its own agent directory through PI_CODING_AGENT_DIR: kanthord/pi under the KanthorD XDG state directory, for example ~/.local/state/kanthord/pi. A worker instance uses pi/ of its data directory.
  • pi runs offline (PI_OFFLINE=1), with in-memory settings, and with telemetry and analytics off.
  • The session loads no extension, no skill, no prompt template, no theme and no context file from a path.
  • The system prompt shows the working directory relative to the home directory, for example ~/work/app.

Tools

The agent receives only the tools of its profile. pi declares to the model only a tool that is declared and registered.

  • Built-in tools are the pi tools read, edit, write, grep, find, ls and bash. grep and find run rg and fd. KanthorD installs pinned copies into bin/ of the pi directory and never takes them from PATH.
  • bash runs each command as the OS user of KanthorD, in its own process group. Under run agent and in a Worker execution, the timeout of each command is at most 10 minutes and at most the remaining wall budget, and the end of the command kills the group, so a background process does not survive. Under run agent, the end of the turn also kills each live command. A Workbench command has no timeout cap, and the end of the command does not kill its group.
  • Worker tools. evidence-upload uploads a workspace file as evidence of the attempt. link_update_list lists the link updates of the node. Only a Worker execution implements them.
  • Operation tools (Workbench only) expose KanthorD operations. A call runs with the identity of the human who sent the last message. An operation that changes state waits for the approval of the human. The operation tool reference lists every tool.
  • An operation becomes a tool when its access is human, it is not a stream and it handles no secret. The tool name is the operation id with each . replaced by --, for example mission--node--create. The agent cannot call the 13 operations that handle a secret or pin a host key: llm.credential.create, .rotate, .check and .login_code; repository.credential.create, .rotate, .check, .ssh_key_create and .ssh_key_rotate; repository.host_key.pin; storage.credential.create, .rotate and .check. A human does these in the dashboard or the CLI.

Guards

The agent contract adds these guards to each session, in this order. A consumer cannot remove one.

Guard What it does Why
Home-relative working directory Shows the working directory relative to the home. The prompt holds no user name of the host.
Tool allowlist Blocks a call of a name outside the declared tools, with the reason The tool <name> is not declared for this agent. A nested call or an extension tool cannot pass the profile.
Marker restore Restores a redaction marker of this run that a pattern rule made, for example a database password in a file, into the input of write and edit. Blocks a call whose input holds a known secret, a marker in a bash command, a marker of the LLM credential or a marker that it cannot restore. The model can write a value that it saw only as a marker into a file: the real value reaches the file. No tool receives the LLM credential.
Checkout confinement (confined profiles) Blocks a file tool whose path leaves the workspace roots, after it resolves ~, .. and each symbolic link. The reviewer reads only the work under review.
Pinned layers Before each model call, re-inserts the work prompt when the conversation lacks it. The task survives a compaction.
Input redaction Replaces each sensitive value in a system, user, tool result and custom entry with a marker <redacted:<rule>:<index>:<tag>>. No input entry of the session file holds a secret value, and the model never receives one.
Output finding Keeps each LLM reply unchanged and counts each known secret in it. KanthorD does not change LLM output. A secret in a reply gives the stderr line cli.run.agent.secret_exposed with the rule and the count. Rotate that credential.

At the exit, the result text and each failure reason pass the exit redaction: a known secret shows as the redaction marker.

Budget and ends

Budget

  • run agent has one wall budget (default 2h) and an optional cost budget in USD. The cost is the list price: the sum of usage.cost.total of each assistant message. The run compares it after each assistant message, so one model call can pass the budget. The first limit ends the turn with budget_end and exit 4, and the result field budget_reached is wall or usd.
  • The wait of each pi retry counts against the wall budget. A model with no price, for example an openai-compatible model, refuses a cost budget with cli.run.agent.budget_unpriced.
  • A Worker execution has a resource budget of 200 model turns and 2 hours. A worker binding can override both values. When the budget ends, pi stops after the current turn and each later bash command is refused.

Ends and classes

End Cause Class Exit
completed The model ends the turn. null 0
budget_end The first wall or USD limit. terminal 4
stopped SIGINT or SIGTERM during the turn. Today a wall limit that fires during the abort gives budget_end instead. terminal 2
failed A provider error that pi classifies as retryable and that is no context overflow, for example a 429, after the last pi retry. retryable 75
failed Each other provider error, or an internal error. terminal 5
  • pi retries a retryable error up to 3 times inside the session. run agent retries nothing by itself. A consumer retries an exit 75 with a new --session path and a workspace that passes the start preconditions. For swe@1, reset or clone the worktree again first, as the evaluation does.
  • The first signal aborts the turn, and the run waits at most 10 seconds. After that time, or at a second signal, the run makes a forced stop.

Invariants

These rules hold for every run. Each one explains one surprise.

  1. The tool set, not the prompt, limits a profile. re@1 changes no file even when a prompt asks for a change, because it has no tool that writes.
  2. A consumer adds text and never replaces the profile prompt. A --system-prompt part that says "ignore the Standard" still comes after the Standard, in the same system prompt.
  3. A run writes a new session file. A second run with the same --session path is refused with cli.run.agent.session_exists before any model call.
  4. No tool receives a known secret. A bash call that holds the token of the --auth entry is blocked, also when the model copies the token from a file.
  5. The agent picks no model. run agent with an unknown or inexact model is refused; it never falls back to a near model.
  6. A refusal costs nothing. Each refusal and each failed start precondition comes before the first provider request. So a dirty worktree refuses swe@1 at no cost.
  7. The agent calls no KanthorD server. A child process gets no KANTHORD_TOKEN and no KANTHORD_ENDPOINT. Only a worker tool reaches the server.

Limitations

  • No sandbox for swe@1. swe@1 is not confined. bash and the file tools run on the host with the rights of the OS user. The workspace is the default location, not a boundary. The evaluation adds an OS read-deny rule for this reason.
  • One message for each run agent call. The command has no resume and no second message. A later call starts a new session.
  • No worker tools in run agent. A run of swe@1 cannot upload evidence or list link updates.
  • One model call can pass the cost budget. The run checks the cost after each reply.
  • No resume of a Worker execution. A worker persists its session to a file but never opens it again.
  • No approval in a Worker execution or a run. Only the Workbench asks a human before a call that changes state.
  • Static catalog. A new profile or a change of a tool set needs a new KanthorD release. A prompt change of layer 1 does not: a file in the agent directory replaces the shipped text for a server consumer.

Where it runs and how to set it up

run agent runs on the machine of the operator, as the OS user. It needs no server. To prepare one run:

  1. Build or install kanthord. In the engine repository, run pnpm run build.
  2. Make a private temporary directory with mode 0700. Log in with pi with PI_CODING_AGENT_DIR set to that directory.
  3. Move its auth.json to ~/.config/kanthord/auth.json with mode 0600. Remove the temporary directory. Do not copy an oauth entry from another file: two files with one refresh token break each other at the first refresh.
  4. For swe@1, use the top level of a git worktree with no uncommitted change and no untracked file as the workspace.
  5. Make a directory for the session files. You must own it, and it must have no group or other write bit. Keep it outside the workspace.
  6. Run kanthord run agent with a new --session path for each run.

In the engine repository, pnpm run play:agent prepares a private play directory and starts one run. A Worker execution runs in a worker process, and a Workbench session and the env@1 run run in the server process.
