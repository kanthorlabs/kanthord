# Audit: worker node execution refactor design

Auditor: Aelita. Engine commit `2797a453`. Inputs: `design.md` (including the code facts list), `review.md`, HANDOFF rulings of 2026-11-14, `worker-service.md`, `worker-service.impl.md`.
Scope: every behavior of today's worker execution that the design does not cover, covers wrongly, or keeps although it is not reasonable ("change proposal").
All paths are under `engine/src/` unless stated. Every item is checked in the code.

## Blockers

- B1 - status:OPEN - action:YES - external stop orders - The design models only `run.stop` and the `ClaimWatch` revoke (section 2, rules 5 and 7). Today the instance exchange delivers stop orders (`human_paused`, `instance_archived`) and the unit stop gives `worker_stopped` (`apps/worker/index.ts:528`, `apps/worker/unit.ts:249-255`, `:363-369`). `stopWith` cancels the joined `stop` context, and `ExecutionRun.halt` takes that requested stop before any step code (`worker/unit/execution-run.ts:195-198`, `:295-310`). A pause of a node reaches a native execution only on this path (`mission/service.ts:1394`). The Scheduler refuses a release with an ordered reason that has no order (`scheduler/release.ts:87-101`, `ORDERED_STOP_REASONS`). - fix:add runner rule 5a: an abort whose reason is an `ExecutionStop` is a requested stop; the runner adopts it through `run.stopOf`, it wins over the code of the step that it aborted, the `ClaimWatch` ends, `onStop` runs, and `execution.release(stop)` carries the ordered reason; add one test per reason. - why:without the rule a pause or a shutdown releases as `operation_failed`, so the Scheduler counts a human act as a failure and backs the node off.
- B2 - status:OPEN - action:YES - credential report before assessment.submit - Section 5.4 sends the final credential report only in `execution.release` (S41). Today `submitAssessment` settles the credentials first (`worker/unit/execution-run.ts:430-444`), because `assessment.submit` can close the execution (`evaluation.ts:661-662`) and `worker.credential` needs a live execution (`worker/contract.ts`, `credential`, `requiresExecution: true`). `releaseStop` also settles first and maps a refused report to `revoked` (`execution-run.ts:515-528`, `:598-600`). - fix:state in 5.4 that every final call (`assessment.submit`, `execution.release`, `execution.release(stop)`) settles the credentials once before the call, and that a refused report ends the execution as `revoked` with no release. - why:a closed assessment with no report loses a rotated OAuth refresh token in custody.
- B3 - status:OPEN - action:YES - trace close and flush before each final call - Rule 9 opens phase and step spans around every step, and rule 10 disposes the agent after the last phase. In section 4, `execution.release` is a step inside `phase finish`, so both spans end after the release. Today the root traces close and the sink flushes for 5 s before `assessment.submit`, `release` and `releaseStop` (`execution-run.ts:431-433`, `:477-478`, `:561-562`), and `finishImplement` ends the finish phase span before the release (`steps-implement.ts:172-185`). `tracking.telemetry.write` needs a live execution (`tracking/contract.ts:897-908`), and `worker-service.impl.md` (Traces) states that a record after the release is refused. - fix:make the final call a runner action outside every phase: end all open phase and step spans, close the agent traces (`run.onTraceClose`), flush, then call; dispose the agent after that. - why:as designed, every execution loses its `finish` phase span, its last step span and the end of its `agent.session` span.
- B4 - status:OPEN - action:YES - cleanup context of onExit and onStop - `StepIo` carries one `signal` from `operationContext`. A stop cancels that context (`execution-run.ts:297`), so `checkpoint.gate`, `branch.push` and the release in `onStop` fail at once; the design fixes only the fence (S30). Today `checkpointOnStop` uses `run.cleanupContext()` and `settleImplement` uses `budget.cleanupContext(operationContext)`, both bounded by `expired_at`, not by the wall budget (`steps-implement.ts:193`, `:290`, `:917`). Gate G after a turn also runs under the `expired_at` deadline (`turn-gate.ts:141`). `worker-service.impl.md` (Stop and budget) states that every cleanup command is bounded by `expired_at`. - fix:give `StepIo` a `deadline` kind per node: work steps get the agent or wall deadline; `gate.g`, `checkpoint.gate`, `claim.fence`, `branch.push` and the release get a fresh context bounded by `expired_at` (from `run.cleanupContext()` in `onStop`). - why:as designed, no stop path ever checkpoints or pushes, so the work of each stopped execution stays local.
- B5 - status:OPEN - action:YES - D24 name reuse across attempts and nodes - The D24 rule picks the next free counter from `git ls-remote` only. A branch that an earlier attempt never pushed is absent there, so a new attempt from the base can get the same name. The instance keys push records and the scratch store by the branch name (`worker/unit/push-record.ts:25-38`, `workspace.ts:270-273`, `:492-519`). With an old record, `pushRuleStart` throws `repository.node_branch.missing` or starts from the local commits of the old attempt (`repository/connector.ts:616-629`). Two nodes with the same slug that have not pushed also get one name. - fix:the server keeps every assigned node branch name per repository binding and never assigns a name twice; the counter takes the maximum of the stored names and the remote names. - why:a reused name carries old attempt work into a fresh attempt from the base, or blocks every execution of that attempt on the instance.
- B6 - status:OPEN - action:YES - D24 adopts a remote branch that the node does not own - With no push record, `todayStart` starts from `origin/<branch>` whenever the remote holds the name (`repository/connector.ts:599-605`). Today the name `kanthord/<node id>` makes a foreign branch of that name unlikely. A semantic name such as `fix/login-timeout` can be a human branch or the branch of another node that appears between the name choice and the first push. The worker then builds on it and pushes onto it (`connector.ts:665-680`). - fix:for an attempt with no confirmed push of its own, refuse a start from an existing remote branch with a new code, and send the first push with `--force-with-lease=refs/heads/<b>:` (expect absent); the server then assigns the next counter. - why:as designed, the worker can write on a human branch and mix two nodes in one branch.
- B7 - status:OPEN - action:YES - D23 conflicts with D13 and the catalogue - D13 and 5.3 rule 9 abort a merge with markers at a budget end, commit the rest, push and release with further work. D23 says that a budget end with markers left submits a conflict report, aborts and moves the node to `Blocked`. S14, S18 and section 4 still list `worker.merge.markers_left`, one conflict turn and no `markers.check` step. Today the first marker check aborts and stops (`turn-gate.ts:401-417`). - fix:delete the markers-left branch of D13 and rule 9; add `conflict.revisions` (loop), `markers.check`, `conflict.report` (evidence) and the Blocked release to S13-S14 and to both `base.refresh` loops of section 4; remove `worker.merge.markers_left` from the stop lists. - why:the golden call-stack test of D21 compares the code with section 4, so a section that contradicts the ruling fixes the wrong behavior.
- B8 - status:OPEN - action:YES - D23 Blocked release is not specified - D23 needs a release stop that the Scheduler and the Mission Service map to `Executing -> Blocked`. `ExecutionStopReason`, the release check (`scheduler/release.ts:87-101`), the settlement classification (`scheduler/settlement.ts:180-195`) and the cause map (`worker/unit/stop-cause.ts`, `modelFaultCodes`) have no such stop. The invariant "stop accounting codes kept" is then false. The design also does not state: whether `onStop` pushes the committed unit work before the Blocked release; which counter the D23 bound uses (`ProgressCtx` exists only inside `release_rounds`); and that the conflict report evidence has no repository asset, which `snapshotOf` and `hasEvidence` would accept (`evaluation-input.ts` `snapshotOf`). - fix:name the stop (for example `conflict_unresolved` under a new reason), list its settlement class and cause; push committed work before the release; keep a separate conflict counter per merge frame; make the report a `produced` asset only. - why:without these rules the refactor either loses unit work or lets a partial merge become the review snapshot.
- B9 - status:OPEN - action:YES - D24 breaks the commit attribution rule - `worker-service.md:419` requires that every commit of an execution is attributable to its task and its attempt. D24 drops the unit id body (`kernel/commit-message.ts` via `turn-gate.ts:92-112`). The unit record keeps only the commits that are checkout heads at the pass (5.1), so the earlier gate commits of a unit name nothing. - fix:add the new head of each checkout to the `worker.gate` span (`kanthord.git.commit`, under `worker.task` with the unit id), and rewrite `worker-service.md:419` as attribution through the trace and the head evidence. - why:the ruling and a documented rule contradict each other, and the page must record the decision.
- B10 - status:OPEN - action:YES - budget end from a thrown cancellation - Rule 6 knows a budget end only as a step `exit` or the `budgetGuarded` check before an `llm` step. Today evaluation and examine also turn a thrown `ContextCancelled` or `DeadlineExceeded` into the budget end when the budget is exhausted and `operationContext` is live (`evaluation.ts:425-442`, `steps-examine.ts:152-161`, `:188-189`). The `stopMapped` middleware maps every unknown error to `run.stopOf`, which gives `operation_failed`. - fix:let `stopMapped` read `budget.exhausted()` and the `operationContext` state, and map those two errors to the chain budget end. - why:a setup, verification or git step that the wall deadline cancels then counts as a failure, not as `assessment_absent` or a further-work release.
- B11 - status:OPEN - action:YES - examine verification stated wrongly - S25 shares `verify.all` with every node and task command, `copyRepeated` and `reruns: 2`. Examine runs only the node commands, with no reruns, no copy, no baseline, and no infrastructure or environment stop; it skips the run when no checkout exists (`steps-examine.ts:70-97`). - fix:give examine its own `verify.node(examine)` step, or a `verify.all` mode, with today's contract. - why:as designed, an examine report changes, its time grows by the task commands, and a flaky command stops the examine.
- B12 - status:OPEN - action:YES - D10 changes the completed count - 5.1 counts a unit as completed only when its put succeeded. With D10 a transient put failure leaves a passed unit uncounted. A budget end with only that unit then sends `budget_end`, which counts toward `mission.further_work_limit` (`steps-implement.ts:172-185`). Today the local amend decides (`done-record.ts:40-77`). - fix:count a unit as completed when it passes with a gate commit and `units.plan` found no valid record, independent of the put result. - why:a server error must not move a node with progress toward `Paused`.

## Suggestions

- S1 - status:OPEN - action:YES - change proposal: live setup before the base merge - `prepareStepsWorkspace` runs the live setup on the pre-merge head (`steps-implement.ts:771-777`), and `refreshAtClaim` merges the base after it (`:353`). A merge that changes the dependency manifests leaves the live environment stale until the release gate. The design keeps this order and puts `agent.open` beside `env.setup(live)` (D20). - fix:run `env.setup(live)` after `base.refresh(claim)`; open the agent beside the workspace branch, because a conflict turn needs it. - why:live verifications then fail on missing dependencies, and the agent spends revision turns on an environment fault.
- S2 - status:OPEN - action:YES - change proposal: indeterminate answers stop the execution - `run.call` turns an `Indeterminate` answer into `operation_failed` with no code (`execution-run.ts:355-365`). A timeout on any read or evidence submit ends the execution, while handover and setup reads retry (`apps/worker/api.ts` `retryIndeterminate`, `execution.ts:249-261`). - fix:retry an indeterminate answer of an idempotent call with the same idempotency key until a short bound, as the release already resolves its own indeterminate answer (`execution-run.ts:488-508`). - why:D8 runs more reads at once, and each transient timeout costs a full counted failure.
- S3 - status:OPEN - action:YES - proof sources and host tool revoke - 5.2 moves the timer only on `run.call`, but 5.5 says host tools also prove the claim. Host tools, credential leases and reports, and telemetry writes all bypass `run.call` (`apps/worker/execution.ts:133-185`, `apps/worker/handover.ts:229-282`, `telemetry-sink.ts`). A host tool that sees an ended execution cancels the host context and sets `state.revoked` (`execution.ts:145-148`); the next `run.call` then stops with `operation_failed`. - fix:put one proof hook on the worker transport for each `requiresExecution` call; route an execution-end answer of any such call to `run.revoke()`. - why:one rule then covers every server call, and a host-tool revoke ends as `revoked`.
- S4 - status:OPEN - action:YES - change proposal: revoke through the stop-order channel - The instance exchange already pushes stop orders on a work version change (`worker/instances.ts:819-829`, `apps/worker/index.ts:519-530`). Open question 4 rejected a heartbeat change, but this channel exists. - fix:queue a stop order with reason `revoked` when the Scheduler ends a running claim; keep `ClaimWatch` as the fallback for a lost exchange. - why:a revoke then stops spend in about one exchange round trip, with no polling.
- S5 - status:OPEN - action:YES - handover and setup paths with no release - 5.4 says a handover stop releases with an empty credential set. A `gateway.*` failure of the handover or of `execution.setup.get` releases nothing: the host logs `worker.execution.setup_unavailable`, and the pull loop pauses with backoff (`execution.ts:52-62`, `:267-280`, `pull-loop.ts:160-161`). An execution-end answer also returns with no release (`execution.ts:128-131`). - fix:list the three outcomes of the claim phase in 5.4: refusal releases, `gateway.*` gives setup unavailable with no release, execution end gives no release. - why:the claim phase is new chain code, and these paths decide whether the claim waits for its expiry.
- S6 - status:OPEN - action:YES - wrong handover codes - 5.4 lists `worker.handover.credential_open_failed`, which does not exist. The code is `worker.handover.sealed_unopened` (`apps/worker/handover.ts:72-77`). `worker.credential.lease_mismatch` is missing (`:100-105`). - fix:replace the code and add the lease mismatch to the S43 and C1 stop lists. - why:the stop lists feed the golden test and the CLI page.
- S7 - status:OPEN - action:YES - workspace.node stops and keep rule - S06 omits `repository.node_branch.missing` (`repository/connector.ts:473-495`, `:604`, `:627`). `prepareImplement` keeps the created directories on that code and removes them on any other failure (`workspace.ts:320-330`). - fix:add the code to S06 and state the keep rule. - why:the code reaches the release, and the keep rule protects a checkout with unpushed work.
- S8 - status:OPEN - action:YES - evaluation outcomes not in the catalogue - The design does not state: a non-success assessment that leaves the node in `Evaluating` stops with `operation_failed` (`evaluation.ts:669-671`); an examine judgement with proposals gives `Undetermined` (`:282-299`); an implement node with no snapshot reviews in an execution workspace with no checkout, and `tested_input` falls back to the newest placed asset (`evaluation-input.ts:164-232`, `:497-499`); no tested input stops with `operation_failed`. With no checkout, assets go into the workspace directory itself (`:524-527`), which D27 must list as a root. - fix:add these rules to S07, S16, S37 and D27. - why:each one is a stop or a result that a port can drop.
- S9 - status:OPEN - action:YES - coder report accumulation - `ExecutionCtx` and `UnitCtx` hold no report. Today each unit end keeps `## <id> <name>` and the last agent text, and drops an empty text (`steps-implement.ts:141-149`, `:460`). - fix:add `reports` to the `units` loop scope with `unit.enter` or `unit_record.put` as writer, and let `report.coder` read it. - why:S28 has no input as written.
- S10 - status:OPEN - action:YES - change proposal: budget end drops the coder report - A budget end skips `submitCoderReport` (`steps-implement.ts:196-204`), and the reviewer reads only the newest report (`evaluation-input.ts:69-78`). The units of an earlier budget-ended execution then have no report. - fix:submit the report of the completed units also in `onExit budget_end`, before the push. - why:the reviewer then sees the report of every unit, not only of the last execution.
- S11 - status:OPEN - action:YES - telemetry that the design leaves out - Rule 9 lists six spans. It omits `worker.task` (round, revision count and the `kanthord.stop.*` attributes of a `no_progress` stop, `method-telemetry.ts:88-110`, `worker-service.impl.md` coder flow), `worker.evaluation`, `agent.session`, the session entry records (`agent-telemetry.ts:259`), the node shape attributes on the prepare phase (`native-method.ts:211-220`) and the git step marks of the stop cause (`method-telemetry.ts:79`, `stop-cause.ts`). A new `worker.step` level changes the parent rule of `agent.turn` in `worker-service.impl.md` (Traces). - fix:list every current span and attribute with its owning step, keep the git step marks in `base.merge`, `base.fetch` and `branch.push`, and update the parent rule. - why:trace queries and the stop cause read these values today.
- S12 - status:OPEN - action:YES - log records - The design names three log messages. The code writes about twenty: `task started`, `task committed`, `task verified`, `units planned`, `verdict planned`, `verdict rule checked`, `verdict rule waived for review`, `release failure routed`, `environment setup`, `setup failed on the node head`, `turn violation`, `root entries removed`, `checkpoint failed`, `tree prepared`, `tree deleted`, `scratch not stored`, `node judged`, `review base off the node history`, `execution ended`, `credential handover received`. - fix:add a log column to the step catalogue, and let the golden test assert the message set. - why:operators and tests read these messages, and a port drops a message that no list names.
- S13 - status:OPEN - action:YES - workspace hygiene steps - No step names: `removeRootEntries` after each gate and each live verification (`turn-gate.ts:461-475`, `steps-implement.ts:928`); the scratch store `.kanthord-scratch/` with its exclude line and its restore per branch (`workspace.ts:308`, `:492-556`, `:953-960`); the leftover release and review trees (`:270-273`, `:719-726`); `keepOnly` of push records and checkouts (`:278-292`). - fix:add these to S06, S07, S22 and `gate.g`, and to the D19 dispose list. - why:they are the crash recovery of the instance, and D19 replaces the `finally` blocks that call them.
- S14 - status:OPEN - action:YES - chain selection - The design does not state how the runner picks a chain. Today `method` of the worker declaration and `intent` decide, and a declaration with no method (`claude-code@1`) stops with `operation_failed` and no code (`native-method.ts:103-104`, `:146-149`, `worker/catalog.ts:49-56`). - fix:add a selection table and the unknown-method stop. - why:the external harness worker then keeps its current failure.
- S15 - status:OPEN - action:YES - change proposal: commit author name - Every worker commit has the author and committer `kanthord <kanthord@localhost>` unless the host sets `GIT_AUTHOR_*` (`kernel/git-environment.ts:5-10`, `:59-60`). D24 removes the name from branches and messages but not from the author. - fix:ask Ulrich whether the trademark ruling covers the author; if yes, take the identity from the worker binding or the project. - why:one decision now avoids a second rewrite of commit identity.
- S16 - status:OPEN - action:YES - turn budget guard in the removed lines - 5.2 removes `native-agent.ts:170-178`. Line 171 also holds `budget.exhaustedAfterTurn()`, which ends the session before a turn that exceeds the turn budget. - fix:remove only the `turnCheck` call and keep the budget guard in `finishTurn`. - why:a literal port aborts the session instead of ending it at the turn limit.
- S17 - status:OPEN - action:YES - record of a routed node unit - In a node with tasks, a release failure of a node command routes to the node unit (`release-gate.ts` `commandOwners`), and its pass writes a record today (`done-record.ts:40-77`). 5.1 restricts only the verdict unit. - fix:write a record only for a task, or for the node unit of a node with no task. - why:no reader reads a node-id record of a node with tasks.
- S18 - status:OPEN - action:YES - release answer handling - S41 states only the Diagnostic case. Today an indeterminate release reads the claim and accepts `finished` (`execution-run.ts:488-508`, `:530-555`), a failed settle in `release` becomes a stop, and `releaseStop` returns the stop as an end when its own release fails (`:588-614`). - fix:copy these rules into S41. - why:they decide whether the pull loop ends.
