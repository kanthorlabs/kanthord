# Review: worker node execution chain design

Reviewer: Aelita, co-owner. Code base: engine commit `2797a453`. Input: `design.md` and `facts.md` in this directory.

The design direction is right: a staged pipeline, a status-based gate G, a claim timer with a push fence, and a unit record outside the user repository. The review found 11 blockers. Each blocker changes behavior that the design claims to keep: gate precedence, the no-progress rule, the record guarantee across attempts, the stop accounting, the push before start, or the claim delay. All 11 blockers are fixed in `design.md`. Four suggestions stay open for Ulrich.

## Blockers

- B1 - status:FIXED - action:YES - parallel base merges - D7 and S13 merged all checkouts in parallel and sent conflicts to S14 one at a time. Gate G in conflict mode checks every checkout, so a second open merge fails with `worker.turn.git_in_progress` (`turn-gate.ts:339-354`). Today `refreshAtClaim` also merges `base_branch` before `upstream_branch` and runs the conflict turn between them (`base-refresh.ts:62-136`). - fix:keep merges serial in a `base.refresh` loop (one frame per checkout and merged branch, `base.merge` then `conflict.turn`); parallelize only the release fetch (new S42 `base.fetch`); cut the ancestor check from 2 processes to 1. - why:a parallel merge stops any multi-repository node with two conflicts, and breaks the upstream order.
- B2 - status:FIXED - action:YES - no-progress counter scope - The design put `unchangedTurns` and `lastVerification` in the per-unit `UnitCtx`. Today gate G resets the counter (`turn-gate.ts:145`), `runUnits` resets it per unit only in the planned round and once after it (`steps-implement.ts:385`, `:451`), routed rounds carry it across units and rounds, and `verdictTurnRetried` puts back the pre-turn value (`:555`). The release gate writes `lastVerification` (`release-gate.ts:211`). - fix:add `ProgressCtx` in the `release_rounds` scope, list the reset rules in section 2 rule 4, move the reset out of gate G into `progress.rule`, and add `unit.enter` for the planned reset. - why:a per-unit counter changes when `no_progress` stops in routed rounds, which the EM cannot see in tests that use one round.
- B3 - status:FIXED - action:YES - unit record accepts an earlier attempt - The design wrote a record for every pass with the head of every checkout, and took a record as valid when each head is an ancestor of HEAD. A unit that passes with no commit then records a base commit, which is an ancestor of every later attempt. A node commit that reached `origin/<base>` also stays an ancestor. Today `writeDoneRecord` writes only on a checkout whose head is a commit of the unit run, and the read covers only `origin/<base_branch>..HEAD`. - fix:put a record only with the commits of the unit run that are checkout heads (else log `unit record skipped`); valid when each commit is in `git rev-list origin/<base_branch>..HEAD` of its checkout, one process per checkout for all records. - why:the page rule "No record of an earlier attempt decides that a task is complete, unless the attempt continues the same node branch" fails with the ancestor rule; the range rule keeps it and costs fewer processes.
- B4 - status:FIXED - action:YES - evaluation budget end - The evaluation chain had `onExit budget_end` with `further_work: true`. Today every evaluation budget end is the stop `assessment_absent` (`evaluation.ts` `endedByBudget`, `runAffectedStep`, `evaluation-input.ts` `setUpReview`). Examine releases a budget end with no stop. - fix:add `Chain.budgetEnd` per chain (implement exit after start, stop `budget_end/wall_time` before start; examine exit with no stop; evaluation stop `assessment_absent`) and remove the evaluation `onExit`. - why:the invariant "stop accounting codes kept" was false; the scheduler counts these ends differently.
- B5 - status:FIXED - action:YES - checkpoint and push before start - `onStop` and `onExit` ran for any stop, also in Prepare, so a `setup_failed`, an `affected_invalid` (D9) or a Prepare budget end would checkpoint and push the node branch. Today a stop before `runStepsImplement` goes to `releaseStop` with no checkpoint and no push. - fix:add `armedFrom` to the chain; implement arms at `start`; before that, a stop or a budget end goes straight to `execution.release(stop)`. - why:a push in Prepare can create a remote node branch at the base head, which today never happens.
- B6 - status:FIXED - action:YES - last failed command first (old D10) - A release tree is scrubbed, so a later command needs the output of each earlier command (`worker-service.impl.md`, the verification memo). The owner of a failure comes from its plan index (`release-gate.ts:188`). - fix:withdraw the reorder; D11 now states plan order; D10 holds a new decision (S10). - why:a reordered round gives false failures and routes them to a wrong owner unit, which costs more turns than it saves.
- B7 - status:FIXED - action:YES - claim watch timing and end - A fixed 60 s tick that skips when `now - lastProofAt < 60 s` detects a revoke up to about 120 s late, not 60 s. The watch also ran across `assessment.submit` and `execution.release`, which can end the claim, so the next tick reads a legitimate end as `revoked`. - fix:fire at `lastProofAt + 60 s` and move the timer on each proof; end the watch at the first `claim.fence`, before `assessment.submit`, `execution.release` and `releaseStop`, and at any stop. - why:the accepted delay is 60 s, and a false revoke after a closed assessment changes the end of a finished execution.
- B8 - status:FIXED - action:YES - fence in onStop - After any stop, `run.call` and `run.checkClaim` throw the stored stop (`requireActive`), and `operationContext` is cancelled. A fence through `run.checkClaim` in `onStop` throws at once, so no stop path ever pushes. - fix:the `onStop` fence uses `run.cleanupContext()` and no `requireActive`; a revoke answer skips the push and keeps the stored stop. - why:today `checkpointOnStop` pushes after every non-revoked stop; the fence must keep that.
- B9 - status:FIXED - action:YES - gate violation precedence - Rule 3 of 5.3 checked `git_in_progress` before `history_rewritten` and `foreign_merge`. Today the order is branch, history, foreign merge, merge missing, operation in progress (`turn-gate.ts:305-356`). A reset plus a conflicted merge then gives a different code. - fix:list the 5 checks in today's order and state that skipping commands 2 and 3 on an unchanged head gives the same result. - why:the design claims that each violation code keeps its condition; precedence is part of the condition.
- B10 - status:FIXED - action:YES - parallel stop winner - Runner rule 6 said that the lowest branch index wins. `ExecutionRun.halt` stores the first `run.stop` in time and cancels `operationContext`, so the runner cannot pick a later one. - fix:the first stop in time wins; a step that needs one code for several branches (gate G) collects the branch results, waits for all, then calls `run.stop` once; the gate keeps a barrier between checks and commits. - why:the old rule cannot be implemented on the current `ExecutionRun`, and gate G must restore every checkout before it stops.
- B11 - status:FIXED - action:YES - checkpoint conclusion of a merge (D13) - Checkpoint mode has no `ConflictMerge`, so it knows neither the conflicted files nor the merge commit. A concluded merge then fails `foreign_merge` with `merge === null`. - fix:add `openMerge` to the context (written by `base.merge` and `conflict.turn`, read by `gate.g` and `checkpoint.gate`); checkpoint with `openMerge` runs the conflict-mode checks on that checkout; markers left abort the merge and commit the rest in write mode. - why:without the key, D13 either stops every budget end in a conflict or skips the marker check.

## Suggestions

- S1 - status:FIXED - action:YES - gate G before-table counts - `hash-object` runs only when `M` paths with a regular mode exist, so a changed turn runs 17 or 18 processes and an agent-committed turn 18 or 19. `update-index` adds 1 in both tables. - fix:mark row 9 conditional and give both totals; the after-table gives 5 or 6 and 8 or 9. - why:the counts feed the EM decision and the section 6 claims.
- S2 - status:FIXED - action:YES - status ahead and behind walk - `checkout -B <b> origin/<ref>` sets an upstream under the default `branch.autoSetupMerge` (`repository/connector.ts:544`), so `git status --branch` walks commits against it on every turn. - fix:add `--no-ahead-behind` to both status calls. - why:after a base merge the walk can cover many commits, twice per checkout per turn.
- S3 - status:FIXED - action:YES - speculative prior reads - S03 read the cleared outcome and the cleared assessment in the first group. Today they run only when no failed checks and no rework exist (`node-reads.ts:368-404`). - fix:run failed checks, rework and link updates in parallel; keep the conditional reads in today's order. - why:a failure of a read that today never runs would stop the execution with `operation_failed`.
- S4 - status:FIXED - action:YES - hidden mutable state - `state.memo`, `state.task`, `state.setupPending` and the open conflict merge had no context key. `checkpointOnStop` reads `state.task`; `pendingSetup` flips `setupPending` across units; the release gate and the live verification share the memo. - fix:add `memo`, `currentUnit`, `setupPending` and `openMerge` to `ExecutionCtx`, with a writer each. - why:the build check (D1) cannot see a coupling that has no key.
- S5 - status:FIXED - action:YES - phase names and nesting - The design renamed the `tasks` phase to `units` and put `release_gate` as a phase inside a loop, while `Chain.phases` was flat. - fix:keep `tasks`; add a `phase` chain node; the nested `release_gate` keeps the current `worker.release_gate` span. - why:a rename breaks trace queries for no gain, and the type must describe the call stack.
- S6 - status:FIXED - action:YES - agent open position (D20) - The agent cannot open in parallel with the merge loop, because a conflict turn inside the loop needs it. `openSession` sets `noContextFiles`, so the open reads no workspace file. - fix:open the agent in parallel with `env.setup(live)`. - why:the setup runs for minutes, so the open hides fully, and the merge loop keeps its order.
- S7 - status:FIXED - action:YES - type-level contract check (D1) - `ChainBuilder<A>` tracked available keys in the type across loops, parallel groups and exits. - fix:keep the `Pick` slice type per step; check reads, parallel writes and exit reads in `build()`; one test builds each chain. - why:Principle 2; the type gymnastics cost more than a build-time walk, and the test fails as early in CI.
- S8 - status:FIXED - action:YES - layer order (D21) - The runner port came first, before the three cost cuts. The gate, the record and the watch each live in one file group today. - fix:order the layers gate G, unit record, claim watch, runner port, parallel groups, telemetry. - why:Principle 7; the EM gets the measurable cuts first, and the port then moves verified behavior.
- S9 - status:FIXED - action:YES - golden call stack - Section 4 feeds an interactive call-stack page, and the code can drift from it. - fix:a test prints each built chain in the section 4 notation and compares it with a golden file. - why:one source of truth for the page and the code.
- S10 - status:FIXED - action:YES - non-fatal unit record put (new D10) - `run.call` stores every failure as the stop, so a transient put failure ends work in progress. - fix:log `unit record failed` for a failure that is not `revoked`; use a call variant that does not `halt`; count the unit as not recorded. - why:a record only saves turns of a later execution.
- S11 - status:FIXED - action:YES - git process count on the gate span - The D6 and D12 savings are estimates from reading the code. - fix:add `kanthord.git.process_count` to `worker.gate`. - why:production traces then confirm the counts.
- S12 - status:FIXED - action:YES - judged-commit history check - S15 listed one verdict-rule `rev-list` per judged checkout and left out `judgedCheckouts`, which runs `rev-parse --verify` and `merge-base --is-ancestor` per judged commit (`verdict-rule.ts:35-53`). - fix:list the history check in S15. - why:the verdict rule invariant includes the drop of judged commits off the node history.
- S13 - status:FIXED - action:YES - invariant I and unmerged entries - Rule 6 of 5.3 checked only the X column. - fix:state that a `u` line also fails invariant I. - why:an unmerged entry has no plain X letter and must fail as `diff --cached --quiet` fails today.
- S14 - status:FIXED - action:YES - no-progress detail size (D14) - `noProgressFactsSchema` is a strict object, and `fitted` cuts only `command` to `STOP_DETAIL_MAX_LENGTH`. - fix:D14 now states that the fitting cuts `agent_reason` before `command`. - why:a 512-character excerpt can push the detail over the limit and fail the assert.
- S15 - status:OPEN - action:YES - `project_id` and row deletion of `worker_unit_record` - AGENTS.md puts `project_id` as the second key column of a project-scoped table. No reader reads a row after its node closes. - fix:decide both in the column review round; delete the rows of a node at its close. - why:the rule "no reader, no record" applies to closed nodes, and the key rule applies to every project-scoped table.
- S16 - status:OPEN - action:YES - scope of the trademark concern - The node branch prefix `kanthord/` (`repository/node-branch.ts:4`) and `.kanthord/affected-tests.json` also put the name in the user repository. - fix:ask Ulrich whether the concern covers them (open question 6 in `design.md`). - why:a second migration later costs more than one decision now.
- S17 - status:OPEN - action:NO - row replacement cost - A routed round that passes a unit again replaces its row. When that newer commit never reaches the remote, another instance reruns the unit, although the older commit was valid. - fix:none; keep one row per unit. - why:the case needs a lost execution after a routed round, and it costs turns, not correctness.
- S18 - status:OPEN - action:NO - early affected check with a moving base (D9) - The release gate reads the declaration after a new fetch of the base, so a base fix during the execution passes there. D9 stops on the claim-time base. - fix:none. - why:a human fix during a running execution is rare, and the early stop saves the whole budget in the common case.

## Decisions checked and confirmed

- D0: a staged pipeline fits; every step runs and adds data. A Chain of Responsibility does not fit.
- The proof reset of D4 is sound. The gateway answers a `requiresExecution` call only for a claim with `ended_at` null and `expired_at` in the future (`gateway/invocation.ts` `liveExecutionRow`), which is the `running` state of `claimStateOf` (`scheduler/execution-store.ts:253`).
- A revoke through `halt` aborts the pi session (`stopOnEnd`) and the running command. A killed git process can leave `index.lock`; `normaliseGitState` removes locks at the next take. A pending push record stays pending. The revoked path runs no checkpoint and no push, as today. The stop accounting codes do not change.
- The status-based gate covers each removed fact: branch, head, staged set, untracked files and operation paths. Conversion-only paths, untracked files and agent commits keep today's handling. The six cached operation paths are per-worktree state.
- The fast path is sound: status lists every path that `add --all` stages, under the same isolated config (`core.fsmonitor=false`, empty global excludes).
- The restore sequence drops from 9 to 4 processes per checkout. A tree id cache per commit is safe.
- D9: the agent cannot fix a declaration at `origin/<base>`, so the early stop saves budget with the same code.
- D11: both verification runs stay; the reviewer independence and the clean-clone check are kept.
- D16: the review placement directory is outside each review tree; a workspace with no checkout runs no setup.
- Parallel per-checkout work is safe: `TreePool.take` and `give` are synchronous, each binding has its own push record, each checkout is its own repository, and each push opens its own SSH access.
- D17 and D18: one slot per instance and one session per execution stay valid.
- The unit record, after B3, holds across instances, after a rebuild or force-push, after a base merge, after a content change, for multi-repository nodes and for an unconfirmed push.
- D2: the shared step list and the shared service list match the different refs and guards of the three trees.
