ERD 4: Telemetry

Scope

This view holds the tables of the Tracking Service. They live in tracking.db, a database file separate from kanthord.db. After this group, the server keeps the spans, the telemetry texts and the session entries that reach it. A human lists and reads traces and imports the capture of an external harness. Telemetry is lossy, so the store holds no complete trace by promise.

The README holds the conventions, the colors and the map of every group.

Capability limits

  • Every other service plugs the interface of the Tracking Service in from ERD 1 onwards, so a trace identity and a root span identity exist in scheduler_execution before this group.
  • The server opens tracking.db at every start and runs the migrations of the Tracking Service on it. The file holds its own migration(service, version, applied_at) table. The README defines that table. In tracking.db it holds the history of the Tracking Service alone.
  • No service reads telemetry to make a decision, and no outcome depends on a row of this group.
  • A foreign key cannot reach kanthord.db. Every project, execution and node value of this group is a correlation value.

Records without a table

  • The local store of an external harness is an append-only log on the host of the harness, not a kanthord record. Only an ingested record is a kanthord record.
  • The Tracking Service holds no state of the progress of an ingestion between two ingestions.
  • The count of a drop and of a refusal is itself telemetry. Its representation is open in HANDOFF.

Tables

Table Owner Basis
tracking_trace Tracking Service Derived: a trace belongs to exactly one project or to no project, it is the unit of deletion, and an ingestion resolves the project through the records of the Tracking Service, under the trace and the project and ingestion. Ruled: the summary columns follow the trace summary.
tracking_span Tracking Service Ruled: primary store holds the span. The columns are derived from the trace model and the span record of the Tracking CLI.
tracking_record Tracking Service Derived: the Tracking Service deduplicates by the record identity that its producer mints, within the writable period of the trace. The identity has the form <span_id>:<name> and holds at most 128 characters.
tracking_telemetry_text Tracking Service Ruled: primary store holds the telemetry text; a trace delete deletes it with its trace. The columns are derived, and the identity of a text has the form <span_id>:<name>.
tracking_session_entry Tracking Service Ruled: session entries holds the entries of an agent session; a trace delete deletes them with their trace.

Constraints

The rules below have two kinds. A structural check is a rule that the Tracking Service enforces at the admission of a record. A producer obligation is a rule that the producer of a record follows, and the Tracking Service does not verify it. The Tracking Service refuses no record for its content.

Admission and durability

  • One transaction inserts the tracking_record row of a record and applies its contribution to its span, its telemetry text or its session entry. The acknowledgement answers Stored only after that commit.
  • tracking_record holds one row for each stored record identity of a trace. A repeat of that identity is Stored and changes nothing. A refused record and a dropped record leave no row.
  • target_id of a record names a span, a telemetry text or a session entry record of the same trace.
  • The records of one execution have a bound. A new record beyond that bound is Refused and writes neither its tracking_record row nor its contribution. A repeat of a stored record stays Stored and adds no row. The bound is 50,000 records for each trace.

Traces

  • A trace belongs to exactly one project or to no project. A server operation that concerns several projects opens one root span, and so one trace, for each project, and the root spans link to each other.
  • A unique index covers tracking_trace.execution_id where it is not null.
  • node_id and attempt of a trace with no execution name the node and the attempt of its server operation, or hold null. An act trace of the Mission Service names its node.
  • The first stored record of a trace creates its tracking_trace row. The server record of the Scheduler Service, an act trace of the Mission Service, an environment trace of the Project Service or the first write of a native worker creates it. For an execution, the Scheduler Service opens the root span after the claim records the execution, and trace_id, root_span_id, project_id and execution_id equal the values of the execution record. An imported record never creates a trace row.
  • A trace has exactly one root span, and root_span_id names it. A lost write of the root span leaves no root row. The trace then stays readable through its other spans, and a reader meets an unresolved parent. The representation of a missing root is open.
  • An ingestion carries no project. It names an existing trace, and it assigns no trace and reassigns no trace. The Tracking Service resolves the project from tracking_trace.
  • An imported record names an execution and a trace that agree with tracking_trace. A record that names another trace is refused.
  • A record that arrives after the writable period of its execution is refused with trace_expired. The predicate reads the ULID time of the execution identity, so it needs no tombstone.
  • The admission of a span updates the summary columns of its trace row in the same transaction. A summary column adds only the values that a record adds.

Spans

  • start_time or end_time is not null. A start with no end is an unfinished span. An end with no start creates the span with no start time.
  • A span row holds no copy of a column of its trace row and no column that an attribute derives. A read joins the trace row and reads attributes.
  • The Tracking Service persists a start when it arrives and an end when it arrives, so a reader reads a span that holds a start and no end. The root span of an execution is persisted when the server opens it.
  • The first record that creates a span binds it to its producer. A record that names that span from another producer is refused.
  • No record replaces a value that an earlier record set. A second end of one span is refused.
  • A record that names its own span identity as its parent is refused. The Tracking Service verifies no further ancestry. A span of an execution names the root span of that execution or a span that descends from it, and that rule is a producer obligation.
  • An unresolved parent is a fact that a reader sees, and never an error. A record can arrive before its parent.
  • producer is derived by the Tracking Service and never read from a record. The producer of an imported record is the claimant of the execution that the trace resolves to. A human who issues an ingestion produces no record.
  • origin distinguishes a span that the server observed from a span that an external harness asserted.
  • attributes maps a name to a value of one kind: a string, a boolean, an integer, a floating-point number or an array of one primitive kind. An event holds attributes of the same kinds.
  • A span carries the identity of every kanthord object that its operation concerns, as an identity attribute with the kanthord. prefix. One object has one attribute name in every span. An identity attribute holds an identity and never the content that it names. That rule is a producer obligation, and the registry of the attribute names is open.
  • A span attribute holds no authored prose. That rule is a producer obligation.
  • A span of links names a span of another trace. A link names no project.
  • text_ids names telemetry texts of the same trace.

Telemetry texts

  • A telemetry text belongs to exactly one trace. A span references it by identity and never embeds it.
  • An agent transcript is the ordered session entries of one agent session. A session entry is a record of its own kind and no telemetry text.
  • tracking_session_entry holds one row for each entry. A unique index covers (trace_id, session_id, sequence). A new entry at a taken sequence is refused.
  • No foreign key joins an entry to its agent.session span, so an entry can arrive before its span.
  • A telemetry text holds no deletion of its own and no expired_at, and content is NOT NULL. The deletion of its trace deletes it, and a reference to a deleted trace resolves to expired. Today the store keeps no tombstone, and a read of a deleted trace answers 404 tracking.trace.not_found. The text read checks the trace first. A text of a deleted or unknown trace answers 404 tracking.trace.not_found. A text that a held trace does not hold answers 404 tracking.text.not_found.

Deletion

  • The trace is the only unit of deletion. The deletion of a trace row deletes its spans, its records, its telemetry texts and its session entries through ON DELETE CASCADE. The deletion of a span deletes no telemetry text.
  • A human deletes a trace through tracking.trace.delete, directly or through a cleanup of the Footprint Service. The delete runs DELETE FROM tracking_trace WHERE trace_id = ? AND state != 'open', so an open trace stays. No start and no timer deletes a trace or a rollup row.
  • The operator configures the writable period of a trace once for the server, never per project, as tracking.trace_writable_days, default 30, a safe integer from 1 to 3650. It bounds only the admission of a record, and it deletes nothing.
  • A deletion of a telemetry row changes no outcome, removes no evidence and changes no state of a node.
  • Telemetry is the one exception to the rule that an owner deletes no record that a peer can reference, as architecture.impl.md rules. A human delete removes a trace that a peer references. scheduler_execution.trace_id and root_span_id keep their values after the deletion of their trace, and a read of them answers 404 tracking.trace.not_found.
