Read, decide and report review findings

Function description

A review finding records one blocker or one suggestion of a review round, or one defect that a human finds after delivery. A reviewer finding comes from the findings of an assessment submit. A human finding comes from finding create.

  • finding list returns one page of the findings of a node.
  • finding get returns one finding.
  • finding undecided list returns one page of the findings of a project that wait for a human.
  • finding decide records the decision of a human on a finding that waits for a human.
  • finding create records a human finding on a node.
  • finding update changes a human finding that holds no decision.

Every operation requires a human JWT.

Review rounds

Each execution assessment is one review round of its attempt. Round 1 reviews the change of the node against the base branch. A later round reviews only the patch since the tested commit of the latest base round of the attempt. When that commit is not on the first-parent history of the head, the round reviews the full change again. A base round has the result success, holds a reviewer finding or holds a fix-node proposal. execution review-round get gives the reviewer the round, the review base and the open findings. Assessments state the rework rule of a round.

A reviewer finding has the label B<n> for a blocker or S<n> for a suggestion. A blocker holds action: yes and a ground. A suggestion holds ground: null. The reviewer reports each defect once. It names each open finding that the change fixes in fixed_finding_ids of the next assessment. A finding that the reviewer does not name stays open.

Route and status

The route of a finding states who acts on it:

  • fix: KanthorD fixes it in a rework of the same attempt. The next coder@1 execution reads it with its identity.
  • report: a human reviews it.
  • record: the finding is information only.

The submit gives each new reviewer finding its route:

Finding route
action: no record
A finding of an assessment that is not current record
action: yes on an implement node, and the assessment causes a rework fix
action: yes on an examine node, and the assessment causes a rework record
action: yes, and the current assessment causes no rework report

A route changes later only from fix, and only for an open finding of the attempt:

  • A current assessment that causes no rework gives each open fix finding of its attempt the route report.
  • A node override or node block that closes the attempt gives each open fix finding of the attempt the route report.
  • A node discard that closes the attempt gives each open fix finding of the attempt the route record.

The status of a finding is fixed when fixed_assessment_id names an assessment, and open otherwise. A current assessment writes its own identity into fixed_assessment_id of each finding of its fixed_finding_ids. Only a fix finding can become fixed.

A finding waits for a human when its route is report and it holds no decision. finding decide takes one of two decisions:

  • accepted: the human agrees that the finding is a defect and owns its fix outside KanthorD.
  • dismissed: the human judges that the finding is no defect.

A decision changes no node, so it accepts a finding of a node in any state, Completed included. A second decision fails with 409 mission.finding.decided.

Human findings

A human records a defect that a human finds after delivery with finding create. The node can be in any state.

  • assessment_id names the assessment that missed the defect: an assessment of the attempt that delivered the code. Today the service accepts any assessment of the node. Read the assessment identities with assessment list. The finding takes the attempt of that assessment. A node with no assessment takes no human finding.
  • expected_mission_version is the version that mission get returns.
  • task_id names a task of the node revision of that assessment, or it is null.
  • The service gives the label H<n>, where n is 1 plus the count of the human findings of the node. It also gives action: yes, ground: null, the route report and created_by.
  • A human finding has no round, and no assessment can fix it. It makes no assessment a base round.
  • finding update changes the kind, the task, the four texts or the owner of the cause until a decision exists. A reviewer finding takes no update.

finding create and finding update check expected_mission_version and keep the mission version, because a finding changes no node. finding create, finding update and finding decide each write one act trace with equal node states before and after the act.

Each of the four texts name, description, fix and why is nonblank and holds at most 8192 UTF-8 bytes. This fixed limit does not follow mission.text_max_bytes. decision_reason holds at most mission.text_max_bytes UTF-8 bytes, 32768 by default.

The read operations change nothing. Each list call reads one page. The CLI does not follow next_cursor.

Expected response

finding list

The API returns HTTP 200. The CLI writes the same object as one JSON line to stdout and exits 0 (shown formatted here). 

{
  "items": [
    {
      "id": "finding_01M4C5G6BQ2X8D4N6R0T3V5W7Y",
      "node_id": "node_01M4C5G6BNQQPFNM7M8W0GW1W4",
      "attempt": 1,
      "round": 1,
      "assessment_id": "assessment_01M4C5G6BPZCGBK0EFKVT5AXH2",
      "source": "reviewer",
      "label": "B1",
      "kind": "blocker",
      "action": "yes",
      "task_id": null,
      "ground": "stated",
      "name": "Reset link never expires",
      "description": "The password reset token has no expiry check.",
      "fix": "Refuse a token older than 30 minutes.",
      "why": "The requirement states a 30-minute expiry.",
      "route": "fix",
      "status": "open",
      "fixed_assessment_id": null,
      "cause_owner": null,
      "created_by": null,
      "created_at": 1791409789303,
      "decision": null,
      "decision_reason": null,
      "decided_by": null,
      "decided_at": null
    }
  ],
  "next_cursor": null
}

The list orders the findings by these keys, in this order:

  1. The attempt.
  2. The round. The human findings come last.
  3. The kind. blocker comes first.
  4. The number of the label.
  5. The identity.

The cursor follows the same order. Without attempt, the list covers every attempt of the node. With round, the list holds only reviewer findings of that round.

finding get

The API returns HTTP 200 with one Finding. The CLI writes it as one JSON line to stdout and exits 0.

Finding

Property Type Purpose
id finding_<ulid> Identity of the finding.
node_id node_<ulid> Node of the finding.
attempt nonnegative safe integer Attempt of the assessment of the finding, computed at read time.
round positive safe integer or null Review round of the assessment, computed at read time; null for a human finding.
assessment_id assessment_<ulid> For a reviewer finding, the assessment that reported it. For a human finding, the assessment that missed the defect.
source string reviewer or human, computed at read time.
label string B<n> or S<n> for a reviewer finding, unique inside its assessment; H<n> for a human finding, unique inside the node.
kind string blocker or suggestion.
action string yes when the change applies, no for a no-op or a won't-do. Always yes for a human finding.
task_id task_<ulid> or null Task of the finding; null for the node criterion or the default standard.
ground string or null Ground of a reviewer blocker: stated, standard, unstated or conflict. null for a suggestion and for a human finding.
name, description, fix, why string Short name, the concrete defect, the recommended change and the reason for the action.
route string fix, report or record. See route and status.
status string open or fixed, computed from fixed_assessment_id.
fixed_assessment_id assessment_<ulid> or null Assessment that named the finding in fixed_finding_ids; null while the finding is open.

decided_by Actor or null human actor of the decision.
decided_at Unix milliseconds or null Time of the decision.

finding undecided list

The API returns HTTP 200 with the page shape of finding list. The page holds the findings of the mission of the project that wait for a human, in descending identity order.

finding decide, finding create and finding update

The API returns HTTP 200 with the Finding after the act. The CLI adds idempotency_key, the key of the request, and writes one JSON line to stdout, then exits 0.

Identity formats follow the identity reference. Timestamps are integer Unix milliseconds in UTC.

Failures

API failures use the shared error envelope.

An update with no field to change fails here.

cli.mission.finding.<command>.token_required All No nonblank token resolves.

cli.file.* decide, create, update --file is absent, not a regular file, -, not UTF-8, not JSON, has a repeated key, is not an object, or fails the schema (cli.file.schema_invalid).
cli.pagination.limit_invalid list, undecided list --limit is not a positive decimal integer.
cli.pagination.limit_out_of_range list, undecided list --limit is greater than 1000.

<command> is list, get, undecided.list, decide, create or update.

A declared failure makes the CLI exit 1 and print <code>: request failed and the row status: <status> to stderr. For a mutation, the CLI also prints the row idempotency_key: <key>. A transport failure, timeout or malformed response exits 1 with cli.mission.finding.<command>.indeterminate. For a mutation, retry with the printed key.

API shape

Command Method and path Operation ID Mutation
finding list GET /api/mission/node/:node_id/finding mission.finding.list No
finding get GET /api/mission/finding/:finding_id mission.finding.get No
finding undecided list GET /api/mission/project/:project_id/undecided-finding mission.finding.undecided.list No
finding decide POST /api/mission/finding/:finding_id/decide mission.finding.decide Yes
finding create POST /api/mission/node/:node_id/finding mission.finding.create Yes
finding update PATCH /api/mission/finding/:finding_id mission.finding.update Yes

Every operation has the access human (human bearer JWT) and a timeout of 30 seconds. node_id, finding_id and project_id are required path parameters.

Query field Commands Rule
attempt list Optional nonnegative safe integer.
round list Optional positive safe integer.
limit list, undecided list 1 to 1000, default 100.
cursor list, undecided list Optional next_cursor of the previous page.

A read takes no body. A mutation takes these headers:

Header Required Purpose
Authorization Yes Bearer <human-jwt>.
Content-Type Yes application/json.
Idempotency-Key Yes idempotency_key_<ulid>; retain it to retry the same act.

Each body accepts no unknown field.

Body Fields
FindingDecide Required decision (accepted or dismissed) and decision_reason (nonblank string).
FindingCreate Required expected_mission_version (positive integer), assessment_id, kind (blocker or suggestion), task_id (task_<ulid> or null), name, description, fix, why and cause_owner.
FindingUpdate Required expected_mission_version, plus at least one of kind, task_id, name, description, fix, why and cause_owner, with the types of FindingCreate.

FindingSubmit

Each item of findings of assessment submit is one FindingSubmit. It accepts no unknown field.

Field Type Rule
label string Required. Matches ^[BS][1-9][0-9]{0,2}$ and is unique in the submit. B is a blocker and S is a suggestion.
action yes or no Required. A blocker holds yes.
task_id task_<ulid> or null Required. A task of the pinned revision, or null.
ground string or null Required. A blocker holds stated, standard, unstated or conflict. A suggestion holds null.
name, description, fix, why nonblank string Required. At most 8192 UTF-8 bytes each.

A submit fails with 400 gateway.request.validation_failed and an issue at findings for each of these cases:

  • A bad or repeated label.
  • A blocker with action: no or with no ground.
  • A suggestion with a ground.
  • An unknown task_id.
  • A blank or oversized text.
  • More than 100 items.
  • A success with a blocker.

A submit fails with an issue at fixed_finding_ids for each of these cases:

  • A repeated identity.
  • An identity that names no open fix finding of the attempt.
  • A success that leaves out an open blocker of the attempt.

The check runs for every submit, also for a submit that is not current. 

curl -i 'http://127.0.0.1:31415/api/mission/node/node_01M4C5G6BNQQPFNM7M8W0GW1W4/finding?attempt=1' \
  -H 'Authorization: Bearer <human-jwt>'

curl -i -X POST http://127.0.0.1:31415/api/mission/finding/finding_01M4C5G6BQ2X8D4N6R0T3V5W7Y/decide \
  -H 'Authorization: Bearer <human-jwt>' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: idempotency_key_01M4C5G6DGWEVZYSPETSQR65JH' \
  -d '{"decision":"accepted","decision_reason":"The token expiry is a defect. The team fixes it in the next release."}'

The Gateway keeps the answer of a mutation for its idempotency key in process memory for gateway.idempotency_ttl seconds, 86400 by default. A retry with the same key, human account and request replays that answer, failures included.

CLI shape

kanthord mission finding list <node-id> [--attempt <attempt>] [--round <round>] [--limit <count>] [--cursor <cursor>]
kanthord mission finding get <finding-id>
kanthord mission finding undecided list <project-id> [--limit <count>] [--cursor <cursor>]
kanthord mission finding decide <finding-id> --file <path> [--idempotency-key <key>]
kanthord mission finding create <node-id> --file <path> [--idempotency-key <key>]
kanthord mission finding update <finding-id> --file <path> [--idempotency-key <key>]

Every command also accepts --token <jwt> and --endpoint <url>. 

kanthord mission finding list node_01M4C5G6BNQQPFNM7M8W0GW1W4 --attempt 1 --round 2
kanthord mission finding decide finding_01M4C5G6BQ2X8D4N6R0T3V5W7Y --file decide.json
kanthord mission finding create node_01M4C5G6BNQQPFNM7M8W0GW1W4 --file finding.json \
  --idempotency-key idempotency_key_01M4C5G6DGWEVZYSPETSQR65JH
Option Default / resolution Purpose
--attempt <attempt> list only; none, every attempt Nonnegative attempt number that selects one attempt.
--round <round> list only; none, every round Positive round number that selects one round.
--limit <count> 100 Maximum findings on the page, 1 to 1000.
--cursor <cursor> None; the first page next_cursor value of the previous page.

The help of each mutation prints an example file. An example finding.json for finding create: 

{
  "expected_mission_version": 8,
  "assessment_id": "assessment_01M4C5G6BPZCGBK0EFKVT5AXH2",
  "kind": "blocker",
  "task_id": null,
  "name": "Reset link works twice",
  "description": "A used password reset token signs the user in again.",
  "fix": "Mark the token used at the first sign-in.",
  "why": "A reset token is for one use only.",
  "cause_owner": "agent"
}

An example update.json for finding update: 

{
  "expected_mission_version": 8,
  "cause_owner": "plan"
}

The CLI validates the identity, the token, the key and the file before it sends a request. Each option is accepted once. See client configuration. The HTTP client has a 31-second deadline for these 30-second operations.
