Import a mission plan

Function description

An import replaces the whole plan of a mission in one transaction. The import set holds one node file for each node and one task file for each task that the plan keeps:

  • An entry without id creates a node or a task.
  • An entry with the id of a current node or task updates it.
  • A current node that no entry names is retired. A current task that no entry names is retired from its node.

mission import preview validates an import set and reports its effect. It writes nothing and stores no receipt. mission import apply validates the same set again, checks the preview digest and the confirmed retirements, and then writes all changes atomically.

An entry with the id of a retired node, of a task of a retired node, or of a task that an earlier write removed fails with mission.import.retired_id.

The import set has one of two formats:

  • markdown: plan files { filename, content }. The Mission service parses each file. The mission export page shows the plan file format.
  • json: plan entries with the fields of a JSON mission export entry.

node and depends_on name plan files inside the import set, never node IDs or paths. bindings holds binding names of the project. The service resolves each name to the current binding revision.

Plan files

A plan file is a node file or a task file. It holds exactly one of intent and node.

  • A node file holds intent: implement or examine. It takes the optional id (node_<ulid>), depends_on, tags, commit_type, bindings and verifications.
  • A task file holds node: the plan file name of a node file of the import set with intent: implement. It takes the optional id (task_<ulid>), bindings: [] and verifications.
  • A task file refuses depends_on, tags, intent and commit_type with mission.import.plan_invalid. details.reason names the key: depends_on_forbidden for depends_on, tags_forbidden for tags, form_invalid for intent, because the file then holds both intent and node, and unknown_key for commit_type and every other key outside the task file keys. An id with the prefix of the other file form fails with mission.import.plan_invalid.
  • After the front matter, one H1 supplies name, one ## Requirement section supplies requirement, and one ## Criterion section supplies criterion.
  • An absent tags reads [].
  • commit_type names the type of every worker commit of the node and of its pull request title: feat, fix, docs, style, refactor, test or chore. An absent commit_type stays absent, and the worker uses feat. Another value fails with mission.node.content_invalid. The commit names shows the headers.
  • name becomes the commit subject of the node or the task. A name that leaves no subject after the final full stops and spaces are removed, for example ., fails with mission.node.content_invalid.

An implement node with no task file is its own single work unit. An implement node with one or more task files covers its verifications with its tasks. Each verification of such a node equals a verification of one of its tasks in the import set. Another verification fails with mission.import.verification_uncovered.

Bindings of a node

A node names every binding that it uses. No node takes a binding from the project. The service resolves each binding name at write time and stores the resolved binding revision. A later change of the project moves no stored binding of a node. A node update or a rebind changes the stored bindings explicitly.

The intent of a node sets the count of each binding kind. A count outside the rule refuses the write with mission.node.bindings_invalid.

Intent Repository Storage Worker
implement 1 or more 0 or more, in order 0
examine 0 or more 0 or more, in order 0
  • An implement node names one or more repository bindings, and the convention is one binding. An implement node with no repository binding fails with mission.node.bindings_invalid.
  • An examine node changes none of its repository bindings. Its execution checks out the base-branch head of each one read-only.
  • The storage bindings of a node form an ordered upload list. An upload uses the first storage binding of that list that accepts the grant, under evidence.
  • A task names no binding. A task acts on every repository that its node names.
  • A mission export writes the binding names of each node, so an exported plan names every binding explicitly.

Import condition

The import condition is state Pending or Available with attempt 0. The import applies it to these current nodes:

  • Each node with changed content. For a task with changed content, the condition applies to its node.
  • Each node that gains or loses a task.
  • Each retired node.

These additional rules apply:

  • An import compares no content of a terminal node (Completed or Discarded). A terminal node with an unchanged filename is a no-op. The import resolves no binding name and no depends_on name of that node.
  • The import fails with mission.import.terminal_change for a new filename of a terminal node. It also fails for a task that enters, leaves or changes its filename in that node, and for a retirement of that node. The message of a retirement is "Import cannot retire a terminal node. Keep its unchanged file in the plan.".
  • A retirement of a node that holds an attempt fails with mission.import.condition_failed. The message is "Import cannot retire a node that holds an attempt. Discard the node, then keep its unchanged file in the plan.".
  • To remove a node that holds an attempt, discard it, then keep its unchanged file in the plan. An import that omits the file of a discarded node fails with mission.import.terminal_change.
  • A change of only depends_on requires a nonterminal node, not the import condition. The dependency rules of dependency apply.
  • A new dependency of a kept node requires no live claim on that node. Only apply checks this rule.
  • An import that adds an unmatched pair of a node and a claimable state fails with mission.node.tags_unmatched. The preview lists one violation for each node file with an added pair.

One failed check fails the whole import. A changed depends_on list counts as an update even if the content is unchanged. An apply that changes nothing keeps the mission version. An apply that changes the plan increases the mission version by one.

The preview digest covers the mission ID, the mission version, the normalized entries and the creates, updates and retirements sets. A change of these sets between the preview and the apply fails the apply with mission.import.retirement_mismatch. A stale mission version fails the preview and the apply. A preview reserves no node.

The import does not unblock a node, reopen an attempt or change priority. It records the human that submits the import as the actor of each revision.

Re-import an applied plan

The import matches a plan file to a current node or task by its id alone. A file name never matches a current node. A plan file without id creates a node or a task. The import retires every current node that no plan file names by id. An edited copy of plan files without id lines, for example the files of the first import, thus replaces the whole plan. Its preview lists every current node in retirements and every file in creates. A retired node that holds an attempt adds mission.import.condition_failed, and a retired terminal node adds mission.import.terminal_change. To remove a node that holds an attempt, follow the retirement exit.

To edit an applied plan:

  1. Export the plan as Markdown. Each exported file holds the id of its node or task.
  2. Edit the exported files. Keep each id line.
  3. Preview the edited files. Make sure that retirements and creates hold only the intended entries. Make sure that updates holds every node that you edited.
  4. Apply the same files. Set preview_digest to the digest of the preview, and set confirmed_retirements to its retirements. 
kanthord mission export mission_01M4C5J3SA6W8RBBC92HA9SSDS --format markdown --out ./plan
kanthord mission import preview mission_01M4C5J3SA6W8RBBC92HA9SSDS plan/*.md --file import.json
kanthord mission import apply mission_01M4C5J3SA6W8RBBC92HA9SSDS plan/*.md --file apply.json

The import.json of the preview:

{
  "format": "markdown",
  "mission_version": 7,
  "reason": "Tighten the login verification"
}

An edit of one verification in plan/login.md previews updates: ["node_01M4C5J3SAMS4Z4KZD8DQ9GFTB"], retirements: [] and creates: [].

The apply.json of the apply:

{
  "format": "markdown",
  "mission_version": 7,
  "reason": "Tighten the login verification",
  "preview_digest": "4f0c2e6a9b1d3c5e7f8a0b2c4d6e8f0a1b3c5d7e9f1a2b4c6d8e0f1a3b5c7d9e",
  "confirmed_retirements": []
}

The import condition also applies to a re-import. A node with changed content must be Pending or Available with attempt 0. To change a node that holds an attempt, use node update. The update applies from the next attempt. To redirect the open attempt, use the unblock path. To remove a node that holds an attempt, follow the retirement exit.

Expected response

import preview

The API returns HTTP 200 with the preview. A plan violation does not fail the request; the answer lists it in violations. 

{
  "mission_id": "mission_01M4C5J3SA6W8RBBC92HA9SSDS",
  "expected_mission_version": 7,
  "preview_digest": "4f0c2e6a9b1d3c5e7f8a0b2c4d6e8f0a1b3c5d7e9f1a2b4c6d8e0f1a3b5c7d9e",
  "creates": ["signup.md"],
  "updates": ["node_01M4C5J3SAMS4Z4KZD8DQ9GFTB"],
  "retirements": ["node_01M4C5J3SBEB4P8KDXAZ6GKB6R"],
  "removed_edges": [
    {
      "dependent_id": "node_01M4C5J3SAMS4Z4KZD8DQ9GFTB",
      "depends_on_id": "node_01M4C5J3SBEB4P8KDXAZ6GKB6R"
    }
  ],
  "no_ops": ["node_01M4C5J3SAYFD1BFNQB3BEBN6P"],
  "violations": []
}
Property Type Purpose
mission_id mission_<ulid> Mission of the route.
expected_mission_version positive integer The mission_version of the request.
preview_digest 64 lower-case hex chars Send this value as preview_digest to apply.
creates array of file names Entries without id.
updates array of node IDs Kept nodes with changed content or changed dependencies.
retirements array of node IDs Current nodes that the import set omits. Send this set as confirmed_retirements.
removed_edges array of edges Current dependency edges that the import removes.
no_ops array of node IDs Kept nodes without a change. A terminal node is always a no-op unless its filename changes. The import ignores the other content of its file.
violations array { code, message, filename, node_id, details } for each failed check. Empty when the import is valid.

The violation codes are mission.import.mission_mismatch, mission.import.duplicate_file, mission.import.plan_invalid, mission.import.duplicate_id, mission.import.unknown_id, mission.import.foreign_id, mission.import.retired_id, mission.import.unresolved_reference, mission.import.reference_kind_invalid, mission.import.cycle, mission.import.verification_uncovered, mission.import.terminal_change, mission.import.condition_failed, mission.node.content_invalid, mission.node.verifications_missing, mission.node.bindings_invalid, mission.node.state_conflict and mission.node.tags_unmatched.

The import validates in three stages: the plan files and their content, the resolved graph, then the import condition. A preview reports every violation of the first stage that fails and stops there. When the three stages pass, the preview runs the write steps of the apply and rolls them back. It then lists one mission.node.tags_unmatched violation for each node file with an added unmatched pair. That violation holds details.claims, and node_id is null for a created node, also in each claim.

import apply

The API returns HTTP 200 with the import result:

{
  "mission_id": "mission_01M4C5J3SA6W8RBBC92HA9SSDS",
  "mission_version": 8,
  "assigned_ids": [
    { "filename": "login.md", "node_id": "node_01M4C5J3SAMS4Z4KZD8DQ9GFTB" },
    {
      "filename": "login-form.md",
      "task_id": "task_01M4C5J3SAYFD1BFNQB3BEBN6P"
    },
    { "filename": "signup.md", "node_id": "node_01M4C5J3SBKF4M6X325KZGRKHH" }
  ],
  "changes": {
    "mission_version": 8,
    "revisions": [],
    "retired_node_ids": ["node_01M4C5J3SBEB4P8KDXAZ6GKB6R"],
    "added_edges": [],
    "removed_edges": [],
    "open_attempts_unchanged": []
  },
  "actor": { "kind": "human", "account": "<account>", "name": "<name>" },
  "accepted_at": 1791446400000
}
Property Type Purpose
mission_id mission_<ulid> Imported mission.
mission_version positive integer Mission version after the apply.
assigned_ids array { filename, node_id } for every node file and { filename, task_id } for every task file, sorted by file name, with the IDs of new nodes and tasks.
changes object The node change result of the import.
actor object The human that submitted the import.
accepted_at integer Acceptance time in Unix milliseconds.

The CLI writes the result plus idempotency_key as one JSON line to stdout and exits 0. The CLI writes no assigned ID back to a plan file. Run mission export to get plan files with IDs.

Failures

API failures use the shared error envelope.

HTTP status / code Operation Meaning
401 gateway.authentication.unauthorized Both Absent, invalid or expired token, or a machine token.
415 gateway.request.unsupported_media_type Both Content-Type is not application/json.
400 gateway.request.invalid_json Both The body is not valid JSON with unique object members.
400 gateway.request.validation_failed Both The body fails the schema, for example an unknown field.
413 gateway.request.body_too_large Both The body exceeds 32 MiB.
400 gateway.idempotency.invalid_key Apply Absent or malformed Idempotency-Key.
409 gateway.idempotency.conflict Apply The key belongs to another request, or its first request is still in progress.
404 mission.mission.not_found Both The mission ID is unknown.
409 mission.version.conflict Both mission_version is stale; details.current holds the current version.
400 mission.node.content_invalid Both reason is blank or exceeds the text limit.
400 or 409 with a violation code Apply The first violation of the preview. 409 for mission.import.condition_failed, mission.import.terminal_change and mission.node.state_conflict, otherwise 400. details adds filename and node_id.
409 mission.node.tags_unmatched Apply The import adds an unmatched pair; details.claims lists each pair as { node_id, revision, claim }.
409 mission.node.filename_conflict Apply Another current node or task of the mission uses the file name; details.filename names it.
409 mission.import.retirement_mismatch Apply preview_digest or confirmed_retirements does not match the current preview.
409 mission.node.claim_live Apply A new dependency names a dependent with a live claim.
504 gateway.invocation.timeout Both The operation exceeded 30 seconds. An apply can still complete.

The text limit is the server configuration value mission.text_max_bytes, 32768 UTF-8 bytes by default.

The CLI exits 1 on every failure and writes <code>: <message> to stderr. A declared remote failure prints <code>: request failed and the row status: <status>. For apply, the CLI prints <code>: request failed and the rows status: <status> and idempotency_key: <key> instead.

cli.mission.import.<action>.files_conflict The file sets format: "markdown", holds files, and the command has plan-file positionals.
cli.mission.import.<action>.token_required No nonblank token resolves.

cli.file.not_found, cli.file.not_regular --file or a plan file is absent or is not a regular file.
cli.file.invalid_path --file is -; the CLI does not read stdin.
cli.file.encoding_invalid, cli.file.not_json, cli.file.duplicate_key, cli.file.not_object --file is not UTF-8, not JSON, has a repeated key, or is not an object.
cli.file.schema_invalid The completed body fails the request schema.
cli.idempotency_key.invalid --idempotency-key is not an idempotency_key_<ulid> value.

<action> is preview or apply.

Header Required Purpose
Authorization Yes Bearer <human-jwt>.
Content-Type Yes application/json.
Idempotency-Key Apply only idempotency_key_<ulid>; retain it to retry the same apply. 
curl -i -X POST http://127.0.0.1:31415/api/mission/mission_01M4C5J3SA6W8RBBC92HA9SSDS/import \
  -H 'Authorization: Bearer <human-jwt>' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: idempotency_key_01M4C5J3SBXJ52XQ9FSFRTK4PR' \
  -d '{"format":"json","mission_id":"mission_01M4C5J3SA6W8RBBC92HA9SSDS","mission_version":7,"reason":"Add sign-up","entries":[],"preview_digest":"<digest>","confirmed_retirements":[]}'

The Gateway keeps the answer of a mutation for its idempotency key in process memory for idempotency_ttl seconds, 86400 by default. A retry with the same key, human account and request replays that answer. This rule also applies to a failure.

CLI shape

kanthord mission import preview <mission-id> [plan-file...] --file <path> [--token <jwt>] [--endpoint <url>]
kanthord mission import apply <mission-id> [plan-file...] --file <path> [--idempotency-key <key>] [--token <jwt>] [--endpoint <url>]
kanthord mission import preview mission_01M4C5J3SA6W8RBBC92HA9SSDS plan/*.md --file import.json
kanthord mission import apply mission_01M4C5J3SA6W8RBBC92HA9SSDS plan/*.md \
  --file apply.json --idempotency-key idempotency_key_01M4C5J3SBXJ52XQ9FSFRTK4PR
Positional argument Purpose
<mission-id> Required mission_<ulid>.
[plan-file...] Markdown plan files in import order. Only for format: "markdown".
Option Default / resolution Purpose
--file <path> Required; no default JSON file with the import controls and, for JSON format, entries.
--idempotency-key <key> Apply only; a generated idempotency_key_<ulid> Sets Idempotency-Key; supply the same key to retry.
--token <jwt> KANTHORD_TOKEN → client-file token; a nonblank resolved token is required Human JWT sent as the bearer credential.
--endpoint <url> KANTHORD_ENDPOINT → client-file endpoint → http://127.0.0.1:31415 Server base URL.

The CLI builds the request body from --file as follows:

  • If the file has no mission_id, the CLI sets it from <mission-id>.
  • For format: "markdown" with positionals, the CLI reads each plan file and sends its base name as filename and its text as content. It does not parse Markdown.
  • For format: "markdown" without positionals, the CLI sends the files of the file unchanged. If the file has no files, the schema check fails with cli.file.schema_invalid, and the CLI sends no request. An empty set needs an explicit "files": [].
  • For format: "json", the CLI sends the entries of the file.

The CLI does not scan directories and asks for no confirmation. Each option is accepted once. See client configuration. The HTTP client has a 31-second deadline.
