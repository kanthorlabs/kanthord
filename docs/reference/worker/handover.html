Hand over execution credentials

Function description

Receive the provider credential of a running execution as a sealed envelope. The caller is a registered worker instance that holds a live claim on the execution.

The server reads the worker binding of the execution and the agent selection that its claim pinned. It then releases the credential revision that the execution pins. If the execution pins no revision yet, the handover pins the newest live revision of that credential. The server seals the credential with AES-256-GCM before the response.

The first handover of an attempt also writes the attempt prompt pin. It reads the base head of each repository binding that names an instruction file, with a 20-second deadline, and pins that commit for every execution of the attempt.

When the instance of the caller is at the server or the container placement, the server releases the server copy of the credential; see instance copies. Each item of the envelope is { credential_id, provider_id, credential }. A name with live instance copies and no live server copy fails with 409 credential.credential.held_by_instance.

When the instance of the caller is at the worker placement, the server releases only the copy of the copy holder of that instance, sealed to the current key of that holder. The copy holder is the instance when the instance holds a live own copy of the name. Else it is the worker machine of the instance. Each item of the envelope is { credential_id, provider_id, name, platform, holder, sealed }. holder is the holder of the copy. The server never opens sealed. The worker opens it with the private key of that holder: the key of its instance, or the machine key of the machine configuration. The worker reads the machine key at each use. A copy that the key does not open, or a machine with no machine configuration, fails the handover on the worker with worker.handover.sealed_unopened. At this placement, ssh_identities is [].

At the first use of a name in an execution, the handover pins the newest live revision of the copy holder. A later handover of that execution reads the pinned revision, whatever the copy holder is then. An own copy that is sealed to an ended key of the instance does not fall back to the machine copy. The handover refuses it.

The worker sends a refresh report of a pinned credential to POST /api/worker/credential, sealed in the same way. The report is { credential_id, digest, credential }. For a machine or an instance copy, the report is { credential_id, digest, sealed }, and digest is the digest of the stored sealed object. The worker seals the report with the key of the holder of the item. Before an OAuth refresh, the worker takes the refresh lease of the revision.

The envelope also carries the SSH key of each repository binding of the pinned node revision, as ssh_identities: one { binding_id, credential_id, private_key } item for each binding. An execution with no repository binding gets []. The handover pins each SSH credential revision to the execution in the same way. The worker matches each item to its setup entry by binding_id, keeps the key in memory, and writes no private key file. A worker host therefore needs no SSH key of its own.

The seal key derives from the client secret of the caller's client identity. The additional authenticated data binds the envelope to the execution identity and the runtime identity. The worker opens the envelope with a key that it derives from the same client secret.

The response is secret. Gateway records no replayable answer for it. A repeated idempotency key returns a conflict without the envelope. Use a new key to receive the envelope again.

worker handover calls the same operation but discards the envelope. It prints only a receipt. Use it to check that a handover succeeds; worker runtimes call the API directly to use the credential.

Expected response

The API returns HTTP 200 with the sealed envelope:

{ "nonce": "<base64-nonce>", "ciphertext": "<base64-ciphertext>" }
Property Type Surface Purpose
nonce base64 string API only 12-byte AES-256-GCM nonce.
ciphertext base64 string API only Encrypted credential, followed by the 16-byte authentication tag.

The CLI writes one JSON line to stdout and exits 0 (shown formatted here): 

{
  "received": true,
  "idempotency_key": "idempotency_key_01M34JC4BJ66JHP41M4MYY6PST"
}
Property Type Surface Purpose
received boolean, always true CLI only The server returned an envelope.
idempotency_key idempotency_key_<ulid> string CLI only Key used for this request.

The CLI output contains no envelope, nonce or credential.

Failures

API failures use the shared error envelope.

HTTP status / code Meaning
401 gateway.authentication.unauthorized Missing, invalid, expired or human token; also a machine token whose worker binding does not resolve.
403 gateway.registration.required The client identity of the token has no live registration.
415 gateway.request.unsupported_media_type The Content-Type is not application/json.
400 gateway.request.validation_failed The body is not exactly { "execution_id": "<execution-id>" } with a canonical execution identity.
413 gateway.request.body_too_large The body is larger than 32 MiB.
403 gateway.invocation.execution_proof_failed The execution is not a live, unexpired claim of the caller's registration.
400 gateway.idempotency.invalid_key Missing or malformed idempotency key, checked after the execution proof.
409 gateway.idempotency.conflict The caller used the key before; a repeat of a completed handover also conflicts.
403 worker.authorization.refused The worker binding does not permit the handover. details.reason is binding_mismatch, binding_removed, binding_disabled or no_native_agent. A draining execution of a native binding with worker_instances: [] gets no binding_disabled.
400 agent configuration code The effective agent configuration is not valid; the code is the first issue, for example agent.enablement.unavailable.
409 credential.revision.revoked The pinned credential revision is revoked.
422 project.bindings.repository.ssh_unreachable The first handover of an attempt cannot read the base head of a binding that names an instruction file, or the read exceeds its 20-second deadline. details.failure_reason names the cause.
422 project.bindings.repository.base_branch_absent The first handover of an attempt finds that the remote does not hold the base branch of a binding that names an instruction file.
403 custody.handover.holder_refused worker placement only: the copy holder of the instance holds no live copy sealed to its current key, for example a stale own copy or a machine copy after a Reset key of the machine. details.reason is server_held when only the server copy exists, else held_elsewhere.
409 credential.credential.held_by_instance server and container placements only: the credential has live machine or instance copies and no live server copy.
409 repository.host_key.unpinned The address host of a repository binding holds no pin. details.host holds the host.
409 repository.credential.ssh_key_legacy The ssh credential of a repository binding holds no generated key. details.credential holds the name.
404 credential.credential.not_found The credential has no live revision to pin.
400 credential.platform.mismatch The credential platform does not match the agent provider.
503 worker.handover.refresh_in_flight server and container placements only: an OAuth refresh of the pinned credential revision does not end in the handover wait. The handover pins nothing. Retry with a new key; the worker retries until the claim expires.

A declared failure makes the CLI exit 1 and write <code>: worker handover: request failed and the rows status: <status> and idempotency_key: <key> to stderr. A transport failure, timeout or malformed response exits 1 with cli.worker.handover.indeterminate and the message worker handover: the result is unknown; retry with a new idempotency key. It prints no idempotency_key row. Retry an indeterminate result with a new --idempotency-key, because a repeated key always conflicts.

CLI shape

kanthord worker handover <execution-id> [--token <jwt>] [--endpoint <url>] [--idempotency-key <key>]

  --token '<machine-jwt>' \

Argument Purpose
<execution-id> Canonical execution identity that the caller's instance claims.
Option Default / resolution Purpose
--token <jwt> KANTHORD_TOKEN → client-file token; a nonblank resolved token is required Machine JWT sent as the bearer credential.
--endpoint <url> KANTHORD_ENDPOINT → client-file endpoint → http://127.0.0.1:31415 Server base URL.
--idempotency-key <key> A generated idempotency_key_<ulid> Sets the Idempotency-Key header.

The CLI checks its input before the request. An invalid execution identity fails with cli.worker.handover.invalid_execution_id. A missing token fails with cli.worker.handover.token_required. A malformed key fails with cli.idempotency_key.invalid. A repeated --token or --idempotency-key fails with cli.option.duplicate. See client configuration for the token and endpoint precedence. The HTTP client deadline is 31 seconds.

The refresh lease

One execution at a time refreshes one OAuth credential revision, at every placement. Before an OAuth refresh, the execution store of the worker calls worker.credential.lease. pi-ai asks for a refresh only for a token that expires within 5 minutes, so a model call takes no lease.

  • The server keeps one lease for each credential revision in memory: { execution_id, expires_at }. A server restart ends every lease. A lease lasts 30000 ms. That covers the OAuth refresh timeout of pi-ai, 15 seconds, and the report.
  • The answer is an envelope, sealed with the handover key of the execution. Its payload is { item, expires_at }. item is the handover item of the stored value of the revision: plain for the holder server, sealed with holder for another holder.
  • The worker adopts the stored value of the answer and refreshes that value. It then sends one POST /api/worker/credential report, also for an unchanged value.
  • A lease of the same execution renews the lease. A lease past expires_at lets another execution take a new lease.
  • A report of the lease holder ends the lease after its write. A report of another execution keeps the lease. The digest rule of the report does not change.
  • Before each retry of its report, the lease holder renews its lease. The lease ends at the report or at its expiry.
  • The worker keeps the handover key of an execution until the execution ends, and zeroes it then. Each lease answer opens with that key.
  • The worker retries worker.credential.lease_held with a new key and the backoff of an indeterminate result. The retry ends when the claim expires or the refresh call aborts.
  • The handover does not wait for a lease. A check of a revision under a lease does not refresh, because the lease holder pins the revision.
Item Value
Method and path POST /api/worker/credential/lease
Operation ID worker.credential.lease
Access client (machine bearer JWT) with a live registration and an execution proof of a live execution
Mutation Yes; secret, so no answer is replayed
Request body { "execution_id", "credential_id" }. credential_id is a revision that the execution pins.

No CLI command calls this operation.

HTTP status / code Meaning
400 custody.handover.lease_invalid The execution does not pin the revision.
409 credential.revision.revoked The revision ended.
503 worker.credential.lease_held Another live execution holds an unexpired lease of the revision, or a check refresh of the revision is in flight. Retry with a new key.
